# 物理寄存器数量做成可配置（64 / 96）

2026-10-08 立。用户定案：**不改 IDU，改 RTU** —— 把 preg 数量做成构建期可配，
64 档与同事交付的 C910 IDU 的 6 位 preg 直接对得上，96 档保持与 D-cache LSU 一致。

---

## 0. 一句话

加一个构建期开关 `PREG=64|96`（默认 96，**不改现有行为**），
**池子、端口位宽、AMT 都跟着档走**；**只有 ROB 表项位域固定 7 位**。

> ⚠️ **2026-10-10 修订**。本节原来写的是"只参数化池子，端口位宽/表项位域/AMT 一律固定
> 取最大值 7 位"。那一版被推翻了，理由与代价见下面 §2 的新表。**旧文留在 §2 的
> "为什么当初不这么做"里** —— 那是这次改动的原始动机记录，别删。

---

## 1. 为什么是"构建期 define"而不是 Verilog `parameter`

1. **仓库先例**：`IFU=0/1/2`、`DCACHE_SIZE`、`BP_PRED` 都是构建期 define + 配置戳
   （`Makefile` 的 `IFU_CFG`）。池子大小与它们是同一类东西：决定**位宽**（数组、掩码常量、
   树、generate 循环），而不只是数值。
2. **要让全构建一致**：整核（`mycpu.v` 里那个 RTU 实例）、两个单测台、变异台都要知道
   它是 64 还是 96。define 走 `RTU_define.vh`，一处定义处处可见；`parameter` 只到得了
   实例化它的那一层，测试台拿不到（除非去读层次里的 `$size`）。
3. ⚠️ **必须带配置戳**：`IFU` 那个坑记在 `memory/ifu-integration.md` 里 —— 只改 `DEFINES`
   而它**不是 `$(SIMV)` 的前置**时，`make build` 会"源文件没变"跳过重编译、静默沿用旧
   simv（两次 CoreMark 返回逐位相同的周期数才被发现）。`PREG` 走同一套戳。

## 2. 哪些东西跟着变、哪些不变（**这是本方案的关键取舍**）

| 项 | 64 档 | 96 档 | 说明 |
|---|---|---|---|
| 池子状态表 `st/nst`、选择树、掩码 `PREG_BM*`、`hit_disp`/`is_wf`/`arch_vec` | **64 项** | 96 项 | 跟着配置变 |
| `free_cnt` 的复位常数与冲刷重算 | `64−32` | `96−32` | 跟着配置变 |
| **端口位宽**（`rtu_preg_alloc*`、`disp*_dst_preg`、`rtu_preg_raddr*`…） | **6 位** | 7 位 | 跟着档走（`RTU_PREG_W`） |
| **ROB 表项位域**（`RTU_E_DST_PREG`/`OLD_PREG`） | 7 位 | 7 位 | **固定取最大值**（`RTU_PREG_EW`），见下 |
| **AMT**（32 × `RTU_PREG_W`）与 `rtu_ren_recover_map` | 192 | 224 | 跟着档走（它是端口） |

### 2.1 为什么当初不把端口也收窄（**2026-10-10 已推翻，但记在这里**）

原话：*"那样就得用 `` `ifdef `` 包住整张端口表…… 端口表随配置变形会让契约失去
'唯一一份'的意义，接线的人还得知道当前是哪一档。"*
**代价**：64 档里每个 preg 字段白占 2 位 —— 表项 4 位/项 × 64 = 256 位，AMT 32 位。

**推翻的两条理由**：

1. **不需要 `ifdef`**。把端口写成 ``[`RTU_PREG_W-1:0]`` 就行 —— 一份端口表，宽度随宏。
   契约的"唯一一份"仍然成立（端口名与语义不变），变的只是**位宽不再是常量**。
2. **"不碰任何其它模块"是假象**。64 档下编号最高位恒 0，靠的是**端口处的隐式截位** ——
   而隐式截位不报错、不报 x。更要紧的是适配层得替它补两件事（alloc 切位、恢复表逐槽
   重排），而那两件**本来就是位宽差造成的**。端口跟着档走后：
   * `rtu_preg_raddr*` / `rtu_csr_rd_addr` 与 IDU 的 6 位**天然同宽**
     ⇒ `a910-elab` 的 `PCWM-W` 从 **5 条收到 0 条**；
   * 恢复表 32×6 与 IDU 的布局**逐位相同** ⇒ 适配层那段重排在 64 档退化成恒等；
   * 位宽差只剩**一处**、而且**显式**：适配层里那几个带 ⚠️ 的切片。

**这次不图面积**：表项位域还是 7 位（256 位浪费照旧），因为位域是**位置宏**
（`RTU_E_DST_PREG 26:20`），一缩后面所有字段整体挪一格，而拼接是隐式零扩展的
（2026-10-10 真踩过：见 §2.2）。AMT 那 32 位跟着端口一起收掉了。

### 2.2 ⚠️ 改这个宏时的两个真坑（都是 2026-10-10 踩出来的）

1. **同文件里的 `[6:0]` 不都是 preg**。还有三类也是 7 位、但绝不能跟着变：
   * iid —— `cmplt_iid*` / `rtu_disp_iid*` / `expt_*_iid` …（= `RTU_IID_W`）
   * flags —— `disp*_flags` / `f0`/`f1`/`f2`（= 7 个 `RTU_FLG_*` 位）
   * 占用数 —— `occ` / `occ_q` / `rob_occ` / `free_cnt` / `arch_cnt`
   一刀切会把它们截成 6 位，**而且不报错**。改完必须两档都跑 `make rtu-unit`
   （随机压力台）。
2. **表项拼接会整体挪格**。`RTU.v` 里 `disp_data* = {... disp0_dst_preg, ...}` 那一大坨：
   端口收窄后拼接短了 2 位，赋给 125 位的表项时 Verilog 在**最高位**零扩展 ⇒
   **所有位域下移 2 格**，`vld` 落到 121 上读成 0。指纹是"ROB 占用计数在涨，但
   `rob_q[0][RTU_E_VLD]` 恒 0"。修法是给那几个字段加 `RTU_PREG_EW` 宽的显式零扩展中间量。

对外表现：**64 档下编号的最高位恒 0**（池子里根本没有 ≥64 的号）。
所以将来接 C910 IDU 时，适配层直接切 `[5:0]` 就行；恢复表 `32×7 → 32×6` 的重排在适配层做
（那件事与池子大小无关，本来就躲不掉）。
为此加一条**跟配置绑定的自检**：64 档下 `PREG_BM6` 必须为 0 —— 否则编号第 6 位可能为 1，
而池子只有 64 项（照 §9 R7 那个"改了宏没生效"的坑的惯例，让它在 elaborate 期就炸）。

## 3. ⚠️ 64 档的固有代价：自由池只有 32 项（**与实现无关，要记在账上**）

池子里 32 项是 x0..x31 的初始映射（D1.2 之后它们**可被顶掉回收**，但任一时刻恒有 32 项
处于 ARCH 态 —— 每条 lreg 一个当前映射）。所以：

```
自由池 = NUM_PREG − 32   ⇒   64 档 = 32 项
```

而 ROB 深度是 64（`RTU_ROB_DEPTH`，本次不动）⇒ **在途的"写寄存器"指令最多 32 条**，
64 项 ROB 填不满。这正是 `rtu_plan_zh.md` §4 不变量 2 批评参考核的那句话
（"free_list 只有 32 项却配 64 项 ROB"）。

⇒ 64 档的正确用法是**配 `RTU_ROB_DEPTH=32`**（那是另一个宏，本次没动，留作后续）；
或者接受窗口被压到 32 —— 功能不受影响，只是乱序深度小。

> ⚠️ **实测更正（2026-10-08）**：我在写这一节时以为"64 档会成为自由池被打空的天然测试"。
> 加了个临时计数器量了一下，**两档完全一样**：单测台里"要号但门房没号"各 35 拍、
> **自由池为 0 的拍数两档都是 0**。那 35 拍是复位/冲刷之后"门房还没补上号"的**瞬态**，
> 不是容量打空（单测台的派遣节奏被 `csr_inflight`/冲刷/ROB 满夹着，在途条数远填不满 32 个自由号）。
> ⇒ **容量性打空两档都没测到**，"池子空了要停"这条路只有瞬态覆盖。

## 6. 没验证到的 / 边界

* **池子被容量性打空**（自由池 = 0）**两档都没测到**（§3 的实测更正）。要覆盖它得专门
  造激励：单测台里把派遣节奏放开（别让 `csr_inflight`/冲刷夹着）、或少 retire 几条。
* **接口没有随配置收窄**：`[6]` 位在 64 档恒 0，但**没有任何检查**保证这一点
  （自检只保证掩码，不保证"消费者不会写进池子的号"）。当前没有任何消费者；
  接 IDU 时由适配层切 `[5:0]` 负责。
* **`RTU_ROB_DEPTH` 没跟着调**（§3）：64 档配 64 项 ROB 会浪费一半窗口，
  本次只记账、不动。
* **第 5 态在主流程里不可达**（2026-10-08）：阶段 1 `ret_free_vld ≡ 0` 且交付 IDU 的
  掩码寄存器现在恒 0 ⇒ 整核跑不出 `RELEASE`。功能证据全在单测台（`+MASKDIR`/`+MASKPCT`）；
  整核那条 A/B 只能证"没碰坏"，不能证"新状态对"。
* 面积/时序一个字不声称（本机没有 Vivado）。64 档理论上更小（选择树少一级、
  状态表少 64 位），但没量过。
