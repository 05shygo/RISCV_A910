# RTU 分配握手改造计划 —— 照 C910 的"门房保持寄存器"

2026-10-07 立。改的是 `mySoC/rtu/rtl/RTU_preg.v` 与 `RTU.v` 的一处门控，
**IDU 一行不动**（它是同事交付件，而且它那侧的行为本来就是这套协议的另一半）。
起因见 `doc/idu_rtu_接口待办.txt` 第一节。

---

## 0. 一句话

把"本拍请求 → 组合出编号与许可"改成 **C910 的"提前把号备在门口，谁要谁拿"**：
编号与许可都进寄存器，被取走的那一拍才补下一个。顺带删掉"没人认领满两拍就回收"
的年龄回收 —— 那条在 C910 模型下必然误伤（号被取走后要经 IR→IS→派发才到 ROB，
中间可能被 IQ 满卡几百拍）。

---

## 1. 要断的环（三条，一条都不能留）

| # | 环 | 位置 |
|---|---|---|
| **1a** | `rtu_idu_alloc_preg*_vld` 是**本拍请求的组合函数**，而 IDU 拿它当"同拍许可"并反馈进停顿链 | `RTU_preg.v:242-244` ↔ `ct_idu_ir_ctrl.sv:246-259` |
| **1b** | `preg_short = free_cnt < ren_preg_req` 进 `disp_stall`，而 `disp_stall → rtu_idu_rob_full → ctrl_is_stall → ctrl_ir_stall → 请求` 又绕回 `ren_preg_req` | `RTU.v:686/691` ↔ `ct_idu_is_ctrl.sv:560-567` |
| **1c** | （同一类，本次不改）IDU 内部把 `rtu_idu_alloc_preg*` 的**编号**当拍组合进 RAT 写数据 | `ct_idu_ir_dp.sv:283-285` |

1c 不是我们要断的环 —— 它是 IDU 与 RTU 之间**唯一一条跨模块的组合路径**，
寄存器到寄存器（IDU 的 IR 寄存器 → 96 位优先编码器 → IDU 的 RAT 写口寄存器），
合法且必要。C910 靠"号已经在寄存器里"把它缩短；我们照做之后，
这条路径变成"IDU 寄存器 → 我们的编码器 → **我们的 tap 寄存器**"，
反而短了（见 §2）。

⚠️ **1b 是这次核出来的新问题**，原计划没提。C910 那侧不成立，因为它的
`rtu_idu_rob_full` 是**寄存器**（`ct_rtu_rob.v:4479`），而我们的
`preg_short` 依赖本拍请求，经 `disp_stall` 绕回 IDU 的停顿链再绕回请求。
池子快要见底时它会**振荡**（`preg_short=1 → 停 → 请求=0 → preg_short=0 → 放行 → …`）。
去掉它的理由：真正该告诉消费者"这一路拿不到号"的是**每路的 alloc vld**（1a 修完之后
它是寄存值），`preg_short` 既冗余又有环。

## 2. 新协议（与 C910 `ct_rtu_pst_preg.v:7376-7393` 同构）

```
        ┌──────────── tap (每路一份, 都是寄存器) ────────────┐
池子 ──>│ pop_lane[k] ? 取一个 FREE 装进来 : 保持不动        │──> rtu_preg_alloc{k}
(96项)  │ pop_lane[k] = !tap_vld[k] | take[k] | tap_hit[k]   │──> rtu_preg_alloc_vld{k}
        └───────────────────────────────────────────────────┘
```

* **take[k]** = 消费者本拍请求了这一路（`req_lane[k]`）—— "请求即取走"。
* **tap_hit[k]** = 本拍派遣里那个号正好是本路备着的号（兜"没请求却派出去"）。
  有它，误用只会让那一路**提前补号**，不会把同一个号发两次。
* **池子的 WF_ALLOC 标记跟着 `pop_lane` 走**（不是跟着请求走）：装进 tap 的那一刻
  这个号就出池子了，之后谁取走、什么时候派遣，池子都不再关心。

**时序（T = 走货那一拍）**

| 拍 | 发生什么 |
|---|---|
| T | 消费者的 IR 级指令**当拍取走** `rtu_preg_alloc{k}`（tap 里的号），同拍用进 RAT |
| T 边沿 | 该路的 tap 补号（重新从池子选一个 FREE 装进去）；池子把新号标 WF_ALLOC |
| T+1.. | 指令经 IS → IS 派发 到 ROB；派遣带着这个号回来 → `hit_disp` 认领 → ALLOC |

⇒ 与旧协议的区别只有一处：**号从"本拍现选"变成"上一拍就备好"**，
于是许可与编号都不再依赖本拍请求 ⇒ 环 1a 断开。

### 3.3 `tb/unit/tb_rtu_rob.sv`

| 位置 | 改动 |
|---|---|
| `:322` | `ren_preg_req` 加 `!disp_stall` **和** `all_need_vld` 门控 —— 照 IDU 的 `!ctrl_ir_stall` |
| `:871-877` | "分配器给出非 FREE" → **"非 WF_ALLOC"**：现在取到的是早就备好的号 |
| 新增检查 | **"备号"不变量**（见 §4）—— 这是本次改动唯一的正向判据，也是 R08 的锚 |
| D_REQ 分支 | 拆成三分支：停派遣 → 丢计划（没取走任何号，安全）；**号没到手 → 原地等**；号到手 → 进 D_DISP |
| D_DISP 分支 | 拆成两支：**被接受**（或本来就是空计划）→ 推进；**没被接受** → **原地举着这份计划**，并**先把接受位结算掉再重新上膛** |

⚠️ **单测台这三处是实跑才逼出来的，纸面推不出来**，逐条留证（都是"症状不指向病因"的那种）：

1. **"原地举着"时重上膛会冲掉接受位** —— 第一版我让 D_DISP 停派遣时原地上膛重试，
   结果 `acc_q`（posedge 锁存）被下一个 posedge 覆盖成 0，**已经真的接受了的 2 条**
   永远进不了参考流。症状：DUT 的 ROB 占用数比参考流多 2，且**差多少都不会自己回来**；
   紧接着参考流里没有那两条 ⇒ 永远没有完成信号 ⇒ 永久停住。
   ⇒ 修法：停下来之前先把 `acc_q` 结算掉（`dispatch_record`），再上膛。
2. **空计划会死等** —— `gen_plan` 有 `n = rand%4 == 0` 的可能。没有"要么空、要么被接受"
   这一条，D_DISP 会为空计划永远等下去。
3. **实时判据与采样锁存混用** —— `all_need_vld`（实时）决定"请求发不发"，
   而 `h_gotv` 取的是**上一拍锁存**的采样值。门房恰好在某个 posedge 补上号时，
   那一拍实时为真、锁存里还是"空"的旧值 ⇒ 取回 `000` ⇒ 卡在 D_DISP 不动，
   而且 `disp_stall` 全是 0（完全看不出是握手问题）。
   ⇒ 修法：加 `req_sent`（"这一拍真的发过请求"）与 `s_need_vld`（看锁存），
   **请求发出去一整拍之后才允许信锁存**。

## 4. 新不变量（写进单测台，也是 R08 的锚）

> **池子里还有 FREE 的下一拍，每一路都必须已经备着号。**

形式化（用**上一拍**的自由数，避开"补号要一拍"的固有延迟）：

```
若 (上一拍 free 数 >= 1) 且 (上一拍不是冲刷拍)  则  {alloc_vld2,alloc_vld1,alloc_vld0} == 3'b111
```

为什么这条能钉死实现：
* 组合输出式（改造前）在没有请求的拍上 vld 恒 0 —— 而"没有请求"是绝大多数拍，
  池子此时有几十个 FREE ⇒ 当场红。
* 光"给号打拍"也不行：那样空池时 vld 仍可能为 1（备了个不存在的号），
  由 `pop_lane` 里的 `|g_sel[k]` 门控兜住。

冲刷那一拍要排除：`flush_lvl` 把 tap 清掉、池子整表重建，下一拍本来就要重新备号。

## 5. 代价与影响

| 项 | 结论 |
|---|---|
| **自由池少 ≤3 个可用号** | tap 常驻占着（96 项里 32 项架构映射，可用 64 → 实际 61）。C910 一样（它每个 lane 一个 alloc 保持寄存器）。换来的是环路消失 + 号提前备好 |
| **阶段 1 整核** | **零影响**：`mycpu.v:1312` 把 `ren_preg_req` 恒接 0，`preg_short` 恒假（删了也不变行为）；tap 会白白备三个号，只让 `free_cnt` 从 64 变 61，而阶段 1 没有人读它 |
| **单元台** | 改三处（§3.3），参考模型不用动 —— 它本来就在"请求那一拍"取样，与 tap 的相位天然一致 |
| **Fmax** | 编码器从"IDU 请求 → 组合出号 → 回 IDU 的 RAT 写口"变成"IDU 请求 → 编码器 → **我们的 tap 寄存器**"，跨模块路径缩短；`disp_stall` 少一项 |
| **冲刷后的第一拍** | tap 是空的（vld=0），下一拍才备上号 ⇒ 每次冲刷多一拍"没号可给"。C910 同样（它的 alloc 寄存器也在 flush 时清零）。IDU 那侧本来就要等 `rtu_ren_flush` + 整表恢复，这一拍藏在恢复窗口里 |

## 6. 没验证到的部分（别当成"已经好了"）

* **环 1a/1b 的消失没法功能验证**：单元台与整核都测不出"没有组合环"。
  能测的只有"备号"这条**行为**不变量（R08 抓得住回退），
  以及将来真接上 C910 IDU 时不再出现振荡。
* **tap_hit 这条兜底没有激励**：造出"没请求却把我备的号派出去"的消费者才能测到，
  本次不造。
* **"请求即取走"是契约，不是机制**：消费者若请求了却不派遣、也不冲刷，
  那个号会**永久停在 WF_ALLOC**（年龄回收已删）。C910 的语义保证不会发生
  （请求、RAT 写、进 IS 由同一个 `!ctrl_ir_stall` 门控），我们的 IDU 照抄了这一点；
  但 RTU 这侧**没有任何东西能发现**消费者违约。
* **`free_cnt` 比真实可用数少 ≤3**：如果将来有人按它判断"还能跑多深"，
  要把 tap 那三个算回去。
