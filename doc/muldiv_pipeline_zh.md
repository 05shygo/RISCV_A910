# 乘除法单元重构方案（高频优先，对齐乱序 3 发射终态）

> 目标：把 `mySoC/MUL_DIV.v` 从「阻塞 EX 的组合乘法 + 假 3 级流水」重构成
> **真流水、不阻塞发射**的乘除法单元，先把 Fmax 拉上去，再顺着同一套接口
> 平滑接到将来的乱序 3 发射核上。
>
> 本文只给方案，不含 RTL 改动。所有"实测"数据都给出复现方法（附录 B）。

---

## 0. 结论摘要

**目标形态：乘法、除法拆成两条独立流水，共用一个带 tag 的请求/写回接口。**

| | 形态 | 发射间隔 (II) | 延迟 | 阻塞发射? |
|---|---|---|---|---|
| `mul_pipe` | 真流水，2~3 级（Booth + CSA 树 / 最终 CPA） | **1** | 2~3 拍 | 否 |
| `div_pipe` | radix-4 SRT 迭代，非流水 | 忙则不发 | 3~17 拍（数据相关） | 否（OoO 下天然；顺序核用 busy 反压） |

四条设计决策，按重要性排序：

1. **接口从第一天就带 tag**（`req_tag / resp_tag`）。顺序核里 tag 先退化成
   `{rd, 序号}` 或干脆不用；换成乱序时只是把 tag 接到 rename/ROB，
   **单元本身一行不用改**。这是整个方案里最省事、也最不能省的一条。
2. **乘法和除法分家**。乘法是吞吐部件（II=1），除法是延迟部件（II≈17）。
   合成一条流水的结果是：除法在跑的时候乘法被卡住，或者乘法流水里要插一堆旁路。
   C906 就是分开的（`aq_iu_mul` / `aq_iu_div` 是两个文件、两个写回口）。
3. **在"冗余形式"上切流水**。Booth 压缩树输出的是 (sum, carry) 两个向量，
   在它们之间插寄存器只需要 2×64 个 FF，而第二级只剩一个进位传播加法器。
   这是把乘法器切成 2~3 级的经典做法，也是 C906 `result_0/result_1` 的做法。
4. **不阻塞发射，用写回口 + tag 广播解决问题**。C906 的精髓不是 Booth 编码，
   而是「EX1 只占 1 拍，结果 2 拍后从自己的写回口出来，谁要用谁等唤醒」。

## 1. 现状与实测

### 1.1 现有 `MUL_DIV.v` 的问题

用 `tb_minirv_mul` 单独驱动（激励完全模仿 `mycpu.v:657` 的
`muldiv_stall = ex_is_muldiv & ~muldiv_ready` 协议）实测：

| 项 | 实测值 | 说明 |
|---|---|---|
| MUL 延迟（issue→`ready_o`） | 3 拍 | 与 `RV32M_IMPLEMENTATION.md` 的"延迟 3 周期"一致 |
| MUL 背靠背间隔 | **4 拍** | 该文档写的"吞吐量 1 条指令/周期"**与 RTL 不符** |
| DIV 延迟 | **34 拍** | 文档写 33，差在 `DIV_DONE` 那一拍 |
| 流水线代价 | 每条 MUL 占 EX **4 拍**、插 3 个气泡 | `muldiv_stall` 停的是整条流水 |

三个结构性问题：

**(a) 3 级流水是假的，白付。**
```verilog
// mySoC/MUL_DIV.v:75
mul_result_stage1 <= $signed(A) * $signed(B);   // 整个 32×32 乘法在这一拍里组合算完
```
stage2/stage3 只是移位寄存器。也就是说**关键路径上早就有一个单周期乘法器了**：
`ID_EX → 乘法器 → stage1 寄存器`。这三级既没有把乘法拆开（时序一点没改善），
又让每条 MUL 多花 3 拍。想要高频，要么把乘法真拆开，要么承认它就是一级。

**(b) 接收条件是「三级全空」**（`MUL_DIV.v:55` 的 `mul_pipe_empty`），
流水线被序列化，背靠背乘法无法重叠。

**(c) 接口没有 tag**：`valid_i / result / ready_o / busy_o` 只能表达
"算了给你"，表达不了"结果 2 拍后从写回口出来，带上 #37 号 tag"。
乱序核的最小需求就是后者。

### 1.2 这些停摆在真实负载里值多少（CoreMark 实测）

`make run TEST=coremark`（IFU=1，默认 BP 配置，difftest 通过）：

| 计数 | 拍数 | 占比 |
|---|---|---|
| 总拍数 | 13,826,243 | — |
| 退休指令 | 9,233,680 | IPC 0.668 |
| **`muldiv_stall`** | **850,150** | **6.15%** |
| （对照）load-use 停顿 | 667,920 | 4.83% |
| （对照）分支误预测 | 343,468 | MPKI 37.2 |

反推：`3×MUL + 33×DIV ≈ 850K`，而静态反汇编里 div/divu/rem 一共只有 20 处、
mul 只有 14 处（热循环里的），所以这 850K 拍**几乎全是乘法**贡献的，
对应约 **27~28 万条 MUL、占退休指令约 3%**。

两个参照系：

- 比 load-use 停顿还大（6.15% vs 4.83%），而 load-use 是大家公认要花力气消的；
- **比整个 BP 调优的收益（+3.77%）还大**，而改动量只是它的零头。

> 重构后能拿回多少：上限是这 6.15%（把停滞全消掉）。实际取决于消费者距离分布 ——
> 距离 0/1/2 的消费者在新方案里分别还要停 2/1/0 拍，而现在所有距离都是统一停 3 拍，
> 所以每条乘法大概能拿回 1~3 拍。**保守估计 CoreMark 能拿回 3~5%**，
> 独立乘法（矩阵乘那种）能全拿。精确值等实现完 A/B 一轮即可测出。

### 1.3 与 C906 的实测对比

| | openc906 `aq_iu_mul` | cdp-tests `MUL_DIV.v` |
|---|---|---|
| 结构 | radix-4 Booth（17 行部分积）+ 进位保留压缩树 + EX3 4-2 压缩器 | 行为级 `*` 一拍算完 + 2 级移位寄存器 |
| 延迟（issue→写回有效） | 单遍 2 拍；真 64×64 走分裂 FSM 5 拍 | 3 拍 |
| 占 EX | 1 拍（单遍） | 4 拍 |
| 独立乘法吞吐 | **1 条/拍**（实测连发 5 条，写回脉冲间隔 1 拍） | 1 条/4 拍 |
| 延迟是否随数据变 | 是（64 位操作数高半字平凡时走快路径） | 否 |
| 写回 | 专用口 + `rtu_iu_mul_wb_grant` 仲裁 + `preg[5:0]` tag | 无（阻塞式） |
| 面积（yosys generic cells，同口径展平） | 9,670（64 位数据通路，含分裂 FSM/累加器） | 7,187（仅乘法部分） |

> 面积那行只是为了说明"直接搬不划算"：C906 那个是 64 位单元，比你整个
> 乘除法单元的乘法部分还大。**RV32 只需要 32×32→64。**

## 2. 从 C906 抄什么、不抄什么

| C906 的设计点 | 采用 | 理由 / 出处 |
|---|---|---|
| radix-4 Booth 编码 + 进位保留压缩树 | ✅ | `booth_code_33_bit.v`（code[2:0]→0/±A/±2A）+ `multiplier_33x33_partial.v`（输出 `result_0/result_1` 冗余对） |
| **在冗余形式上切流水** | ✅ | 压缩树出 (sum, carry) 后插寄存器，第二级只剩 CPA。切分级数可调，面积代价只有 2×64 FF |
| mul / div 分成两条独立流水 | ✅ | `aq_iu_mul.v` / `aq_iu_div.v` 分开，各有自己的写回口 |
| 结果带 preg tag、广播唤醒 | ✅ | `iu_rtu_ex3_mul_wb_vld` + `iu_rtu_ex3_mul_preg[5:0]` |
| 专用写回口 + grant 仲裁 | ✅ | `rtu_iu_mul_wb_grant` / `iu_idu_mult_full` |
| 除法用 radix-4（每拍 2 位）而不是逐位恢复余数 | ✅ | `aq_iu_div_shift2_kernel.v`，用 r 与 d/2d/3d 的比较选商位 |
| 除法按前导位提前结束 | ✅ | `div_ff1_res` 优先编码器决定迭代次数（`aq_iu_div.v:431`） |
| 操作数预扩展，四种 MUL 共用同一阵列 | ✅ | 33 位扩展 + `sign/su/usign` 控制 |
| 64 位分裂 FSM（`IDLE→SPLIT0→SPLIT1→CMPLT` 四遍） | ❌ | RV32 用不上；将来上 RV64 再按同样思路加 |
| `src2` 累加口（madd/msub） | ❌ | 非 RISC-V 标准扩展，除非要做 MAC |
| ICG 门控时钟风格（`gated_clk_cell`） | ❌ | 跟你的综合/DFT 流程绑死，收益另算 |
| 全局 flush（`rtu_yy_xx_flush_fe`） | ❌ | 顺序核可以，乱序核要**按 tag 冲刷**，否则每次重定向都白清在飞的乘法 |
| 阻塞式握手（`iu_idu_mult_issue_stall`） | ❌ | 那是给顺序发射用的；乱序核不该反压发射队列 |

一句话：**抄"结构 + 写回/唤醒机制"，不抄"64 位专用逻辑 + 顺序核握手"。**

## 3. 目标接口（OoO-ready）

### 3.1 参数

```verilog
parameter DATA_W = 32;      // RV32（长期目标就是 RV32，不做 RV64 分裂路径）
parameter TAG_W  = 7;       // 物理寄存器号：PRF = 128 项 → 7 位
parameter MUL_LAT = 2;      // 乘法流水级数（2 或 3），编译期可调；选 2 的依据见 §9.2
```

> **已定参数**：PRF = 128（→ `TAG_W = 7`）、长期 RV32、频率对标 `RISCV_CPU/cpu` 参考核。
> 参考核的乘法单元实测 **869 MHz**、除法单元 **1.33 GHz**（nangate45，统一 I/O 口径，见 §9），
> 所以本方案的频率目标就定在 **~870 MHz**，`MUL_LAT = 2` 正好够（§9.2/§9.4）。

### 3.2 信号

| 方向 | 信号 | 位宽 | 说明 | C906 对应 |
|---|---|---|---|---|
| I | `req_valid` | 1 | 发射请求（乘法每拍可来一条） | `idu_iu_ex1_mult_sel` |
| I | `req_op` | 4 | MUL/MULH/MULHSU/MULHU/DIV/DIVU/REM/REMU | `idu_iu_ex1_func` |
| I | `req_src0/1` | 32×2 | 操作数 | `idu_iu_ex1_src0/1` |
| I | `req_tag` | TAG_W | **结果的身份证**（乱序：preg；顺序：序号） | `idu_iu_ex1_dst_preg[5:0]` |
| I | `req_src2` | 64 | **MAC 累加/加减操作数**（见 §4.6；接口第一天预留，P1/P2 接 0） | `idu_iu_ex1_src2[63:0]` |
| I | `req_acc_mode` | 2 | `00`=忽略 src2 / `01`=加 / `10`=减 | `mul_ex1_add` / `mul_ex1_sub` |
| O | `mul_ready` | 1 | 乘法口空（II=1 时恒 1） | `!iu_idu_mult_full` |
| O | `div_busy` | 1 | 除法忙，发射队列本拍不要选它 | `iu_idu_div_full` |
| O | `resp_valid` | 1 | 写回有效 | `iu_rtu_ex3_mul_wb_vld` |
| O | `resp_data` | 32 | 写回数据 | `iu_rtu_ex3_mul_data` |
| O | `resp_tag` | TAG_W | 回带 tag，供唤醒/写 PRF | `iu_rtu_ex3_mul_preg` |
| I | `wb_grant` | 1 | 写回总线仲裁（多个单元共用一个口时才需要） | `rtu_iu_mul_wb_grant` |
| I | `flush_valid` | 1 | 冲刷 | `rtu_yy_xx_flush_fe` |
| I | `flush_tag` | TAG_W | **只冲刷比它年轻的在飞项**（乱序必需） | 无（C906 全清） |

顺序核（P1）里 `flush_tag`/`wb_grant` 可以接常量，接口不变。

### 3.3 时序（示意图）

```
乘法背靠背（2 级流水，II=1）:
        T    T+1   T+2   T+3   T+4
req    M0   M1    M2    M3    M4     ← 每拍都能收一条
M1级   M0   M1    M2    M3    M4
M2级        M0    M1    M2    M3
resp          R0    R1    R2    R3   ← 写回脉冲间隔 1 拍

除法（radix-4，迭代 n 次）:
req    D0
busy   ────────────────────────┐
iter        |<-- n 次迭代 --->|
resp                          R0
```

## 4. 乘法器微架构

### 4.1 数据通路

```
 src0[31:0] ──────────────────────────┐
                                      ▼
                            ┌───────────────────┐
 src1[31:0] ───────────────►│ radix-4 Booth 编码 │  17 组 select/sign
                            └───────────────────┘
                                      │
                            ┌─────────▼─────────┐
                            │  部分积生成 (×17)  │  每行 34 bit
                            └─────────┬─────────┘
                                      │
                            ┌─────────▼─────────┐
                            │  4-2 压缩树        │  17→9→5→3→2 共 4 级
                            └─────────┬─────────┘
                                      │  (sum[63:0], carry[63:0])  ← 冗余形式
                                      │  ★ 流水寄存器就插在这里 ★
                            ┌─────────▼─────────┐
   src2[63:0] ──(MAC,§4.6)─►│ 3:2 CSA (预留)     │  ← 现在就把位置留出来
                            └─────────┬─────────┘
                            ┌─────────▼─────────┐
                            │ 最终 CPA (64bit)   │  Kogge-Stone / 2×CLA
                            └─────────┬─────────┘
                                      │
                            ┌─────────▼─────────┐
                            │ 结果选择 + 写回    │  MUL→[31:0], MULH*→[63:32]
                            └───────────────────┘
```

### 4.2 四种 MUL 共用一条通路

不要为 MULHSU/MULHU 单独做逻辑。采用 C906 的"操作数预扩展"：

- `src0` 按 `MULHU`(无符号) / 其他(有符号) 扩展到 **33 位**；
- `src1` 同理；
- 于是 **signed×signed、signed×unsigned、unsigned×unsigned 都变成同一个 33×33 有符号乘法**
  （无符号侧高位补 0、符号位补 0，正好就是无符号数）；
- 阵列算出 64 位积，按 op 选低 32（MUL/MULW）/ 高 32（MULH/MULHSU/MULHU）。

这样 Booth 阵列、压缩树、CPA 都只有一份，op 只影响扩展位的取值和最后的选择 mux。
C906 正是这么做的（`mul_ex1_nosplit_src0/1` + `mul_ex1_src0_sign64`，`aq_iu_mul.v:266-345`）。

### 4.3 流水切分方案

| 方案 | M1 | M2 | M3 | 寄存器代价 | 适用 |
|---|---|---|---|---|---|
| **A. 2 级**（推荐起点） | 操作数锁存 + Booth 编码 + 部分积 + 压缩树 | 3:2 CSA（MAC 预留，§4.6）+ 最终 CPA + 结果选择 | — | 2×64 FF（冗余对） | 目标频率 ≤ 乘法器单周期**减半** |
| **B. 3 级** | 操作数锁存 + Booth 编码 | 部分积生成 + 压缩树 | 3:2 CSA（MAC 预留）+ 最终 CPA + 结果选择 | ~17×3 bit（存 Booth 码）+ 2×64 FF | 目标频率更高时 |
| C. 4 级 | — | 再拆压缩树 | — | 中间行寄存器昂贵 | 一般不做 |

**注意 B 的寄存器选择**：千万不要在 M1/M2 之间存 17 行部分积（17×34 ≈ 578 FF），
存 **Booth 编码结果**（17 组 ×(select 2bit + sign 1bit) ≈ 51 FF）便宜一个数量级。
C906 把 `data_for_code` 的编码放在 EX1、部分积放在 EX2，就是这个思路。

**推荐**：先按 A 做。综合实测（§9）表明 2 级刚好落在 800~900 MHz 档，
与参考核的乘法单元齐平；只有当目标频率再往上一个档时才需要上 B。

### 4.4 为什么必须在冗余形式上切

压缩树的输出天然是 (sum, carry) 两个向量 —— 它们**没有进位传播**，可以安全地
跨寄存器传递，下一级用一个 CPA 收尾即可。如果先把它们加成一个 64 位数再寄存，
第二级就只剩布线了，等于把延迟全堆在 M1，白切。

代价：流水寄存器从 64 bit 变成 128 bit；收益：CPA 那一大坨（64 位 Kogge-Stone
约 6~7 级逻辑）从 M1 里摘出去了。这笔账在 32 位乘法器上通常是划算的。

### 4.5 面积估算（量级）

| 块 | 估算 |
|---|---|
| Booth 编码（17 组） | ~300 门 |
| 部分积生成 | ~1,100 门（17×32 个 AND/mux） |
| 4-2 压缩树（4 级） | ~1,200 门 |
| 64 位 CPA | ~800 门 |
| 3:2 CSA（MAC 预留，§4.6） | ~200 门 |
| 流水寄存器 + 控制 | ~400 门（含 128 FF）+ 64 FF（src2） |
| **合计** | **≈ 3.7~4.7K 门**（量级与现有 7.2K 的乘法部分同级或更小，因为不再有 64 位×3 级全宽寄存器） |

### 4.6 MAC（乘累加）口 —— 留口子，暂不实现

**已定：留。** 接口见 §3.2 的 `req_src2[63:0]` + `req_acc_mode[1:0]`。
这是 C906 的做法（`idu_iu_ex1_src2[63:0]` + `mul_ex1_add`/`mul_ex1_sub`，
`aq_iu_mul.v:28,57,130`）；**参考核没有这个口**（`MUL_EX.v` 只有 rs1/rs2）。

> 既然确定要留，**插入点现在就得定死**，否则以后再加等于把 M2 级重切一遍。

**插入点：M2 级的 CSA，不是 CPA 之后。**

```
 M2 级（切分方案 A）:
   (sum, carry) ──┐
                  ├──► 3:2 CSA ──► 最终 CPA(64) ──► 结果选择 / 写回
   src2[63:0] ────┘        ↑
                      acc_mode: 加 / 减 / 忽略
```

- **为什么用 CSA 而不是直接接个三输入加法**：`sum + carry + src2` 是三个数，
  先用一级 3:2 压缩器化成两个，CPA 宽度不变（仍 64 位）。代价只有一级 CSA
  （~200 门 + 约 60~80 ps）。直接做三输入加法器，延迟和面积都更差。
- **减**：`src2` 取反加一后进 CSA（C906 的 `mul_ex1_sub` 就是这么做的）。
- `acc_mode = 00` 时，CSA 退化成把 (sum, carry) 原样透传，**不引入额外延迟**
  （综合会把那一级优化掉）—— 所以"留口子"对不带 MAC 的负载是零成本。

**必须提醒：这会给 M2 增加一段延迟，而且是一种特殊形态。**

`src2` 在 M1 和操作数一起打拍，所以 MAC 的路径是
`src2_m1_reg → CSA → CPA → 结果寄存器`，仍然是一条普通的 reg→reg 路径；
但如果将来做**单元内部累加器**（`acc` 在 M2 里回环），M2 就变成
`acc_reg → CSA → CPA → acc_reg` 的**自环** —— 没有任何地方可以插流水、也不能靠
retiming 拆开，M2 的周期直接等于 CSA+CPA。**这是加 MAC 之后 M2 会变慢的唯一原因**，
也是 §4.3 里要在 M2 预留 CSA 位置的理由。

**两种累加器形态，将来必须选一种**：

| | **外部 64 位操作数**（C906 做法，建议） | 单元内部累加器 |
|---|---|---|
| 状态 | **无状态** | 有状态 |
| 乱序兼容 | 天然兼容 rename/ROB/按 tag 冲刷，**单元一行不用改** | 要额外做保存/恢复/冲刷撤销，且必须保证同 tag 序 |
| 代价 | 需要 64 位操作数来源（RV32 下得占两个 GPR，或一对专用 acc 寄存器） | 单元里一个 64 位 acc 寄存器 + 读出口 |

**建议走 C906 那条"外部 64 位操作数"**：OoO 下无状态的一律优先。
§6.3 已经要求按 tag 冲刷，再叠一层内部状态只会让冲刷语义更难写对。
P1/P2 阶段 `req_src2` 直接接 0、`req_acc_mode` 接 `00`，接口不改。

## 5. 除法器微架构

### 5.1 算法选型

| 算法 | 迭代数（32 位） | 每级逻辑 | 评价 |
|---|---|---|---|
| 逐位恢复余数（现状） | 32 | 很短 | 太慢 |
| **radix-4 SRT（推荐）** | **~16**（可早退到 3） | 中（QDS + 4:1 mux + CSA） | C906 的做法，性价比最高 |
| radix-8 SRT | ~11 | 长（QDS 表大、3d 倍数难算） | 高频下每级吃不消 |
| 全展开组合除法器 | 1 | 极长 | 面积/频率都不可接受 |

选 **radix-4 SRT**，和 C906 同路线（`aq_iu_div_shift2_kernel`，每拍 2 位）。

### 5.2 状态机与迭代

```
IDLE ──req──► PREP ──► ITER×n ──► FIXUP ──► RESP ──► IDLE
                │         │           │         │
            取绝对值   余数进位保留  商/余符号   带 tag 写回
            前导位扫描   每拍 2 位    除零/溢出
            算迭代次数   QDS 选商位    特殊值
```

关键点：

- **前导位提前结束**（抄 C906 的 `div_ff1_res`）：迭代次数由被除数/除数的
  前导零/一决定，`n = ceil(有效位宽/2)`。小操作数（常见！）只跑 3~4 拍。
  这需要一个 32 位优先编码器（~150 门），换来的是平均延迟大幅下降。
- **商用冗余形式累加**（on-the-fly 转换），避免最后再补一个全宽减法。
- **一次只跑一条**。除法不做流水（见 5.5）。

周期预算：PREP 1 + ITER n + FIXUP 1 + RESP 1 ≈ **3 + n 拍**，满量程 n=16 → 19 拍；
小操作数（如 100/7）→ 7 拍左右。对比现状恒 34 拍。

### 5.3 QDS（商位选择）

C906 用的是**比较法**而不是查表 ROM：算出 `r` 与 `d`、`2d`、`3d` 的比较结果
（`div_remainder_lt_divisor_01/10/11`），据此选 `{-2,-1,0,+1,+2}` 商位。
好处是没有 ROM、没有大扇出查表，逻辑浅，容易过时序。建议照抄这个思路。

### 5.4 特殊值与符号

RISC-V 规定的边界必须在 FIXUP 级一次做干净：

| 情况 | DIV/DIVU | REM/REMU |
|---|---|---|
| 除数为 0 | −1 | 被除数本身 |
| `INT_MIN / -1` | `INT_MIN`（溢出不回绕） | 0 |
| 符号 | 商 = 两符号异或 | 余数符号 = 被除数符号 |

**验证重点**：这四个格子加上 `0xFFFFFFFF` / `0x80000000` 的交叉组合，
是最容易出错的地方，务必有定向用例（见 §8）。

### 5.5 为什么除法不做流水

做流水的代价是每一级都要带一套 64 位余数 + 商寄存器和完整的 QDS，面积翻几倍；
收益是把 17 拍变成 II=2~3 —— 但除法在真实负载里占比 <1%，**这条流水线 99% 的时间是空的**。
所以正解是：**慢就慢，但绝不阻塞别人**。C906 也是这么处理的：
除法走自己的 `iu_idu_div_full` 反压，乘法流水完全不受影响。

在乱序核里这就是"发射队列没选它"；在 P1 的顺序核里用 `div_busy` 停 ID（不是停整条流水，
至少取指/访存可以继续）。

### 5.6 面积估算

| 块 | 估算 |
|---|---|
| 64 位余数寄存器 + 进位保留减法 | ~900 门 |
| QDS 比较器（d/2d/3d） | ~700 门 |
| 前导位优先编码器 | ~150 门 |
| 商 on-the-fly 转换 | ~500 门 |
| 符号/特殊值修正 | ~200 门 |
| **合计** | **≈ 2.5~3K 门** |

## 6. 写回、唤醒、冲刷

### 6.1 写回口

- 乘法 II=1，**必须有专用写回口**，否则背靠背乘法每两条就要抢一次总线。
- 除法复用同一个口（分时），或单独一个低速口。仲裁优先级：**mul > div**
  （div 慢，多等一两拍无所谓；mul 被抢就会掉吞吐）。
- 顺序核（P1）如果采用 §7 里"延迟正好等于 EX→WB"的做法，**可以完全不新增写回口** ——
  乘法的结果正好在它自己的 WB 拍就绪，直接并进 `mem_wD → MEM_WB` 通路即可。

### 6.2 唤醒

写回当拍广播 `resp_valid + resp_tag`，所有在发射队列里等这个 tag 的项在**同拍**被唤醒
（和 C906 的 `iu_rtu_ex3_mul_wb_vld` 广播同一个套路）。乱序核里这条广播线是
关键时序路径，tag 比较要做成"每项一个比较器"的分布式形式，别串成一条长链。

### 6.3 冲刷（OoO 与顺序核的区别）

- **顺序核**：重定向即全清（乘法流水只有 2~3 级，清掉就行）。
- **乱序核**：必须**按 tag 冲刷** —— `flush_tag` 之后的项作废，之前的要保留并正常写回。
  实现上每个流水级存一个 tag，做 `younger_than(stage_tag, flush_tag)` 比较，
  命中就 kill 掉该级的 `valid`。

**容易漏的一条**：kill 掉的那一级**不能**再产生 `resp_valid`，否则会往 PRF 里写
一条本不该退休的指令的结果 —— difftest 会直接抓到，但要注意是"偶发、依赖时序"的，
所以 §8 要有专门的定向用例。

### 6.4 重定向路径：C910 / C906 是怎么解决的

§9.5 指出本核的关键路径是「EX 改向寄存器 → IFU」（1767 ps / 566 MHz）。查了同门的
两份真实 RTL，**结论很干脆：这条路上必须有一级寄存器，本核没有。**

**问题的本质**（`mycpu.v:713-727`）：

```verilog
wire [31:0] actual_npc = ex_is_jalr ? ex_alu_c
                       : (ex_br_taken | ex_is_jump) ? (pc_EX + ex_sext)
                       : (pc_EX + 32'd4);
wire mispredict = have_inst_EX & ~ex_inst_misaligned & (actual_npc != ex_pred_npc);
assign iu_ifu_chgflw_vld = mispredict & ~redirect;   // ← 纯组合
assign iu_ifu_chgflw_pc  = actual_npc;               // ← 纯组合
```

`actual_npc` **纯粹是组合逻辑**（目标加法 + 比较），却要在**同一拍**里：
目标加法 → 比较 → IFU 改向控制 → 取指元数据 / icache 地址与 way 选择。
一拍塞四件事，再加一个扇出 3791 的寄存器 —— 这就是那 1767 ps。

**C910**（`ct_iu_bju.v:1008-1015`）：改向信号**全是触发器直出**。

```verilog
assign iu_ifu_chgflw_vld      = ex2_pipe2_chgflw_vld;      // reg
assign iu_ifu_chgflw_pc[62:0] = {ex2_pipe2_tar_pc_msb[23:0],
                                 ex2_pipe2_tar_pc[38:0]};  // reg
assign iu_ifu_cur_pc[38:0]    = ex2_pipe2_cur_pc[38:0];    // reg
assign iu_ifu_bht_pred        = ex2_pipe2_bht_pred;        // reg
assign iu_ifu_chk_idx[24:0]   = ex2_pipe2_chk_idx[24:0];   // reg
```

分界线在 **EX1→EX2**：BJU 在 EX1 里做完比较 + 目标加法，
在 EX1→EX2 边界打拍成 `ex2_pipe2_*`（`ct_iu_bju.v:895,931-932`），
**IFU 拿到的是一个已经算好的 PC**，有一整拍去做 pcgen 选择 + 取指。

**C906** 更彻底 —— BJU **根本不直连** IFU 的改向口：
`aq_iu_bju.v` 的输出只有 `iu_rtu_ex1_bju_cmplt` / `iu_rtu_ex1_bju_wb_vld`（报给 RTU），
改向由 **RTU** 发出（`aq_rtu_top.v:397-398  rtu_ifu_chgflw_pc/vld`
→ `aq_ifu_pcgen.v:82-83`）。**改向点从 EX 挪到了退休级。**

| | 改向从哪发 | 到 IFU 前有寄存器吗 | 误预测惩罚 |
|---|---|---|---|
| **cdp-tests 现状** | EX | **没有**（纯组合） | 最小 |
| **C910** | EX1 算、EX2 发 | **有**（`ex2_pipe2_*`） | +1 拍 |
| **C906** | RTU（退休级） | 有（RTU 输出） | +好几拍 |

**代价与收益**：两家都拿"多一拍（C906 是多几拍）惩罚"换"一整拍时序余量"。
这笔账在本核是明显划算的：误预测 343,468 次 / 13,826,243 拍 = **+2.5%**，
而频率能从 566 MHz 往 1 GHz 走。

**两个配套动作，值得一起抄**：

1. **C910 的 PC FIFO**（`ct_iu_bju_pcfifo.v`）：IFU 取指时把每个取指包的
   `cur_pc / tar_pc / bht_pred / chk_idx / dst_vld / jal / jalr` 推进一个 FIFO
   （`ifu_iu_pcfifo_create0/1_*`），BJU 在 EX2/EX3 从 FIFO 取出来做**预测校验**
   （`bju_pcfifo_ex2_*/ex3_*`），结果再送到 RTU（`iu_rtu_pcfifo_pop0/1/2_data`）。
   **好处**：IFU 的预测信息不需要组合地回灌到分支比较逻辑里，两条路解耦；
   这条 FIFO 还兼做"取指包 → 提交"的追踪链。
2. **C906 的独立目标口**：`iu_ifu_tar_pc[63:0]`（`aq_iu_top.v:219`）——
   预测命中的跳转走这条，**误预测走 RTU 那条**。两条路分开，各自都短。

**给本核的最小改动建议**：在 `iu_ifu_chgflw_*` **之前加一级寄存器**
（和 C910 一样，在 EX 的边界打拍）。代价是误预测惩罚 +1 拍（+2.5%），
收益是切断那个 3791 扇出的锥、IFU 侧拿回一整拍。
**这件事应该在 P2 划微架构时一起做**，不要等 RTL 写完再补 —— 补的时候要动 IFU 的接口。
具体改法与三个必须一起处理的坑见 §6.5，实测收益见 §9.8。

### 6.5 给改向路径加一级寄存器：具体怎么做

**最小改法**（`mycpu.v` 的 `mispredict` 那一段）：

```verilog
reg        chgflw_vld_q;
reg [31:0] chgflw_pc_q;
always @(posedge cpu_clk or posedge cpu_rst) begin
    if (cpu_rst) chgflw_vld_q <= 1'b0;
    else         chgflw_vld_q <= mispredict & ~redirect;
    chgflw_pc_q <= actual_npc;
end
assign branched          = chgflw_vld_q;   // ★ 冲刷也要跟着延后一拍
assign iu_ifu_chgflw_vld = chgflw_vld_q;
assign iu_ifu_chgflw_pc  = chgflw_pc_q;
```

**★ `branched` 必须跟着延后 —— 这是最容易漏的一条。**

现在 `branched = mispredict` 是**同拍**冲 IF/ID。如果只把 `iu_ifu_chgflw_*` 打拍、
`branched` 不动：

| 拍 | EX | ID | `branched` | 结果 |
|---|---|---|---|---|
| T | 分支 A 误预测 | 错误路径指令 X | 1 | X 被冲掉 |
| T+1 | 气泡 | **X′（T 拍还在 IF 的那条）** | 0 | **X′ 漏进来了** |

T 拍在 IF 的那条错误路径指令，T+1 升到 ID，而此时 `branched` 已经回 0 —— 它会活下来。
**所以 `branched` 和 `iu_ifu_chgflw_*` 必须是同一个信号的两路扇出**（都从 `chgflw_vld_q` 来），
冲刷窗口和改向窗口才对齐。

**另外三个必须一起处理的点**：

1. **背靠背误预测会把待发的改向吃掉。**
   打拍之后，T 拍的 A 分支要等 T+1 才发出改向；而 T+1 的 EX 里是错误路径上的指令 X
   （因为 T 拍没有冲 ID），**X 自己也可能误预测**。两个 `mispredict` 撞在同一个寄存器上，
   A 的改向被 X 覆盖。
   **修法**：T+1 拍把 EX 也压掉 —— 给 `have_inst_EX` / `mispredict` 加上 `~chgflw_vld_q`。
   注意**不能**在 T 拍就压 EX：那时 EX 里的正是那条分支，压了就丢掉它的 rd 写回
   （JAL/JALR 要写 rd）。
   > 别用"`chgflw_vld_q` 保持两拍"这种偷懒修法：`iu_ifu_chgflw_vld` 在 IFU 里
   > 还兼着 **BHT 的 VGHR 修复**（`rv32_ifu_bht.v:542  ghr_updt_vld = cp0_ifu_bht_en && iu_ifu_chgflw_vld`）
   > 和 lbuf 清脉冲（`rv32_ifu_lbuf.v:1506`），拉两拍会把这些副作用做两遍。

2. **和陷阱的优先级要重新处理。**
   现在 `mispredict & ~redirect` 是同拍掐掉。打拍之后，T+1 拍可能**同时**有
   "T 拍那次的待发改向"和"T+1 拍的陷阱（`redirect`）"。陷阱来自 WB，而 T 拍的分支
   在 T+1 时在 MEM —— **陷阱指令更老，应该赢，并且待发的改向必须作废**：

   ```verilog
   else chgflw_vld_q <= (mispredict & ~redirect) | (chgflw_vld_q & ~redirect);
   ```

   IFU 侧本来就有优先级（`rv32_ifu_top.v:583  backend_pc = rtu_ifu_chgflw_vld ? rtu : iu`），
   但那是"两个都发、选一个"，靠不住 —— **待发的那次要在核侧就清掉**。

3. **`iu_btb_target = actual_npc` 是另一条 EX→IFU 的组合路径**（`USE_IFU2` 的 BTB 训练），
   它和改向路径共用 `actual_npc` 这个锥。打了拍之后它很可能顶上来成为新的关键路径。
   训练晚一拍**没有正确性问题**（`iu_btb_cur_pc` / `iu_btb_chk` 是随指令登记的），
   所以可以一起打拍；但**改完必须重新跑一遍综合看谁顶上来**。

**代价**：误预测惩罚 +1 拍。CoreMark 实测 343,468 次误预测 / 13,826,243 拍 = **+2.48%**。

**收益**：见 §9.8。

## 7. 落地路线

### P1：当前 5 级顺序核（先拿收益，不碰乱序）

**核心技巧：把乘法延迟做成正好等于 `EX → WB` 的拍数（本核是 2 拍），
就既不用第二写回口、也不用完整的计分板。**

理由：结果在乘法指令自己的 WB 拍就绪 → 直接并进 `mem_wD`（`MEM_WB` 入口加个
`mem_is_mul` mux）→ 提交点、`instret`、精确异常全部不动。乘法指令**照常沿流水退休**，
不会出现"已经退休但寄存器还没写"的窗口，中断/陷阱语义原样成立。

消费者这边要注意两点：

1. **在飞的是多条，不是一个**。乘法 II=1，流水 2 级，所以同时在飞的乘法最多
   `MUL_LAT` 条（2 条）。互锁要做成 **N 项（N=MUL_LAT）的 `{valid, rd}` 小队列表**，
   每一项都跟消费者的 rs1/rs2 比，命中就停 ID —— 不是照抄一个 `load_use_exist` 就够
   （`Hazard_Detection.v:78` 只比一条）。
2. **停 2 拍，不是 1 拍**。消费者在乘法发射后的第 1、2 拍进来都得停（乘法的结果
   第 2 拍才到 WB）；到第 3 拍时乘法的结果已经躺在 WB 级数据上，
   **现成的 `RAW_C` 前递通路（`Hazard_Detection.v:57`）直接就能拿到**，
   不需要新增前递源。

   > 对照：现状是消费者要等 4 拍（乘法占满 EX）。所以依赖距离近的也快了，
   > 独立指令更是从 1 条/4 拍变成 1 条/拍。

**WAW 不用管**：乘法不阻塞流水，所以年轻指令的 WB 一定晚于它要覆盖的那条乘法的 WB
（乘法的写发生在自己 WB 那一拍，年轻指令排在后面），写序天然正确。这是顺序核的红利；
到 P2 乱序时由 rename/ROB 接管。

改动清单：

| 文件 | 改动 | 量级 |
|---|---|---|
| `mySoC/MUL_DIV.v` | 乘法拆成 2 级真流水；接口加 `req_tag/resp_tag`（P1 先接 rd 序号） | 重写，~300 行 |
| `mySoC/mycpu.v` | MUL 不再进 `muldiv_stall`；新增 `ex_is_mul` 沿流水下传；`mem_wD` 加 mux | ~20 行 |
| `mySoC/Hazard_Detection.v` | 新增 N 项 `mul_pending` 小队列表 + `mul_use_exist`，命中就停 ID | ~20 行 |
| `mySoC/EX_MEM.v` / `MEM_WB.v` | 各加一个 `is_mul` 标志位 | ~4 行 |

预期：独立乘法从 1 条/4 拍 → **1 条/拍**；依赖距离 0/1/2 的消费者从统一停 3 拍
变成停 2/1/0 拍。CoreMark 上界的实测基线见 §1.2（`muldiv_stall` = 850,150 拍 / 6.15%），
保守估计能拿回 3~5%。
**除法不变**（还是 34 拍），但可以顺手把 radix-4 一起换掉（§5）。

验证 A/B 的方法：跑一次 CoreMark 读 TB 里现成的 `b2_raw_muldiv`（IFU1 报表里叫
`b_raw_muldiv`，见 `tb/tb_miniRV_dpi.sv:2781`），改前改后各一次即可。

风险：如果 2 级乘法都塞不进一个周期，就得上 3 级 → 延迟 3 拍 > EX→WB 的 2 拍 →
这时才需要第二写回口/计分板（或者干脆让乘法在 MEM 多停 1 拍）。

### P2：乱序 3 发射

- 单元**不用改**，只把 `req_tag` 从 `{rd,seq}` 换成 rename 阶段的 `preg`；
- 发射队列：乘法口每拍可选中 1 条（3 选 1 的仲裁），除法口 `!div_busy` 时可选；
- 写回接 PRF 的写口 + 唤醒广播；
- 冲刷换成 `flush_tag` 比较。

**P1 阶段就要把 tag 通路的位宽参数化**，否则 P2 要重写一遍接口。

### P3：扩展（按需）

- 3 发射若想每拍 2 条乘法 → 例化第二个 `mul_pipe`（接口天然支持），
  或把阵列做成 2 路交错；
- 上 RV64 → 按 §2 的思路加分裂 FSM（C906 的 4 遍 scheme 可以直接借用）；
- 需要 MAC → 加 `src2` 累加口（C906 的 `mul_ex1_add/sub` 就是这么用的）。

## 8. 验证方案

### 8.1 定向用例（必做）

| 类别 | 用例 |
|---|---|
| 乘法边界 | `0×x`、`1×x`、`-1×x`、`0x80000000×-1`、`0xFFFFFFFF×0xFFFFFFFF` |
| MULHSU 符号 | `(0x80000000, 0xFFFFFFFF)`、`(0x7FFFFFFF, 0x80000000)` —— 最容易错的组合 |
| 除法特殊值 | 除零（DIV/DIVU/REM/REMU 四种行为不同）、`INT_MIN/-1`、`x/1`、`0/x` |
| 余数符号 | 负数被除数 × 正负除数四种组合 |
| 依赖距离 | 乘法后第 1/2/3 条指令就用 rd（覆盖前递与停顿的所有窗口） |
| 写同一 rd | `mul x5,…; addi x5,x0,1`（顺序核里天然安全，但要测） |
| MAC（启用后） | `acc_mode=00` 时结果与不带 MAC 逐位相同（确认那级 CSA 被优化掉、零成本）；加/减各一组；`src2` 全 0/全 1；连续 MACC 的累加次序与冲刷撤销 |
| 在飞冲刷 | 乘法发射后 1 拍/2 拍发生分支误预测；除法迭代中途发生陷阱 |
| 中断 | 乘法在飞时来 MTIP（P1 的提交语义要保证结果已写入） |

### 8.2 随机差分

用现成的 golden model（提交步进，不受周期数影响）跑随机 M 扩展序列，
每条指令前随机插入依赖距离。**注意**：现有 golden model 的 MUL/DIV 是
在提交当拍算的，只要"架构结果 + 退休顺序"不变，它的时序改动不需要动 —— 这是
这个 difftest 设计的好处，别去改它。

### 8.3 结构性断言（建议加进 TB）

- `resp_valid` 的条数 == 发射的条数 − 被冲刷的条数（防丢/防重）；
- 同一 `tag` 在一条指令的生命周期里最多写回一次；
- 被 `flush` 掉的乘法**绝不出现** `resp_valid`；
- `div_busy` 期间发射队列确实没向 div 口发请求。

> ⚠ **新发现的一个重要口径问题：单元级孤立综合是偏乐观的。**
> 参考核的乘法路径：孤立测量 **1151 ps**，放进整核同一版综合里是 **1340 ps（+16%）**。
> 原因是孤立综合时端口驱动理想、工具全力优化这一条路径；整核里要和 15 万门抢优化预算、
> 线负载也不一样。**所以"单元 869 MHz"这个目标值应该按 750~870 MHz 区间来理解**，
> 落地时留余量。这也再次说明 §9.4 的结论方向对、绝对值要打折。

> **⚠ 复核说明（2026-09-27）**：上一版这张表里除 `MUL_DIV` 外的所有数字都**没加 I/O 延时**。
> 补上加延时重跑后，**单元级的数字基本不变**（乘法器 1415、参考核 MUL 1151、C906 1097，
> 都在 ±0.5% 内）—— 因为这些单元的操作数端口后面本来就有一级流水寄存器，
> 乘法发生在 reg→reg 之间。**唯一被坑到的是 cdp-tests 的 `MUL_DIV`**（它的乘法是端口→寄存器）。
> 参考核 `SRT_div` 反而从 952 ps 降到 **750 ps**：原来那条 952 ps 是"输出端口没约束"造成的假象。
>
> 换句话说：**单元级的对标数字是站得住的；出问题的是整核那一行**，见坑二。

### 9.3 两个必须说清楚的坑

**坑一：不加输入延时，`端口 → 寄存器` 的乘法路径既不上报也不优化。**
`MUL_DIV` 的操作数 `A/B` 是模块输入端口。不给 `set_input_delay` 时 Genus 认为
端口 0 时刻到达，那条 32×32 乘法路径**不会出现在关键路径报告里**，工具也不会去优化它。
第一版测得"现状 MUL_DIV 只要 869 ps、能过 1 GHz"就是这么来的 —— 是假象。
加上 `set_input_delay 0.25` 再跑，关键路径立刻变成
`B[9] → mul_result_stage1_reg[61]`，**逻辑 1379 ps**，面积从 3,291 涨到 15,066 cells。

**坑二：整核关键路径落在"我为仿真补的行为级 memory stub"里 —— 这次是真失真。**

cpu 参考核的 `Dcache` / `Icache` / `BRAM_IROM` / `Mem_BRAM_256K` 在仓库里**没有实现**
（Vivado 的 `.xci`，源码快照里没有），是我为了跑通综合补的行为级模型
（`ip_stubs_trim.v`：**异步读**，`assign spo = ram[a]`）。综合出来就是
`u_LSU_u_dcache_u_Dcache_512B_u_ram_reg[0:31][0:137]` 这样一片触发器阵列 ——
而**最差路径的终点就落在这片的 D 端**：

```
u_ROB/rob_rd_ptr_reg[1] → ROB 提交逻辑 → dcache 写数据/地址 → u_ram_reg[30][65]/D   1894 ps
```

起点（ROB 提交指针）和中间的逻辑**都是真的**，但**终点是假的 macro**。
把 cache 阵列黑盒化（等价于"这里是一块 SRAM macro，内部不算逻辑"）重跑：

| 口径 | 关键路径 | Fmax |
|---|---|---|
| 原始（阵列 = 触发器 + 异步读 mux） | 1894 ps（dcache 写口） | 528 MHz |
| **cache 阵列黑盒化** | **1668 ps**（IFU 的 PC 自环） | **~600 MHz** |

新关键路径 `u_IFU/pc_reg[5] → pc_reg[30]` 是 IFU 的 PC 更新自环，
**没有任何阵列参与，是真路径**。

> **更正记录**：上一版我写的是"这条 cache 阵列路径是真的，不是失真"——**说错了**。
> 当时只看了 `cpu/src/dcache.v:131` 的 RTL 就下结论，没有回头确认 `Dcache` 这个模块
> 到底是谁定义的。它是我的 stub。这次的结论有"黑盒化重跑"作证据。

**边界**：黑盒化假设"时序行为跟原 RTL 一样、只是内部不算逻辑"。严格说真实情况介于两者
之间（真 BRAM 是**同步读**，而 RTL 的用法是**异步读**，两者必有一处要改），所以完整表述是
**cpu 参考核 ≈ 1668~1894 ps ≈ 528~600 MHz**。cdp-tests 的整核数字（1733 ps）同理：
它自己 RTL 里就是 `reg [..] array`，真做 ASIC 也会换成 macro。**整核数字只当参照，
不要用它来定乘除法单元的频率目标。**

### 9.4 结论（直接写进 §4.3 和 §5.1 的选型）

1. **单周期 32×32 乘法 ≈ 1400 ps，卡在 ~700 MHz** —— 两个独立测量互相印证
   （裸乘法器 1415 ps；现状 MUL_DIV 的乘法逻辑 1379 ps）。
   **要 800 MHz 以上，乘法必须拆 2 级。**
2. **现状的设计代价很贵**：为了把乘法塞进一个周期，综合工具不得不把 `MUL_DIV`
   撑到 **15,066 cells**（约束放松时只要 3,291），换来的还是"1 条/4 拍"的吞吐。
   同一套约束下，C906 那套 2 级方案只要 **8,267 cells 就能跑到 873 MHz** ——
   **又小又快，还顺带把吞吐从 1/4 拍到 1/1**。
3. **拆 2 级 = 870~910 MHz**：C906 的 1097 ps 和参考核的 1151 ps（一个 2 级、
   一个 3 级）是两个独立证据。所以 **`MUL_LAT = 2` 是对的**。
   —— 目标频率就此定在 **~870 MHz**（对齐参考核乘法单元 869 MHz）。
4. **除法用 radix-4 SRT 单次迭代只要 750 ps（1.33 GHz）** —— 除法**远不是**频率瓶颈，
   它只是慢在迭代次数上（32 → 16 次，延迟 34 → ~19 拍）。
   加上 §5 的"留 MAC 用的一级 CSA"（~60~80 ps），仍有充足余量。
5. **整核面积参照**：参考核 155,835 cells / 331,778 µm²（乱序），
   cdp-tests 现状 15,546 cells / 33,631 µm² —— **差 10 倍**。做乱序 3 发射时，
   ROB/rename/PRF/发射队列的面积会是大头（参考核光 ROB 就 16,749 cells）。
   ⚠ **这个比值不能直接用**：参考核的 PRF 是 `reg [31:0] regs[0:63]`（`regs.v:113`）
   带 **7 个写口 + 13 个读口**综合成触发器，而真 PRF 是定制的多端口寄存器堆。
   看量级可以，别当结论。

### 9.5 顺带测出来的：两个核的真实关键路径（对 P2 的预警）

做综合时顺手把两个核的关键路径挖了一遍（`report_timing -max_paths 20000` + 离线按
起点/终点过滤掉阵列路径）。**下面的 cpu 数据用的是"cache 阵列黑盒化"那一版**
（§9.3 坑二），不是被 stub 污染的那一版。

**cpu 参考核**：干净口径下 19996 条路径里 **16161 条与阵列相关、3835 条干净**。
干净路径的最差一档：

| 起点 | 终点 | 延迟 | RTL 对应 |
|---|---|---|---|
| `IFU/pc_reg[5]` | `IFU/pc_reg[18]` | **1671 ps** | **IFU 的 PC 更新自环**（pc+4 / 分支目标 / 重定向 mux 回自己）—— 真路径，无阵列 |
| `ROB/rob_rd_ptr_reg[1]` | `csr_reg_mepc_reg[3]` | 1664 ps | 提交指针 → 异常/CSR 写 |
| `ROB/rob_rd_ptr_reg[1]` | `IDU/rename_free_cnt_reg[6]` | 1662 ps | 提交指针 → free list 计数 |
| `ROB/rob_rd_ptr_reg[1]` | `ROB/rob_wr_ptr_reg[5]` | 1661 ps | `rob_rd_ptr` → 64 项 `rob_valid` **优先扫描** → `restore_wr_ptr`（`ROB.v:447-456, 524`） |

**按起点统计才看得出真正的问题**：

| 起点 | 条数 | 占比 |
|---|---|---|
| **`ROB/rob_rd_ptr_reg[{0,1,3}]`（提交指针）** | **3080** | **80%** |
| `Branch/br_rf_ex_br_rs1_data_o_reg[12]` | 241 | 6% |
| `MUL/MUL_EX/Mul_Core/op2_{l,h}_s1_reg[3]`（单元的乘法路径） | 79 | 2% |
| `DIV/div_rf_ex_subtype_o_reg[2]` | 34 | 1% |

> 也就是说：**参考核的"真问题"不是某一条路径，而是提交指针的扇出锥** —— 它组合地扇到
> ROB 内部、CSR、rename/free list、IFU、LSU、Issue，一条锥占了干净路径的 80%。
> 单条最长的是 IFU 的 PC 自环（1671 ps），第二名开始就全是这条锥了。
>
> （对比：被 stub 污染的那一版里，这条锥的头名是 1870 ps。黑盒化之后它降到 1661 ps，
> 说明之前那个数里还掺着工具为绕开假阵列而做的妥协。）

**cdp-tests**：**300 条最差路径全部从同一个寄存器出发** ——
`U_ID_EX_ex_pred_npc_reg[1]`（EX 级的"IFU 预测的 next PC"，扇出 **3791**）：

| 终点 | 条数 | 延迟 | 真假 |
|---|---|---|---|
| IFU `ifdp_meta_q_reg[...]`（取指元数据：issue PC/region） | 27 | **1767 ps** | **真** —— 纯逻辑，无阵列 |
| icache tag SRAM `mem_q[*][*]/D`（写数据/写使能） | 249 | 1733~1752 ps | **半真** —— 逻辑真，阵列内部假 |
| icache tag SRAM `q_q_reg[*]/D`（输出寄存器） | 24 | ~1733 ps | 同上（读口） |

```
mycpu.v:719  wire mispredict = have_inst_EX & ~ex_inst_misaligned & (actual_npc != ex_pred_npc);
mycpu.v:726  assign iu_ifu_chgflw_vld = mispredict & ~redirect;   // → IFU 改向
mycpu.v:727  assign iu_ifu_chgflw_pc  = actual_npc;
```

**假的那部分**：`rv32_ifu_spram.v:31` 是 C910 风格同步 SRAM 的**行为级模型**
（`reg [63:0] mem_q[0:1023]`），综合成 512×59 / 1024×64 的触发器阵列。
真 macro 里写译码和读 mux 都在 macro 内部（算在 setup / clk-to-Q 上），不在组合路径上。
路径尾部那段 `g733775 (AND2_X4, fanout 25, 64 ps) → MUX2 → mem_q[6][22]/D`
就是这段假东西；而**扇出 3791 里也有很大一部分是在驱动 512 项译码**，同样被夸大。

> ⚠ **cdp-tests 的真关键路径 = EX → IFU 取指（改向路径）**。
> 原始口径下 1767 ps（起点 `ex_pred_npc_reg[1]`）；把 SRAM 按 macro 边界黑盒化后
> **1606 ps ≈ 623 MHz** —— 起点变成 `pc_o_reg[31]`，因为阵列一去，剩下的就是
> "目标加法 + 比较 + IFU" 这条纯逻辑链。详见 §9.8。

**注意这和 BP 准确率是两回事**：它决定的是"改向要多快"，不是"预测得多准"。
MPKI 调得再低，只要改向本身要吃一整个周期，每次误预测的代价就下不来。

**给 P2（乱序 3 发射）的四条**：

1. **提交指针的扇出锥必须切**（**最重要的一条**）。参考核把 `rob_rd_ptr` 组合地扇到
   ROB 内部、CSR、rename/free list、IFU、LSU、Issue，占了干净路径的 **80%（3080/3835）**。
   做法：提交指针进每个域前**先打一拍**，各域用自己的寄存副本。
2. **恢复逻辑别用优先扫描**。`restore_wr_ptr` 那段 64 次循环（`ROB.v:447-456`）在锥里
   自成一档（黑盒化后 1661 ps）。用空闲项链表/free list，或至少按 4 项一组分两级扫。
3. **PC 自环要专门设计**。参考核干净口径下的**头名就是它**：`IFU/pc_reg → pc_reg`，
   1671 ps。分支目标 / pc+4 / 重定向三路要**并行提前算好**，最后只留一个窄 mux。
4. **重定向/改向路径要在微架构阶段就规划**。两个核都被它卡着（cdp-tests 1767 ps）。
   而且 cdp-tests 现状这条是**可以打拍的**（改向晚一拍只影响误预测惩罚，不影响正确性）
   —— 但要跟"少一拍惩罚"一起算总账。

### 9.6 复现方法

综合脚本在 `/tmp/synth/`（`cpu/`、`cdp/`、`unit*/` 各一套，含文件列表与 Genus tcl）。
踩过的坑，改 RTL 后再跑综合会再遇到：

| 坑 | 现象 | 处理 |
|---|---|---|
| **没加 `set_input_delay`** | `端口→寄存器` 的路径不上报也不优化，测出来的"关键路径"根本不含乘法器 | 测独立部件时务必给输入端口加输入延时（§9.3 坑一）。**复核结论**：端口后面本来就有流水寄存器的单元不受影响（裸乘法器 / 参考核 MUL / C906 MUL 复跑后都在 ±0.5% 内），真正被坑的是 cdp-tests 的 `MUL_DIV` |
| **用行为级 stub 补仓库里缺的 memory macro** | 阵列被综合成"触发器 + 异步读 mux"，最差路径落在阵列**内部**，整核频率严重偏低（cpu 参考核 1894 → 1668 ps，§9.3 坑二） | **把 memory 声明成空模块（黑盒）**再跑一次，用两次的差当假象量；判定方法见下 |
| **怎么判断一条路径是不是假的** | —— | 看**终点/起点**：`*_reg[i][j]`（二维数组）、`/CE`、`/CEN` 都是阵列相关；再往上翻一层，确认这个数组到底是**真 RTL** 还是**你为了跑通综合补的 stub**（`grep "module <名字>" `）。本次就是漏了这一步才误判过一次 |
| **CRLF 换行** | Genus 宏预处理器把 `\`+`\r` 当断行失败 → `` `read_reg `` 一类宏"未定义" → 级联报错 | 转 LF |
| **先用后声明** | `LSU.v` 的 `dcache_mem_rdata`、`mycpu.v` 的 `if_accept` | 声明上移（与 `sim/rtl_patch/` 同思路） |
| **`~`MACRO(x)``** | V2001 解析器不支持表达式里的函数式宏 | 内联（全设计只有 6 处） |
| **`if (!rst \|\| x)`** | Genus 拒绝把该信号识别成异步复位（`CDFG-364`） | 拆成 `if(!rst)…else if(x)…`（语义等价，x 本就不在敏感表里） |
| **`forever_cpuclk` 等门控时钟** | —— | 不需要特殊处理，直接约束主时钟即可 |

改动都在 `/tmp` 的镜像里，**没有污染 `cdp-tests/` 和 `cpu/` 的源码**。

### 9.7 PRF 写口数：**定 2 个**

三个数据点（都在本机源码里，可复核）：

| 核 | 规模 | PRF 写口 | 依据 |
|---|---|---|---|
| `RISCV_CPU/cpu` 参考核 | 2 发射乱序 | **7 个专用口** | `regs.v`：每个 FU 一套 `wflag/waddr/wdata` —— alu0/alu1/branch/mem/mul/div/csr，另有 2 个 alloc 口；PRF 就是 `reg [31:0] regs[0:63]`（`regs.v:113`）直接综合成触发器 |
| **C910**（同门，3 发射乱序，真流片） | 3 发射 | **2 个**（pipe0 / pipe1） | `ct_iu_rbus.v:318` / `:500` |
| C906 | 1 发射顺序 | 乘法专用口 + `rtu_iu_mul_wb_grant` 仲裁 | `aq_iu_mul.v` |

**C910 的分配方式（最值得抄的部分）** —— 写口是"每口挂一条 ALU 流水，别的单元并进去"：

```
pipe0 写口 = ALU0 + div + cp0 + vfpu-mfvr     // ct_iu_rbus.v:318,363
pipe1 写口 = ALU1 + mult + vfpu-mfvr          // ct_iu_rbus.v:500,536   ← 乘法在 pipe1
pipe2      = AGU/store，不写回
```

- 写口 mux 只做**一位有效的 `case`**（`ct_iu_rbus.v:361-372`、`:536-544`），**本身不做仲裁**；
- 冲突在**发射时**解决：`ct_iu_mult.v:357  assign iu_idu_ex1_pipe1_mult_stall = mult_ex1_inst_vld;`
  —— 乘法在 EX1 的那一拍，pipe1 不再接受 ALU 指令；
- **C910 的 `preg` 就是 `[6:0]`（7 位 = 128 项）**，跟本方案定的 PRF=128 完全一致。

**决定：cdp-tests 的 PRF 定 2 个写口**（照抄 C910 的分配：**乘 → pipe1，除 → pipe0**）。理由：

1. C910 是唯一的同门真实参照，它就是 2 个；
2. 写口少 → PRF 小 → 频率高（写口的代价是每 bit 一个合并级；**读口才是面积杀手**，
   3 发射要 6 个读口，那才是该抠的地方）；
3. "两条指令同拍抢同一个写口"**在发射仲裁里解决**，不是靠加写口解决；
4. **反例就是参考核的 7 个专用写口** —— 那就是它整核 155,835 cells、只跑到 600 MHz
   的原因之一（§9.4 第 5 条），不要学。

**对本单元的直接后果**：

- §3.2 的 `wb_grant` **要真做仲裁，不能接常量**：乘法每拍都可能要写回（II=1），
  会持续占用它那个口。发射队列必须保证同一拍只选一条要写该口的指令，
  否则**乘法会把 ALU1 饿死**（C910 是靠 `mult_stall` 反压解决的）。
- **乘除分属两个口**（乘→pipe1，除→pipe0）是个额外好处：除法那 3~19 拍完全不影响乘法写回。

**P2 再定一件事**（现在不用定）：是否让乘法和 ALU1 **物理上共用 EX 级**（C910 的
`mult_stall` 就是干这个的）。共用省一条流水前端，代价是乘法与 ALU1 互斥。
**本方案建议先不共用** —— 乘法独立流水才能保住 II=1 不打折，等面积紧张再说。

**已定**（2026-09-26）：

| 项 | 决定 | 影响 |
|---|---|---|
| 频率目标 | 对标 `RISCV_CPU/cpu` 参考核 | 参考核乘法单元 **869 MHz** / 除法 **1.33 GHz**（剔除假路径后的统一口径，§9.2）→ 目标 **~870 MHz**，`MUL_LAT = 2` 够用（§9.4） |

| **PRF 写口** | **2 个**（照 C910：乘→pipe1，除→pipe0） | `wb_grant` 要真做仲裁、不能接常量；发射队列须保证同拍只选一条写同一口的指令，否则乘法会饿死 ALU1。详见 §9.7 |
| **除法提前结束** | **保留** | 延迟数据相关（满量程 19 拍，小操作数 3~7 拍），但 ROB/计分板不受影响 —— 乱序下"什么时候回来"本来就由 tag 广播决定。代价只是一个 32 位优先编码器（~150 门，§5.2）。**C910 也做**（radix-16，`srt_iter_finish = srt_remainder_zero \|\| srt_cnt_zero`） |
| **MAC 累加口** | **留**，P1/P2 接 0 | 已把插入点定死在 M2 的 3:2 CSA（§4.6），`acc_mode=00` 时零成本；否则以后加等于重切 M2 级。**C910 就是这么做的**（`idu_iu_rf_pipe1_mla_src2_preg/vld`，src2 直接从 PRF 读） |

**遗留**（都是 P2 阶段的事，不阻塞 P1）：

1. **乘法要不要和 ALU1 物理上共用 EX 级**（C910 用 `mult_stall` 这么做）——
   共用省流水前端，代价是乘法与 ALU1 互斥。**建议先不共用**，见 §9.7 末尾。
2. **乘法单元的 op 编码怎么扩展到 MAC** —— 现在 `req_op` 4 位 + `req_acc_mode` 2 位
   （与 C906 的 `func[3]=add/func[4]=sub` 正交做法一致），够用；等真要加 MAC 指令时再定
   具体指令编码。

### C.3 三处与方案不同：综合和仿真把方案改掉了什么

**(1) 压缩树的切分点必须往前挪两级（§4.3 方案 A → A'）。**
方案 A 是"M1 = 编码 + 部分积 + 整棵压缩树；M2 = CPA"。照这个写法综合出来
`req_op[0] → sum_m2[60]` = 1056 ps 逻辑 + 250 ps 输入延时 ≈ 1306 ps ⇒ 只有 **766 MHz**，
比现状好不了多少（树里每一级在 nangate45 上约 110 ps，6 级就吃掉 660 ps）。
改成 **M1 只做树的前 4 级、后 2 级落到 M2** 之后 M1 降到 ~820 ps ⇒ 917 MHz，
而 M2（2 级 CSA + MAC CSA + CPA）仍有余量。代价是中间的 2 行也要各占 64 个 FF
（M1→M2 寄存器 2×64 → 4×64），比多切一整级（方案 B）便宜得多。

**(2) 除法的 PREP 必须拆成两拍（§5.2 的 "PREP 1 拍" → 2 拍）。**
方案里 PREP 一拍算完"取绝对值 → 前导位编码 → 求差 → 对齐量 → 摆除数 → 2D/3D"，
综合出来是 `req_src0[11] → d3_r[26]` **1922 ps**，比现状整个 MUL_DIV 还慢 ——
它会直接顶穿整核 Fmax。拆成：
```
拍1: |a| / |d| + 控制位            ~8 级
拍2: 前导位 → s → 对齐量 → 摆除数  ~19 级
```
之后这条路径掉出前三名（不再是瓶颈）。代价是除法延迟 +1 拍（n+4）。C906 也是
这么做的：它的 PREP 是 WFI1 → WFI2 → ALIGN 三个状态。

**(3) Booth 的符号不能省，但也不能绕道去算 |A|。**
第一版按"幅度 + 符号"写：`mag = |A|`（一级 34 位条件取反）再用 `cneg ⊕ A[32]` 当
扩展位。这一级在 M1 的关键路径上占 ~350 ps。去掉它的办法是直接用 A 的**符号扩展
形式**：正部分积取 `A_ext`（高位补 A 自己的符号）、负部分积取 `~A_ext`（高位补
`~A` 的符号）+ 在常量行里补 +1。于是这一级只剩"2A 左移一位"（纯布线）和一级取反。
⚠️ 顺带记一个坑：写成"把 33 位 A 当**无符号幅度**、用编码符号当扩展位"的话，
结果**只在高 32 位上错** —— `mul`（取低 32 位）完全看不出来，`mulh/mulhsu/mulhu`
全错。整核 difftest 里现有的用例几乎只用 `mul`，这个错是**单元级 TB** 抓到的。

### C.4 接口和整核侧的三个决定（与 §7 的措辞不同，但等价或更省）

1. **乘法结果在 WB 级注入，不在 `mem_wD`。** §7 写"MEM_WB 入口加 mux"，但按 §3.3
   的时序图乘法是 T 拍发射、T+2 拍出响应 —— 那正是它的 **WB 拍**，而 `wb_wD` 在
   T+1 边沿就已经从 `mem_wD` 锁好了，赶不上入口。所以 mux 落在 WB 级的输出上
   （`mycpu.v` 的 `wb_wD_eff`）。对齐靠"响应属于哪条指令由指令自己说了算"：
   `is_mul` 跟着指令走完流水，乘法的发射拍与 WB 拍恒定相差 2 拍。
2. **互锁不需要另建 N 项列表。** 顺序核里 `ex_is_mul/ex_wR` 与 `mem_is_mul/mem_wR`
   **就是**那份 MUL_LAT=2 的在飞列表，所以 `mul_stall` 只是 4 个比较器。行为上
   和 load-use **完全同构**（`stall` 与 `flush_ID_EX` 一起拉），只是停 2 拍。
3. **除数器保留"占住 EX + busy 反压"，不走 tag 写回。** 顺序核里 4~20 拍不值得
   引入计分板；结果出来那一拍由 `ex_alu_c_final` 折进流水，照常退休。
   ⚠️ `div_stall` 必须用 `md_resp_is_div` 限定 —— 乘法是真流水，它完全可能在除法
   迭代期间从写回口出来一条响应，不区分的话除法会拿着**乘法的结果**提前放行。

### C.5 三个真 bug（都是"看代码看不出来、跑起来才发现"）

| 症状 | 根因 |
|---|---|
| `mulh/mulhsu/mulhu` 高 32 位全错, `mul` 对 | Booth 行的符号扩展写错（见 C.3(3)） |
| 除法永远不出结果, 核挂死 | 顶层把 `div_req` 与了 `~div_busy`。除法是"请求保持到出结果"的协议, 请求中途变 0 会被当成"请求方跑了"而中止 —— 于是 FSM 每拍都在 IDLE↔ITER 之间弹跳 |
| 除法从流水里凭空消失 | `mul_stall` 看的是 EX **和 MEM** 两级, 于是"mul 退到 MEM + div 占着 EX + ID 要用 mul 的 rd"这一拍会把 ID_EX 清掉, 把**正在迭代的除法**一起清没了。修法: `flush_ID_EX` 里给 `mul_stall` 加 `~div_stall` 门控 |
