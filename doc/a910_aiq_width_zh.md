# A910 AIQ 深度扫描 (4 / 8 / 16) —— 参数化、等价证明与收益曲线

2026-10-16。承接 `a910-ooo-perf-aiq` 那轮诊断（A910 三发射乱序核只比 5 级顺序核快
3.9%，根因指向"移植时把发射队列砍小了"）。

**这一步做的事**：把 `ct_idu_is_aiq` / `ct_idu_is_aiq_entry` 从逐表项写死的 4 项改成
`AIQ_ENTRY` 参数化的 generate 版本，用 `+define+AIQ_ENTRY=N` 同源编 4/8/16 三档，
并行跑 `coremark_i1` 对比。

## 1. 结论 (TL;DR)

1. **加宽有效，但 8 项就基本吃完了**：4→8 省 **4.42%** 周期，8→16 只再省 **1.26%**
   （第二段只值第一段的 28%）。
2. **瓶颈按预期搬家了**：AIQ 满从"等派拍"的 39.8% 掉到 9.4%，腾出来的位置立刻被
   **BIQ / LSIQ / SDIQ / ROB** 顶上 —— 这就是 `ct_idu_is_ctrl.sv:576` 那个
   "任意一个队列满 ⇒ 整个程序序派遣口停" 的直接指纹。
3. **16 项的"满"已经不是深度不够了**：满的那些拍里 89.4% 正在发射（占着说明活儿多），
   占用均值才 5.41/16。再往上加深度没有意义。
4. 下一步的杠杆不在 AIQ，也不在 ROB：**ROB 从头到尾没满过**（occ ≥ 60 一拍都没有，
   峰值才 40）。现在挡在最前面的是**BIQ 满 16.3%**、**未决重定向 15.9%**（前端）、
   **LSIQ 满 11.1%**、**前端无货 19.3%**。前两个是"派不进去"，后两个是"前端没货"。

|---|---|---|---|---|---|---|---|---|---|

### 整场 30 迭代 CoreMark（**正式分数，以此为准**）

| AIQ_ENTRY | 判定 | 拍数 | IPC | Total ticks | **CoreMark 分数** | **@180MHz** | 合法性 |
|---|---|---|---|---|---|---|---|
| **4** | **PASS** (0 失配) | 10,992,323 | 0.859 | 10,959,101 (10.96 s) | **2.7375** | **492.7** | ✓ 余量 9.6% |
| **8** | ⚠️ **FAIL (失配)** | — | — | — | — | — | 见 §6 |
| **16** | **PASS** (0 失配) | 10,306,172 | 0.916 | 10,189,233 (10.19 s) | **2.9443** | **530.0** | ✓ **余量只剩 1.9%** |

* **AIQ=4 复现了已知的 2.737**（最后拍 10,992,342 vs 改动前的 10,992,343）⇒ 整条链路
  （树 / 台子 / 参数化在 N=4）逐位可信。
* **整场 4→16 省 6.24%，比 i1 代理的 5.63% 更大** ⇒ 快代理方向对，但**低估**了幅度。
* 分数口径：`分数 = ITERATIONS(30) × 1e6 / Total ticks`。⚠️ CoreMark 自己打的
  `Iterations/Sec : 3` / `Total time (secs): 10` 是 port 的**整数除法**假象
  （`core_portme.c:47 return ticks/1000000u` 截断），**别引用那两行**。
* ⚠️ **合法性门槛卡得很死**：`core_main.c:415` 要求 ticks ≥ 10,000,000。16 档实测
  10.189M —— **再优化 2% 分数就作废**。再往后必须先把 `ITERATIONS` 加上去
  （但那会替换入库的 `bin/coremark.bin`，历史分数将不可比，需要先定口径）。

<sup>[1]</sup> 占"有指令等着派"的拍数（`perf_blk_aiq / perf_blk_wait`）。
<sup>[2]</sup> 与 4/8 档差 13 条，是仿真停在"黄金模型撞到 ecall"那一刻的停机口不同所致；
三档的**逐条比对都是 0 处不一致**（见 §4），与指令流正确性无关。

"没满"（1.1% / 0.3%）纯属假象 —— 它们被 AIQ 堵在身后，根本没轮到它们满。AIQ 一放开，
它们立刻现形。**同时"等派总拍数"在三档里单调下降**（370,680 → 331,621），说明堵点
确实在变松，不是在换个地方原地打转。

> `rtu_idu_rob_full` 是 `rtu_disp_stall`（`RTU.v:891`
> `= rob_full | csr_inflight | flushing | mispred_pend`，`RTU_idu_lsu_adapter.v:284`），
> 四个条件相或。拆开一量：**`rob_full`（occ ≥ 60，`RTU_define.vh:97`）在三档里
> 一拍都没出现过**（ROB 峰值占用才 40），CSR 在途也是 0。那一格 9.3%→15.9% 的增量
> **全部是"未决重定向 + 冲刷恢复窗"**，属前端/预测器，不是后端容量。
> 探针已按四项拆开（`+PROBE_PERF` 输出里那组 `├ └` 就是）。

### AIQ 自身的深挖

| | 4 项 | 8 项 | 16 项 |
|---|---|---|---|
| 满（cnt ≥ N−1，占全拍） | 46.2% | 23.9% | 8.7% |
| ├ 其中有就绪项 | 68.2% | 77.9% | **89.4%** |
| └ 其中无就绪项 | 31.8% | 22.1% | 10.6% |
| 发射率（次/拍，上限 1） | 0.531 | 0.567 | 0.579 |

"满着仍在发射"与"满且有就绪项"始终同值（127,755 / 71,991 / 29,674 拍），说明
**ALU 发射口没有仲裁气泡** —— 有就绪项就一定在发。所以：
* 4 项时满＝**深度不够**（有就绪项发不出去，占满的 68.2%）；
* 16 项时满＝**活儿真的多**（89.4% 正在发射），已经不是深度问题了；
* 发射率 0.579 ≪ 1，单发射口**没有饱和** ⇒ 剩下的损失在别处（上游喂不满 + 其余队列）。

## 2. 参数化改了什么（转交 IDU 同事）

改的是 **IDU 地盘的**两个文件，外加 TB 里的探针：

| 文件 | 改动 |
|---|---|
| `mySoC/idu_c910/rtl/ct_idu_is_aiq.sv` | 整体重写：逐表项写死 → `generate` 展开；新增 `AIQ_ENTRY`（默认 **8**） |
| `mySoC/idu_c910/rtl/ct_idu_is_aiq_entry.sv` | 新增 `AIQ_ENTRY`；agevec 端口从写死 `[2:0]` 变成 `[AIQ_ENTRY-1:0]` |
| `tb/a910/tb_a910_difftest.sv` | `+PROBE_PERF` 的 AIQ 深挖改成跟着 RTL 走（`$bits` 量深度），不再写死 4 |
| `tb/a910/tb_aiq_equiv.sv`, `tb/a910/ref/` | 新增：逐拍等价自检台 + 冻结的原版（见 §4） |
| `Makefile` | 新增 `make aiq-equiv` |

### 两处**刻意**的语义改动（已证明 N=4 逐拍等价）

1. **年龄向量 (agevec) 改成 N 位自屏蔽约定**（位 i ↔ 表项 i，自己那一位恒 0）。
   原版是 N−1 位紧凑约定（"除自己外按序号降序"），4 项时正好 3 位才写得死。
   自屏蔽下 `older_ready[i] = |(agevec[i] & ready)` 一步到位。
   两种约定在 N=4 时逐位等价（自测台按语义映射后逐位比过）。
2. **full / 1_left 判据**改写成"下一拍占用 `R = cnt + create − pop`"再比
   `AIQ_ENTRY` / `AIQ_ENTRY−1`，不再枚举项。原版 N=4 的六个枚举项与之**逐项等价**，
   但有两个坑必须留着（自测台各抓到一次，见 §4）：
   * `full` 上必须带 `&& !aiq_xx_issue_en`（原版三项全是 `pop_0` 起头：本拍有项发走
     就腾出坑，下一拍照样能派）；
   * 优先级编码是 "**低位优先 ⇒ 比它小的那些项全忙**"，写成 `&(vld | ~MASK)`，
     别写成 `~|(vld & MASK)`（那是"全空"，会一拍给好几个表项发 create）。

另：原版 `aiq_entry_create_sel` 是**死代码**（赋了值没有任何读者），已删。

### 怎么用

```bash
make a910-difftest-all VCS_FLAGS_EXTRA=+define+AIQ_ENTRY=4   # 回到 4 项
make a910-difftest-all VCS_FLAGS_EXTRA=+define+AIQ_ENTRY=16  # 扫 16 项
# 不给 +define+ 就是默认 8 项
```

⚠️ 三个 meminit 软链（`meminit.bin/.hex/meminit128.hex`）是**编译期烧死的绝对路径**，
多个 BUILD_DIR 并行时它们共用同一组软链 —— 同时跑不同用例会互相踩。

## 3. 三档怎么跑的（口径）

* **快迭代代理**：`coremark_i1`（1 迭代，405,543 拍，~2 分钟），加 `+PROBE_PERF`
  一次打全。
* 三个独立 BUILD_DIR 同源编：`obj_a910_dt`(4) / `obj_a910_dt_a8`(8) /
  `obj_a910_dt_a16`(16)，三个 simv **并行**跑，日志在 `/tmp/sweep/n{4,8,16}.log`。
* 跑分**不经 make**（直接调 simv）：
  ```bash
  ./obj_a910_dt/simv +vcs+lic+wait -no_save -exitstatus \
     +TEST=coremark_i1 +PROBE_PERF +MAX_CYCLES=2000000 -l /tmp/sweep/n4.log
  ```

### ⚠️ 这台代理的可用范围

* ✅ **结构性口径可信** —— 周期去向、谁在挡、占用/满率、瓶颈迁移，逐拍累加的真值。
* ❌ **比值类 A/B 的绝对值不可信**（见 `iter1-proxy-unreliable`）：i1 的 IPC 0.837 与
  整场 30 迭代的 0.859 差 2.6%。**所以 §1 表里 −4.42% 这个数，方向和各队列的此消彼长
  是可信的，但"score 涨多少"必须拿整场 30 迭代重测一遍才能对外报。**
* ❌ **Fmax 没测**。N=16 时 issue 数据通路的选择器是 16 级优先级链，
  older-ready 是 16×16 与或阵 —— 面积/时序都没量过。**默认取 8**（也是 C910 每 bank
  的原值），要上 16 得先过综合。

### 三档都是"指令流正确"的

三档的 difftest 判定都是 `FAIL (用例自检没过)`：`黄金模型停在 ecall 时 a0 != 0`。
这是 **CoreMark 自己的失败分支**（`ITERATIONS=1` 撞 coremark 的 `≥10s` 规则，分数不合法
→ 退出码 1），**不是指令失配** —— TB 里那句提示就是干这个的，用 `+NOVALID` 可放开。
三档日志里 `与黄金模型不一致` 的出现次数都是 **0**。

> 对照：**N=4 这一档与改动前的树逐拍等价（§4）**，它同样是这个判定 ⇒ 这个 FAIL 是
> 这棵树/这个二进制固有的，不是本次改动引入的。

## 4. 为什么敢动同事的文件：逐拍等价自检

`make aiq-equiv` —— 把新版 `ct_idu_is_aiq(AIQ_ENTRY=4)` 与
`tb/a910/ref/` 里**冻结的原版**并排喂同一串开环激励（灌满 / 单建表 / 排空 / 随机四段
+ 随机写回 + 偶发冲刷），逐拍比较：

* 输出：`issue_en` / `issue_read_data` / `full_updt` / `1_left_updt`
* 内部：`entry_cnt` / `entry_vld` / `entry_ready` / `issue_en` / **每个表项的 agevec**

第一处分歧就停并打印现场（输入 + 两边状态），退出码非 0。

```
跑 200000 拍, 不一致 0 处
覆盖: 发射 4425 拍 | full 21296 拍 | 1_left 23342 拍 | 建表 104866 拍 | 冲刷 1332 次
AIQ 占用分布 (cnt=0..4): 41750 23129 23934 23259 21824   [cnt>N: 66101 拍]
  ⚠️ cnt>N 那 66101 拍是开环激励『满着还硬建表』走出来的
     (真核里被 ctrl_is_dis_stall 闸住, 不可达) —— 两份 RTL 在这一支上
     同样逐拍一致, 属额外覆盖。
===> PASS: 参数化版本 (N=4) 与原版逐拍一致
```

最后那行是**故意**的：开环激励不看 ctrl 的闸门，会把"队列已满还硬建表"这一支也喂进去
（真核里不可达）。那一支下 `cnt` 会跑到 N 之上（建表请求被记账，但优先级编码已经没有
空项可给）—— 这是**原版就有的性质**，不是本次引入的。两份 RTL 连这一支都逐拍一致，
所以是额外覆盖；单独计数、不藏进直方图外。

**这个台子当天抓到两个真 bug**（都是我在重写时引入的，difftest 只会报"整颗核卡死"，
指不到地方）：

| # | 症状 | 真因 |
|---|---|---|
| 1 | 第 4 拍就有分歧 | 建表优先级编码写反：`~\|(vld & MASK)` 是"比我小的全空"，应为 `&(vld \| ~MASK)`"全忙" —— 一拍给 4 个表项全发了 create |
| 2 | 第 13 拍 `full_updt` 多堵一下 | `full` 少了 `&& !issue` |

**变异自检**：故意把 `1_left` 判据改成 `AIQ_ENTRY-2`，台子在第 7 拍报
`1_left_updt: new=1 ref=0` 并让 make 退出码变 2 ⇒ 台子不是空转的。
（顺带修了一个真坑：VCS 不加 `-exitstatus` 时 `$fatal` **不影响退出码**，红了 make 还是绿的。）

## 6. ⚠️ 未决：整场下 AIQ=8 失配（4 和 16 都干净）

整场 30 迭代里 **AIQ=4 与 AIQ=16 逐条比对通过（0 失配）**，**AIQ=8 在第 2,246,837 条退休
（T2,503,931）失配**：

```
pc=0x00000f2c  0x00079683 = lh a3,1942(a5)        ← LOAD，两边同一条指令
debug_wb_value 0x0000008b (模型) / 0x0000007a (DUT)   ← 差 0x11
内存 0xfa8c..0xfa9c 整排 DUT = GM − 0x11              ← 那个 0x11 的 store 没落
```

指纹与 `doc/a910_difftest_zh.md` **§7.1**（"已提交的 store 丢写"，LSU 地盘、只定位未改、
已转同事）一模一样。AIQ 是 ALU 发射队列，碰不到 store 通路；但**不能说与我无关** ——
它改变调度，可能只是把这条时序敏感的既有竞争**撞出来**（§4.7 那条：`cmit_set=1` 与
`flush=1` 同拍，LSU 用边沿前的值判 flush_clear）。

**4 和 16 都过、只有 8 挂**，目前只能解释为"时序敏感的暴露点恰好落在 8 的调度上"，
但也**不能排除 8 档自身有 corner**。

⇒ **把默认档定成 8 之前，必须先查清这一条。** 三个候选取舍：
① 先查出根因（推荐）；② 默认退回 4（= 原树，放弃收益）；③ 默认取 16
（已 PASS 且有分数，但 Fmax 代价未测、分数余量只剩 1.9%）。

## 7. BIQ 同理参数化（2026-10-16 同日）

照 AIQ 的模板把 `ct_idu_is_biq.sv` / `ct_idu_is_biq_entry.sv` 参数化（`BIQ_ENTRY`）。
**动它的依据来自参照测量**：整场 30 迭代里 **C910 的 BIQ 满只占 0.0%**（它 12 项），
而我们 4 项时 11.8%、AIQ 加宽后升到 **17.0%** —— 是唯一一项比参照设计差一个数量级的地方。

| BIQ_ENTRY | 拍数（coremark_i1） | IPC | BIQ 满 | AIQ 满 |
|---|---|---|---|---|
| 4（原树） | 387,606 | 0.876 | 15.0% | 19.0% |

## 8. 疑点：-O3 版 CoreMark 两个环境都跑不动（**未定论**）

**动机**：C910 那边 CoreMark 是这么编的 ——
`-O3 -mtune=c910 -funroll-all-loops -finline-limit=500 -fgcse-sm ...`，
而我们只有 **`-O2`**。而参照测量显示我们**每次迭代多跑 1.64× 的指令**
（314,689 vs C910 的 191,899），分数因此直接吃 1.64× 的亏。

**已查清的**：

| 查了什么 | 结果 |
|---|---|
| 软乘除? | ❌ 不是，`ARCH=rv32im`，二进制里有 26 条 M 指令 |
| run 类型不同? | ❌ 不是，两边都是 `2K performance run`、`CoreMark Size: 666` |
| 镜像超限? | ❌ 不是：`.text` 57,565 B + `.data` 到 0xE0F8，栈顶 0x10000，**还剩 ~7.9 KB**；两块存储器都是 64 KB |
| 启动代码不同? | ❌ 不是：两边 `_start` **逐条一样**，只有 `jal main` 的落点不同（0x26a8 vs 0xcb24） |
| 静态代码膨胀 | ✅ 14 KB → **57.6 KB**（`-funroll-all-loops` 的典型特征） |

**两个环境的失败是不一样的，不能当一个 bug 看**：

* **A910**：正确执行了 **47,452 条**才失配 ⇒ **镜像装载/取指都没问题**；
  失配差值是 **0x11**（`pc=0x2454` reg24: 0x27 vs 0x16）—— **与 AIQ=8 整场那次同指纹**。
* **顺序核**：只退休 **10 条**就死（正好把启动跑完、死在 `main` 入口），**原因不明**。

⇒ **结论：`-O3` 那条路现在量不了**，因为 A910 上它 47K 条就撞上了既有的 store 丢写
（AIQ=8 那次是 2.25M 条才撞上）。**这反过来把那个 store bug 的优先级顶上来了**：
它现在是**两件事的共同拦路虎** —— 整场 AIQ=8 的分数、以及这条 1.64× 的工具链路。

**建议**：先修 store 丢写（`doc/a910_difftest_zh.md` §7.1 家族，LSU 地盘），
再回来量 -O3。不要先花时间在工具链上。

## 10. ★★★ store 丢写：**结案**（2026-10-16 晚）

前面 §9 的三条嫌疑（SDIQ 被冲、WMB/CE merge 丢、dcache dirty 被清）**全都不对**。
逐拍探针把现场钉死之后，真因是 **LSU 里一次"阵列回读 vs LFB 回填"的同拍竞争**，
与冲刷无关。

### 10.1 先把前面读错的地方纠正掉

* **`[CEM] ahit` 不是 "命中 dcache"**。它是 `wmb_ce_merge_data_addr_hit` =
  "CE 手里的 store 地址 == 当拍 SQ pop 地址（16B 粒度）" —— CE 拿着队头那笔时**恒为 1**。
  §9 里"写 0xfa8c 命中了 dcache 行"这句作废。
* **"0xfa84~0xfa8f 从没上过 AXI" 也不是丢写**：那条线后来被**回填进 dcache 变脏**，
  写回本来就要等到被逐出（本用例到失配为止都没逐出）。拿内存比对会把它读成"少一次更新"。
* **§9 的失配地址也不是 0xfaae**。逐笔打交付值（`[R20-LDB]`）看到：
  `T57360 iid=50 addr=0xfa8c wb_data=0x0003`（黄金模型 0x14）——差 0x11 的正是这笔。

### 10.2 现场（`+PROBE_RGN`，按地址/set 触发，不设拍窗）

线 `0xfaa0`（set 21）：

```
T56977..84  load 0xfaa2..0xfaae 连续 miss（该行还不在 dcache）→ LFB 取数
T56986      [R20-WD] set=21 dirty-wr din=10101 wen_b=01100 src[L,V,A,W]=1000  ← LFB 回填 way0
T56987      [R21-DIR] 00000 -> 10001        ← 回填落地
T56987      [R20-ST]  iid=119 addr=0xfaa0 hit=0 v0=0 t0=0 darr=00000  ← store 在 st_da，判 miss
T56987      [R20-SQE] e0 iid=119 vld=1 info_vld=0                    ← 建表/首次采信息那一拍
T56988      [R20-SQE] e0 iid=119 info_vld=1 dc_vld=0                 ← 记下 miss，之后再没改过
T57006      [R20-WMB] e3 addr=0xfaa0 dc_req=0 biu_req=1              ← 于是这笔走内存
T57008      [R20-W]   wr_addr=0xfaa0 strb=000f data=...0027          ← 内存里是对的
            dcache 里那条线却一直是回填来的旧值 0x0016
T57441      load 0xfaa0 命中 dcache ⇒ 读回 0x0016（黄金模型 0x0027）⇒ 第 47452 条退休失配
```

三条同族链路都要讲清楚：

1. **st_da 的回读是"上一拍"的内容**。tag/dirty 是单口同步 SRAM，index 由 **AG 级**
   送进去（`ag_dcache_arb_st_dirty_idx = st_ag_addr[9:5]`），st_da 用的是再往后一级的
   寄存回读 ⇒ 只要 LFB 的回填**正好落在 store 还在 st_dc 的那一拍**，本次回读拿到的
   是回填**之前**的阵列（read-first）⇒ 判 miss。原本已有的 `st_dc_dcwp_hit_idx`
   旁路只把 **dirty 位**补了一刀，**命中判据本身没补**。
2. 判 miss 之后，表项把 `dc_vld=0` 记进了 SQ（`st_da_sq_dcache_valid`）。
3. 本该有第二次机会：SQ 表项里的 `lsu_dcache_info_update` 会在**回填那一拍**发现
   "我等的行进来了"并回写 `dc_vld`。但它被 `sq_entry_dcache_info_vld` 闸着，
   而那一拍 `info_vld` 还是 0（要到 `st_da_info_set` 的下一拍才置 1）⇒ **更新被吞**。

⇒ 表项永远停在 miss；这笔 store 走 BIU 直写内存，而回填已经把**旧值**铺满 dcache。
**内存与 dcache 从此各持一份**，谁后到谁说话。

### 10.3 修法（同事已授权改 LSU；两处，互补）

| 文件 | 改什么 | 盖住哪个窗口 |
|---|---|---|
| `lsu_st_da.sv` | 把写口的 **tag 数据/写使能**也按 `st_dc_dcwp_hit_idx` 那套寄存下来，命中判据加一支：写口那一拍把**本行**写进 dcache（tag 比过 + valid 位取自写口的 din/wen）就当命中 | 回填落在 **st_dc** 那一拍 |
| `lsu_sq_entry.sv` | 建表拍允许 `lsu_dcache_info_update` 的 **miss 支**（新增出口 `compare_dcwp_miss_up_vld`）落地 | 回填落在 **st_da** 那一拍 |

两支都是**纯增量**：阵列回读命中时行为完全不变。第二处**不能**放宽成
`|| st_da_info_set` —— 建表拍的 `origin_dcache_valid/way` 还是上一个住户的残值，
会把错路号写进表项。

> ⚠️ 踩过的坑：`a && b | c && d` 在 Verilog 里是 `a && (b|c) && d`（`|` 比 `&&` 紧），
> 省括号会把 `st_da_info_set` 变成**所有**更新前提 ⇒ store 一离开 st_da 就再也学不到回填，
> 反而把 0xfa8c 那笔推去写内存。实测抓到，已补括号。

### 10.4 验证

* `-O3` 快复现（原来是第 47,452 条退休失配）：**失配消失**，一路跑到 219,025 条退休无失配。
* `make a910-difftest-all`：见 §11。
* 遗留（**新现象，另案**）：-O3 跑到 T256.8K 时**挂住**——SQ 里一笔已退休 store
  （iid=115 @0xf73c）的 SDIQ 数据源没了，`sq_entry_cmit_data_not_vld` 恒 1 ⇒
  `RTU_flush` 的 WAIT 态永远出不去 ⇒ 前端冻结。与本次丢写**不是**同一条（这次是
  "数据没到"，不是"数据走错地方"），但同属 §9 那条"退役先于数据"的族谱，需要单独查。

### 10.4.2 挂死根因（2026-10-16 晚，逐拍追完）

**一句话**：**同一笔 store 被派发了两次** ⇒ 建了**两张 SQ 表项**、绑**同一个 SDIQ 号**；
SDIQ 表项在第二张表建出来**之前**就已经把数据发完并弹掉了 ⇒ 第二张表**永远拿不到数据**
⇒ 它退休了却没有数据 ⇒ `sq_entry_cmit_data_not_vld` 恒 1 ⇒ `RTU_flush` 的 WAIT 态
永远出不去 ⇒ 前端冻结 ⇒ 死锁。

逐拍现场（-O3 flags 版，T260,174~260,181，`+PROBE_BD`/`+PROBE_SDP`）：

```
T260174  IDU 派发 iid=109 @0x0000f75c sdiq=1000        ← 第一次派发
T260176  st_dc: create=1 sdio=1000 pulse=1000          ← 建 SQ 表项#1，脉冲把 SDIQ 表项3 的
                                                          has_in_sq 置 1
T260177  sdiq entry3: has=1 issue=1                    ← SDIQ 把数据发出去（给了表项#1）
T260177  IDU **又派发** iid=109 @0x0000f75c sdiq=1000   ← ★ 同一笔 store，3 拍后第二次派发
T260178  sdiq entry3 → 无效（数据已发完，弹掉）
T260179  st_dc: create=1 sdio=1000 pulse=1000          ← 建 SQ 表项#2，脉冲**打给一个已经没了的
                                                          SDIQ 表项** ⇒ 没人接 ⇒ 数据永远不来
T260181  sq notdvld=000100                             ← 表项#2 退休了却没有数据 ⇒ 闸门锁死
```

**为什么 -O2 能跑通而 -O3 挂**：双派发**两边都有**（-O2 那 4 万拍里也抓到 1 次，5 拍间隔；
-O3 是 3 拍间隔），差别只在**竞速**——

| | 第二次建表时 SDIQ 表项还在吗 | 结果 |
|---|---|---|
| -O2 那次（iid=112@0xf6e0） | **还在**（`sdiq v=1110`）⇒ 脉冲置上 has ⇒ 正常发数据 ⇒ 两张表都拿到 | ✅ 没事 |
| -O3 这次（iid=109@0xf75c） | **已经弹了**（`sdiq v=0101`）⇒ 脉冲打空 | ❌ 孤儿 ⇒ 死锁 |

⇒ 这是**既有竞态**，激进优化只是把双派发的间隔从 5 拍压到 3 拍，正好压进 SDIQ 弹出窗口。
**不是什么"展开把核跑坏了"**，也（大概率）与本次丢写修复无关：那条在"阵列命中判据"，这条在
"IDU 派发 → SDIQ 借还"这条契约上。

**修法候选**（未动，属 IDU↔LSU 契约，先给同事）：
1. **查双派发本身**：为什么同一笔 store 会在第一份还在流水里时再派一次
   （replay？`st_da_restart_vld`？）—— 最干净的修法在源头。
2. **SDIQ 弹出加守卫**：`lsu_idu_ex1_sdiq_pop_vld` 要求"绑它的 SQ 表项数据已齐"
   —— 挡不住"以后还会来第二张" ✗，只能缓解。
3. **逃生口**：SQ 表项若发现自己的 SDIQ 号已失效且无数据，允许按"已完成"放行
   （或重新取数）—— 兜底，但要想清楚对齐/边界语义。

#### 10.4.3 ★ 结案：候选 ① —— 一行 RTL（2026-10-16 晚）

**双派发的源头是 `mySoC/lsu/rtl/lsu_st_ag.sv` 的 DC 出口写错了掩码口径**：

```verilog
// 原版 ct_lsu_st_ag.v:1331-1375
assign st_ag_stall_restart = cross_page_str_imme_stall_req || st_ag_dcache_stall_req
                             || st_ag_mmu_stall_req || st_ag_atomic_no_cmit_restart_req; // ⚠️ 不取反 mask
assign st_ag_dc_inst_vld   = st_ag_inst_vld && !st_ag_stall_restart;
// 本仓原来                    st_ag_inst_vld && !st_ag_stall_vld     ← stall_vld 已被 mask 取反 ⇒ 错
```

`mask=1` = RF 那条 store 比 AG 里那条**更老**（原版注释 "for performance, when ag stall, let
oldest inst go"）。那拍原版做的是**两个必须成对的动作**：

1. `st_ag_stall_vld=0` ⇒ AG 寄存器让给更老的（手里更年轻那条**被挤掉、永远到不了 DC**）；
2. `st_ag_stall_restart_entry` 选 `st_ag_lsid`（被挤掉那条）发 wakeup ⇒ 让它回 LSIQ 重新发射。

本仓 ② 是对的、① 的 DC 口却用了 `!st_ag_stall_vld` ⇒ **被挤掉的那条照样往 DC 走** ⇒ 同一条
store **既建了一张 SQ 表项、又被 wakeup 重新发射再建一张** = 双派发。
**`mask=0` 那拍 `stall_vld == stall_restart`，两种写法逐拍等价 ⇒ 只动 mask=1 那条路。**
（`lsu_ld_ag.sv` 没这个 bug：它写的是 `!ld_ag_stall_ori`，本来就是 mask 之前的口径。）

**定位手法**（加了 `+PROBE_LSIQ` 探针）：探针打 `lsiq_dp_pipe4_issue_entry` / 每个表项的
`frz` / `lsu_idu_imme_wakeup` / `lsu_idu_secd`。判据是**"两个不同的 LSIQ 表项发同一条指令"**
（一次 entry1、一次 entry0）—— 这一条直接排除"同一表项重发"，指向"重复注入"。
`frz` 是"发过一次就置 1"的锁，看它是被 `lsu_idu_imme_wakeup` 清的，顺着它的 6 个来源倒推就到了
`st_ag_stall_restart_entry`。
⚠️ 探针的 `p4_is`（当拍读哪个表项）与 `idu_lsu_st_iid`（**上一拍**读到的数据，是寄存器）
**差一拍**，映射是 `p4_is(T) ⇒ iid(T+1)`；按同拍读会得出自相矛盾的结论（这轮先被骗了一次）。
