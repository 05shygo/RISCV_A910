================================================================================
一、组合环：IDU 把 rtu_idu_alloc_preg*_vld 当"同拍许可"用
================================================================================

---- 问题（一句话）----------------------------------------------------------
IDU 拿 RTU 给的 alloc vld 决定自己停不停，而这根 vld 又是 IDU 本拍请求的
组合函数 —— 请求 → vld → 停顿 → 请求，绕成一个组合环。

---- 环是怎么闭合的（三行）--------------------------------------------------

1) IDU 的停顿链里有这根 vld（ct_idu_ir_ctrl.sv:246-254）：

     assign ctrl_ir_preg_stall =
          ir_inst0_vld && dp_ctrl_ir_inst0_dst_vld && !rtu_idu_alloc_preg0_vld
       || ir_inst1_vld && dp_ctrl_ir_inst1_dst_vld && !rtu_idu_alloc_preg1_vld
       || ir_inst2_vld && dp_ctrl_ir_inst2_dst_vld && !rtu_idu_alloc_preg2_vld;

     assign ctrl_ir_stage_stall = ctrl_ir_preg_stall;
     assign ctrl_ir_stall       = ir_inst0_vld && (ctrl_is_stall || ctrl_ir_stage_stall);

   同一根 ctrl_ir_stall 又是 IR 级寄存器的使能（:193），并往上一路反压到
   ID 级与 IFU（ct_idu_id_ctrl.sv 的 idu_ifu_inst*_ready）。

2) 请求本身由停顿链决定（ct_idu_ir_ctrl.sv:259-262）：

     assign idu_rtu_ir_preg0_alloc_vld = ir_inst0_vld
                                         && !ctrl_ir_stall          ← 就是上面那根
                                         && dp_ctrl_ir_inst0_dst_vld
                                         && !dp_ctrl_ir_inst0_dst_x0;

3) RTU 的 vld 是"本拍请求"的组合函数（RTU_preg.v:242-244）：

     assign rtu_preg_alloc_vld0 = req_lane[0] & (|cand0);   // req_lane ← ren_preg_req

   ren_preg_req 正是第 2 条那根请求数出来的。环闭合。

---- 为什么不能靠"晚一拍再用"绕开 ------------------------------------------
因为 IDU 是**同拍消费**编号的（ct_idu_ir_dp.sv:283-285）：

     assign ir_inst0_dst_preg[5:0] =
            {6{!ir_inst0_data[IR_DST_X0]}} & rtu_idu_alloc_preg0[5:0];

编号同拍就进 RAT（ct_idu_ir_rt）并随指令进发射队列（路径如此；RAT 的写使能现在
是悬空的，见 (4) 的先决条件）。所以 vld 必须在**同一拍**告诉它"这拍拿不拿得到"；
拿不到就当场把 IR 级停住 —— 这是"池子空了立刻停"的机制，改成晚一拍等于晚一拍
才发现池子空，会多派出指令（或派出拿不到号的指令）。

⚠️ 注意这与 rtu_plan_zh.md §6.0 写的"T 拍你要、T+1 拍你用"**不是同一个相位**。
§6.0 那句是给我们自己的重命名级定的口径；接 C910 IDU 时以 IDU 的"同拍取用"为准。

---- C910 的做法：vld 与编号一起放进寄存器 ----------------------------------

ct_rtu_pst_preg.v:7376-7393（alloc_preg0_vld / alloc_preg0[6:0] **都是寄存器**）：

     always @(posedge alloc_preg_clk or negedge cpurst_b)
     begin
       if(!cpurst_b) begin
         alloc_preg0_vld  <= 1'd0;
         alloc_preg0[6:0] <= 7'd0;
       end
       else if(rtu_yy_xx_flush) begin          // 冲刷清掉
         alloc_preg0_vld  <= 1'd0;
         alloc_preg0[6:0] <= 7'd0;
       end
       else if(alloc_preg0_invalid) begin      // 空着、或 IDU 这拍要取走 -> 重填
         alloc_preg0_vld  <= dealloc_preg0_vld;
         alloc_preg0[6:0] <= dealloc_preg0[6:0];
       end
       else begin                              // 否则保持不动
         alloc_preg0_vld  <= alloc_preg0_vld;
         alloc_preg0[6:0] <= alloc_preg0[6:0];
       end
     end

重填条件（ct_rtu_pst_preg.v:6995，另有 :7353 同形的项）：

     assign alloc_preg0_invalid = (!alloc_preg0_vld
                                   || idu_rtu_ir_preg0_alloc_vld ...);

出口只是这根寄存器的组合扇出（:7460-7467）：

     assign rtu_idu_alloc_preg0_vld  = alloc_preg0_vld;
     assign rtu_idu_alloc_preg0[6:0] = alloc_preg0[6:0];

于是整件事变成"**提前把号备在门口，谁要谁拿，拿走的下一拍补一个**"：

  * vld 不再依赖本拍请求（只依赖上一拍的池子状态）⇒ 环路被寄存器打断；
  * 值必须**常驻有效**：池子空时 vld=0，IDU 就停 —— 这正是 IDU 要的"同拍许可"；
  * 号是谁的并不重要（自由池里的号彼此等价），所以"上一拍备的号给这一拍的指令"
    在功能上是成立的；
  * 附带好处：96 位优先编码器被摘出改名关键路径 —— 和我们 RTU 用 WF_ALLOC 打拍
    是同一个动机（RTU_preg.v:8-14、§4.2 的 P3）。

---- 对本核的两条落地路线（选一条）-------------------------------------------

路线 A：照抄 C910 —— 适配层给"号 + vld"各加一级寄存器，
        重填条件照 alloc_preg*_invalid 写（!vld || 本路请求）。
  ⚠️ 号会晚一拍到 IDU，派遣回执也跟着晚一拍 ⇒ **必须同时把 WF_ALLOC 的回收
     窗口从"晚一拍"放宽到"晚两拍以上"**（RTU_preg.v:359-390 的 wf_age：
     晚两拍没人认领就把编号放回 FREE）。否则指令还攥着号，号已经被回收/重发。

路线 B：只破环、不给号打拍 —— 许可改用**已寄存的** `rtu_preg_free_cnt`
        在适配层合成（vld_k = 本路请求 & 池子够），编号路径保持组合。
  ⇒ 环路同样断开（free_cnt 是寄存器），且不引入额外延迟；
  ⇒ 但回收窗口仍是零余量，见下条。

两条都要实测的一件事：**派遣回执必须在"选择拍 +2"之内到**（现在是 +1/+2 两拍
容忍）。IDU 侧 IR 改名 → IS → IS 派发 才到 ROB（ct_idu_is_ctrl 的 is_dis_* 那一级），
所以回执大概率落在 +2 或 +3。**这个数现在量不出来** —— 因为 IDU 顶层根本没有
派遣记录端口（见第二节），等 Phase 3 补出来才能量。稳妥做法：先把回收年龄放宽。


================================================================================
二、RTU 需要 IDU 新增的端口
================================================================================

前提：RTU §6.1 要的"三路派遣记录"（每路 12 个字段 + vld）在 IDU 顶层
**一个都不存在** —— 116 个端口里没有 rob_create*，也没有 pst_dis_inst*。
C910 原版是 idu_rtu_rob_create0..3_{data[39:0], en, dp_en, gateclk_en}，
4 路、打成一条 40 位总线。所以这不是"接线"，是
**给 IDU 加端口 + 从 IS 派发级把字段引出来**（Phase 3 记的那件事）。

⚠️ 有两根**连 C910 都没有、我们必须新造**的字段，别指望照抄：

  * **pc**：C910 的表项里**不存 pc** —— 它靠 IU 里的一条 PC FIFO，退休时按序弹出
    （ct_rtu_rob.v:355 `iu_rtu_pcfifo_pop0_data[47:0]`、:294 的
    `rtu_iu_rob_read*_pcfifo_vld`），所以它的 40 位 create 总线里没有 pc。
    而我们的 RTU 是**每条表项存 pc**（RTU_define.vh 的 `RTU_E_PC 120:89`，D8）。
    ⇒ `disp*_pc` 必须由 IDU 在派遣当拍送出来（IDU 内部有，见下表），
      或者改成 C910 那种 pcfifo 路线（那是改 RTU 的表项，不是加端口）。
  * **chk**：见 (2)。

(2) chk 旁路：**3 × 25 = 75 根新增端口** ------------------------------------

  idu_rtu_disp{k}_chk[24:0]

  作用：前端在取指时打包的预测快照（GHR/BTB/TAGE 那一套），RTU 存进 ROB 表项，
  退休时用它去训练预测器 —— 这样"写哪一格"与退休时的预测器状态无关。

  ⚠️⚠️ **10-08 更新：这一条的负担已经大幅降级，原来的判断作废。**
  原先写的是"IDU 完全没有这条路 ⇒ 要加输入口 + 随指令锁存 + 派遣点引出"三步。
  同事在 cbcbd18 "idu chk" 里把**前两步做了**：

    (a) **顶层输入口已加**：`ifu_idu_if_inst0/1/2_chk[24:0]`
        （ct_idu_top.sv:15/17/19），三路齐全。
        ifu2 侧本来就有对应的旁路输出（rv32ifu2_top.v:204/207/210
        的 `idu_inst0/1/2_chk[24:0]`）⇒ **IFU 侧不用改，接上即可**。
    (b) **随指令锁存已做**：chk 跟着指令走完 IF → ID → IR → IS 全程 ——
        顶层有 dp_id_pipedown_inst*_chk / dp_ir_inst*_chk，
        `ct_idu_is_pipe_entry` 里存成 `entry_chk`（:101-118），
        在 IS 级读出侧就是 `is_inst{k}_read_chk`（ct_idu_is_dp.sv:215-217）。

  ⇒ **只剩第三步：把 IS 读出侧的 chk 引到顶层给 RTU。** 不用再动流水线。

  ⚠️ 但有个坑要当心：同一次提交还给 BIQ 加了个出口 `idu_biq_chk[24:0]`
     （ct_idu_top.sv:170），它的源头是 `is_biq_create0/1_chk`
     （ct_idu_is_dp.sv:465-493）—— **只有 2 路**（BIQ 是 2 个 create 口）。
     RTU 要的是 **3 路**（派遣组里任意一路都可能是分支）⇒ **别直接抄 BIQ 那两路**，
     要按 is_inst{k}_read_chk 三路重取。

  ⚠️ 另：ifu2 那三根 chk 在现核 mycpu.v 里仍是**悬空**的（那是接旧 IDU 的顶层），
     接 C910 IDU 时三根要全部接上，别再留悬空。


(3) 位宽/路数要"改"而不是"加"的 -------------------------------------------------

  ⚠️ 2026-10-08 定案更正: **IDU 的 preg 位宽不改** —— 改由 RTU 提供 64 档
  (`make ... PREG=64`, 见 doc/rtu_preg_size_config_zh.md)。原来那一版计划
  ("IDU 扩到 96 / 7 位 + LSIQ 12 项") **作废**。64 档下 RTU 的池子就是 64 项,
  与 IDU 的 6 位 preg 天然同宽。

  项            IDU 现在       RTU         怎么接 (64 档)
  ------------  -----------    ----------  ----------------------------------
  preg 位宽     6 位           7 位        RTU 端口**保持 7 位不变** (取两档最大),
                                          64 档下最高位恒 `0` ⇒ 适配层切 `[5:0]`

                                          适配层要逐槽重排 (32 个 7→6 的切片)。

                                          ⚠️ **定案更正（2026-10-08，用户拍板）**：
                                          原来写的"释放的所有权在 RTU ⇒ 可丢弃"
                                          **是错的**。这根线是**寿命**信息，不是寻址风格

                                          (lsu_st_da.sv:309 的 st_da_wb_cmplt_req 只看

                                          时，会把那条 store 还要读的物理号放回池子
                                          ⇒ 号被重分配 ⇒ store 读到别人的值（静默错数）。
                                          极性：**位 = 1 ⇒ 这个号还被引用着，不许回池**
                                          (名字里的 dealloc 读成"可以释放这些"正好相反)。

                                          ② 它只覆盖 SDIQ 的 src0（= store 数据），
                                          基址若在 SDIQ 弹出之后还会被重读则兜不住。

三、IDU 顶层端口表变更（2026-10-08, commit cbcbd18 "idu chk"）
    —— 与 RTU 无关，但**影响接线方和冒烟台**，接之前要知道
================================================================================

同一个提交里同事还动了两处顶层端口，都不在 RTU 这条边上，但会绊到接线：

---- 3.1 删了 3 根 ready，换成 1 根 accept_num ---------------------------------

  IDU 顶层**删掉**了 `idu_ifu_inst0/1/2_ready` 三个输出，**换成**
  `idu_accept_num[1:0]`（ct_idu_top.sv:20）。

  内部那三根 ready 还在（ct_idu_id_ctrl.sv:36-38），只是不再出顶层：
    inst0_ready = inst1_ready = !ctrl_id_pipedown_stall
    inst2_ready = !ctrl_id_pipedown_stall | !ctrl_xx_is_inst0_sel[0]
  顶层把它们压成（ct_idu_top.sv:180）：
    accept_num = {inst2_ready | inst0_ready, inst2_ready}

  编码核过了，**没有歧义、也没有 bug**：因为 inst0_ready 与 inst1_ready 恒相等，
  可达状态只有三个 —— 全停(0)、只收 1 条(inst2_ready=1)、收满 3 条，
  对应 2'b00 / 2'b01 / 2'b11。**2'b10（=2）不可达**（这正是 `|inst0_ready`
  那一项的用处：把"3 条"和"1 条"区分开）。

  语义 = **本拍从 IFU 收下几条（程序序前缀）**。

  ✅ **好消息：ifu2 早就有这个口** —— rv32ifu2_top.v:212 就是
     `input wire [1:0] idu_accept_num`（注释"同拍消费的前缀条数"，接到
     `pop_num`，:666）。所以这次改动是**把 IDU 对齐到 ifu2 的既有握手**，
     不是给我们新增负担；反而比原来的三根 ready 更好接。

---- 3.2 新增 chk 送 BIQ 的出口（别和 RTU 那路接混） ---------------------------

  `idu_biq_chk[24:0]`（ct_idu_top.sv:170）—— 把 chk 送到 BIQ（分支路径）。
  与 RTU 的 `disp{k}_chk` 是**两个不同的出口**，源头也不同：
    * BIQ 那路源头是 `is_biq_create0/1_chk`，**只有 2 路**；
    * RTU 要的是 `is_inst{k}_read_chk`，**3 路**。
  接的时候别图省事从 BIQ 那两路分叉。

---- 3.3 ⚠️ 冒烟台已过时，`make idu-unit` 现在会 elaborate 失败 ----------------

  `tb/unit/tb_idu_c910.sv` 的端口连接不是手写的，是
  `scripts/gen_idu_smoke_tb.py` 从 ct_idu_top.sv 的端口表**生成**的
  （脚本头注释里就写了"改了 IDU 顶层端口之后重跑本脚本即可 —— 忘了重跑，
  elaborate 会报 port not found，那正是这个冒烟台存在的意义"）。

  同事这次改了端口表但**没重跑生成器**。实测：
      $ python3 scripts/gen_idu_smoke_tb.py --check
      tb_idu_c910.sv 与 ct_idu_top.sv 端口表不一致 —— 需要重新生成
  现在那份 TB 里还连着已删除的 `idu_ifu_inst0/1/2_ready`（:82-84 / :256-258），
  且缺 `ifu_idu_if_inst0/1/2_chk` / `idu_accept_num` / `idu_biq_chk`。
  ⇒ **跑 `make idu-unit` 之前先重跑 `python3 scripts/gen_idu_smoke_tb.py`。**

四、LSU ↔ RTU 那边（只留指针，细节在对照表里）
================================================================================

本文只写 IDU 边。同一天 LSU 侧的接口变化写在 doc/rtu_接口对照表.csv / .xlsx
的「RTU↔LSU」表里（新增一节「访存异常」），要点三条：

  1. 新增 4 根：`lsu_rtu_wb_pipe3_expt_vld/_expt_addr[31:0]`（load）、
     `lsu_rtu_wb_pipe4_expt_vld/_expt_addr[31:0]`（store）。语义 = **地址非对齐**。
  2. **RTU 侧不用改口** —— 走现成的 `expt_vld/iid/cause/tval` 收集口即可：
     cause 按口给（pipe3→4 / pipe4→6），tval = `_expt_addr`，iid = 同拍 cmplt iid。
  3. 🔴 但适配层多两条硬约束（下面 4.1 / 4.2）。

---- 4.1 两源同拍 ⇒ 必须先比 iid 取最旧 ----------------------------------------

  丢错一条的后果是**年长那条的异常永久丢失**（它会按正常流程退休走掉，
  且不会被重取 —— 冲刷只冲比 trap 那条更年轻的）—— 而 RTU 的 `RTU_expt.v`
  只能跟"**已经收下的**"比年龄（它手里最多只有一条），
  所以这个比较只能在适配层做（或把 RTU 的异常口加宽到 2 路）。
  用 `RTU_iid_cmp` 同款模比较即可。

---- 4.2 🔴 `expt_vld` 必须用 `cmplt` 门控 —— load 侧现在有个真 bug ---------------

  ⚠️ **`lsu_ld_wb.sv:165-175` 新加的那段 always 缺 begin/end**：

      always @(posedge forever_cpuclk or negedge cpurst_b)
      begin
        if (!cpurst_b)
          ld_wb_iid[6:0]        <=  7'b0;      ← 只有这一句在 if 里
          ld_wb_expt            <=  1'b0;      ← 无条件
          ld_wb_expt_addr       <=  32'b0;     ← 无条件
        else if(ld_wb_pre_inst_vld)
          ld_wb_iid[6:0]        <=  ld_wb_pre_iid[6:0];   ← 只有这一句在 else-if 里
          ld_wb_expt            <=  ld_wb_pre_expt_vld;   ← 无条件
          ld_wb_expt_addr       <=  ld_da_wb_expt_addr;   ← 无条件
      end

  于是 `ld_wb_expt` / `ld_wb_expt_addr` 成了 `ld_wb_pre_expt_vld` /
  `ld_da_wb_expt_addr` 的**无条件一拍延迟**（同一 always 里对同一变量的最后一次
  非阻塞赋值胜出 —— 复位那拍也会被覆盖，只是 `ld_da_expt` 同时被复位、实际值仍为 0，
  属侥幸）。而导出的 cmplt `lsu_rtu_wb_pipe3_cmplt = ld_wb_inst_vld` 是**有门控**的
  （:152-162：置位要 `ld_wb_pre_inst_vld`，且 `rtu_yy_xx_flush` 那拍清零）。

  ⇒ **会出现 `expt_vld = 1` 而 `cmplt = 0` 的拍。而那一拍的 `lsu_rtu_wb_pipe3_iid`
     是残留值**（上一条 load 的、或 0）。真会碰上的两种情形：

    ① 冲刷那拍：cmplt 被 `rtu_yy_xx_flush` 清掉，expt 没有清的口；
    ② `ld_da_wb_cmplt_req = ld_da_inst_vld && !ld_da_secd`（lsu_ld_da.sv:515）
       而 `ld_da_wb_expt_vld = ld_da_expt`（:516）是**裸**的 —— `ld_da_expt`
       只在复位与 `ld_dc_da_inst_vld` 时更新（:268/:292），**没有冲刷清零**，
       而 `ld_da_inst_vld` 有 ⇒ 两根脱节。

  ⚠️ 后果是**静默的**（不报 x、不报 z）：若消费方拿裸的 `expt_vld` 去报异常，
    就会**按错误的 iid 报异常**；RTU 把它收进单表项并一直挂到那条 iid 退休
    ⇒ 冤枉一条无辜指令陷入、或静默掐掉它的退休。**只有 difftest 能抓。**

  ⇒ 契约（写进适配层）：**`expt_vld` 必须与同口的 `cmplt` 相与之后再送进 RTU**，
     iid / tval 也按这一拍取样。这不是"保险"，是**必须**。
  ⇒ 顺手请同事补上那段 begin/end —— **store 侧 `lsu_st_wb.sv:59-74` 写法是对的**
     （`begin/end` + 用 `st_wb_pre_inst_vld` 门控），照着改即可。

  ✅ 好消息：store 侧**没有**这个相位问题（begin/end 齐、门控齐），
     但 4.2 的"与 cmplt 相与"对两个口一视同仁，写成一条规矩更省心。
