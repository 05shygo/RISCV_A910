# ifu2 — 自研 2 级 3 发射取指单元

2026-09-25。入口 `rtl/rv32ifu2_top.v`，6 个文件 **1,251 行**。
对照：`mySoC/ifu_rv32i`（C910 派生，3 级）41 文件 **14,967 行**；
`RISCV_CPU/cpu` 那个乱序核的整个前端 1,354 行。

`make run TEST=x IFU=2` 选用；`IFU=1` 仍是原树，`IFU=0` 是更早的 PC/NPC/IROM 通路。

## 1. 实测结果（同一二进制，逐拍 difftest 全过）

### CoreMark 正式跑分（ITERATIONS=30，`GM_MONITOR=1`，全部 "Correct operation validated"）

score = ITERATIONS × 10⁶ / Total ticks（1 周期 = 1 µs，归一到 1 MHz ⇒ 与 CoreMark/MHz 同值）

| 配置 | Total ticks | **Score** | vs 五级 | vs IFU=1 |
|---|---:|---:|---:|---:|
| IFU=0 五级流水（无 IFU） | 13,221,118 | 2.269 | — | +4.2% |
| IFU=1（C910 派生）@ i-cache 1 KB | 13,781,723 | **2.177** | **−4.1%** | — |
| **IFU=2 @ i-cache 1 KB** | 11,387,824 | **2.634** | **+16.1%** | **+21.0%** |
| IFU=2 @ i-cache 64 KB | 11,353,676 | **2.642** | +16.4% | +21.4% |

> ⚠️ **本表的周期数停在 `5707cab`,没跟上 `1ae4705`(GHR 默认 12→8)。**
> 2026-09-26 在 HEAD(换真实 RAM 之前)重测:IFU=2 @ 1 KB 是
> `Total ticks 11,328,179` / score **2.648** / `cycles 11,362,153`。
> **不变量(seedcrc / crcfinal / 退休条数 9,233,680)仍逐位一致** —— 变的只是

> 引数当验收标准前先按当前 HEAD 重测一遍,别直接抄本表。

**两条要点**：
1. **IFU=1 在当前 Makefile 默认配置（1 KB + 5,372 bit 预测器）下比"完全没有 IFU"还慢 4.1%。**
   这就是"复杂度换不来性能"的量化版本：3 级流水 + 初始化 + IPB 那一套的固定开销，
   盖过了方向预测精度带来的收益。
2. **IFU=2 基本不挑缓存容量**（1 KB 2.634 vs 64 KB 2.642，差 0.3%）。所以它赢的不是缓存。

## 2. 流水

```
F0  next_pc ─┬─→ i-cache 阵列寻址 (set = pc[8:4], 同步读, 真实 RAM)
             ├─→ 块 BTB (行 = 16 B 块 × 4 slot, 同步读)
             └─→ gshare 方向表 (同一块索引 ⊕ GHR, 同步读)
                    │
F1  q_pc/q_data ─→ tag 比较 → 对齐 ≤3 条 → 截断于第一个预测 taken → IBUF → IDU
     q_hit / slot_vld / slot_taken ─┘
```

**全设计只有一份 PC 寄存器**，在 `u_icache` 内部（`q_pc_q`）。顶层组合地算
"下一个取指地址"喂给阵列，下一拍它就是 `q_pc`。这不是省事，是**唯一不会重复取指
的写法**：若顶层另存一个 `pc_q` 再寄一份给 F1 用，一旦取指停顿，延迟的那份会把
同一个地址连看两拍，同一条指令被推进 IBUF 两次（difftest 报重复提交）。
把阵列地址定义成"下一个地址"、`q_pc` 定义成"它的寄存值"之后，数据与 PC 天然对齐，
停顿只是原地重看同一拍数据。

所有表都按**取指块**（16 B）索引，一次查表覆盖整块 4 个 slot —— 这是 2 级能成立的
前提：预测必须在指令译码**之前**就绪。

### i-cache 的阵列是真实 RAM（2026-09-26）

原来 tag/data 是裸 `reg` 阵列，上 FPGA 会烂成触发器。现在是 4 片 `rv32ifu2_spram`：

```
u_tag_way0 / u_tag_way1   32 × 23    ← 只有 tag，valid 不在这里
u_dat_way0 / u_dat_way1   32 × 128
```

三条设计决定，都是有原因的，改之前先读 `rtl/rv32ifu2_icache.v` 与
`rtl/rv32ifu2_spram.v` 的头注释：

1. **必须是 1R1W（简单双口），不能照抄 C910 的 1RW。** 查找读每拍都要发，而读地址
   （`next_pc[8:4]`，顶层组合算出来的）与写地址（`refill_pc[8:4]`）是**两个独立来源**
   —— redirect 与 `refill_en` 同拍时能落在毫无关系的 set 上。1RW 只能丢掉读，丢掉
   那拍 F1 就没数据了，正好是"重定向进 PC 零气泡"那条快路上的气泡。C910 敢用 1RW
   是因为它用 `trans_busy_q` 给**整个**回填事务插了气泡；ifu2 没有气泡可花。
2. **读口必须写穿透。** 回填那拍发的读很可能与写同址（PC 被冻在缺行上，块内偏移 0
   时前进量一定还在同一 16 B 行内 ⇒ 同一个 set）。没有写穿透，每次 miss 都要多花
   一拍并多发一次 BIU 事务。实测把写穿透去掉，`addi` 的 `BIU read txn` 从 45 涨到
   83（+84%）、拍数 308 → 362。
3. **valid 就放在 tag 行里**（行 = `{valid, tag}`，24 位，C910 结构），不另设
   valid 触发器。命中路径直接用阵列的寄存 Q，于是 valid 与 tag **不可能各说各话**
   —— 这一点有实测价值：把写穿透弄丢时，旧结构（valid 在触发器、tag 在阵列）会
   出现"valid=1 但 tag 是旧的"⇒ **假命中并交付 X**；现在两者一起从同一行读出来，
   陈旧读只能是 "valid=0" 的干净缺失，失效模式从"交付错指令"降级成"多几次回填"。
   牺牲路要的那两个 valid 位靠**捕获**（下一段），不靠第二个读口。

### 牺牲路那两个 valid 位是怎么来的（`valid_q` 捕获）

C910 能把 way 提前两级算好（`fifo → victim_q → trans_way_q`），靠的是它给整个回填
事务插了气泡。ifu2 没有气泡可花，牺牲路必须在 `refill_en` 那一拍就绪 —— 而**唯一的
读口那一拍正被查找读占用**。解法是**捕获**，靠一条构造性恒等：

```
q_set_q(k) = rd_set(k-1) = rd_addr(k-1)[8:4] = q_pc_q(k)[8:4]
refill_pc[8:4] = "事务开始时 q_pc 所在 set" = rf_set
```

于是**只要 `q_set_q == rf_set`，那一拍阵列 Q 里装的就是 `rf_set` 那一行**，抓进
`valid_q` 即可。捕获条件写成 `q_set_q == rf_set` 正是为了把这件事变成构造性事实，
与 BIU 快慢、与 redirect 都无关。

⚠️ 写成"miss 期间每拍都抓"是**错的**：一旦 BIU 变慢（`rv32ifu2_refill` 明确支持任意
延迟，FSM 会停在 `S_WAIT`）或期间来一次 `redirect`，`rd_set` 就变成别的行，抓到的是
别的 set 的 valid —— 不会交付错指令，但会按错的 valid 挑牺牲路，表现为罕见的周期
漂移，短用例抓不到。

⚠️ **`victim_way` 是 one-hot，不是编号**。回填后把 LRU 指向另一路时，对应的是
`victim_way[0]`（way0 是牺牲者 ⇒ 指向 way1 ⇒ lru 置 1），**不是** `~victim_way[0]`。
基线那句 `lru_q[rf_set] <= ~rf_way` 里的 `rf_way` 是**编号**，所以那边才取反 ——
照抄符号会得到正好相反的替换策略。实测：2 路里明明有一路无效却去挤有效那路，
CoreMark 上 `BIU read txn` 从 95,164 掉到 92,138、拍数反而 +194，而 difftest 与
三个 CRC 全过（**功能对、只有时序错**，是最难发现的那类）。

配套事实：**初始化扫描仍是 32 拍**（tag RAM 的写口被扫描借用，C910 式 sweep）。
它藏在 BTB 的 64 拍扫描下面，所以总拍数里看不见 —— 保持 32 是因为免费，不是因为
可观测。`btb`/`bht`/`ras`/`ibuf` 本次**不动**：它们的训练路径是组合读 + 同拍回写
同址，同步 RAM 做不了单拍 RMW；而"组合读 + 同步写"正好是 FPGA 分布式 RAM 的推断
模板，本来就落不成触发器。

改动验收（与换之前逐位一致）：`addi` 308；`branch_bench` 161,496 拍 + 五类准确率
全同；CoreMark `Total ticks 11,328,179` / `seedcrc 0xe9f5` / `crcfinal 0xf8b3` /
`retired inst 9,233,680` / `BIU read txn 95,164`；47 个用例 difftest 全过。

## 3. 相对 C910 版少掉的复杂度（不是少掉的功能）

| 删掉的东西 | 原行数 | 为什么能删 |
|---|---:|---|
| LBUF + entry | 1,757 | **在原顶层里本来就是死码**（`rv32_ifu_pipeline.v:239` 把 `cp0_ifu_lbuf_en` 接 1'b0，输出全悬空） |
| 间接 BTB + 阵列 | 661 | 实测 **0 %/Kbit**（256→4 行 ticks 逐位相同） |
| i-cache 独立封装 `icache_top` | 821 | 原顶层从不例化它 |
| SFP | 119 | SoC 里 `cp0_ifu_nsfe` 接 0 |
| PCFIFO credit/token、IP fragment、prefix 切分 | — | 见下 |
| way 预测状态、错 way 重发、首次受阻保存 | — | 两路并行读 + tag 比较后 mux |
| debug / vector / 多区域 / 断点 / precode 阵列 | — | 本 SoC 用不到 |

**"取指包"这个概念被取消了。** C910 要求凑出对齐的指令前缀，于是有 fragment /
prefix / PCFIFO 拆分一整套状态机。这里 F1 **逐 lane 交付 1~3 条**（每条独立 valid），
参差不齐由 IBUF 吸收，消费侧只看队列深度。于是那套机制整体消失。

**way 预测也没了。** 2 KB 的容量下多读一路数据，比维护"预测了哪一路 / 错了怎么重发 /
首次受阻怎么保存"那套状态机便宜得多。

## 4. 分支预测

* **块 BTB**（`rv32ifu2_btb.v`，64 行 × 4 slot：数据 8,704 + 标签 1,472 = 10,176 bit）：只管"有哪些控制转移、
  目标在哪、什么类型"。**不存方向**（方向本来就是 gshare 的活，两处各存一份必然后悔）。
* **gshare 方向表**（`rv32ifu2_bht.v`，512 行 × 4 slot × 2 bit = 4,096 bit）：`idx = pc[12:4] ^ fold(GHR)`。
  索引**只有一个公式，读和写都调它**。
* **RAS**（`rv32ifu2_ras.v`，8 项，`BP_RAS` 开关，**默认关**）：ret 的目标问栈顶，
  不问 BTB。实测见下表 —— 它对 jalr 密集的用例是大赢，对 CoreMark 是小亏。
* 训练回送走 `iu_btb_*`（条件分支 / JAL / JALR **全覆盖**）——原设计只回送条件分支，
  jalr 的目标学习完全缺失。

### 两条用血换来的规矩

1. **索引只能有一个公式。** 原设计类 3 卡在 50% 的最终病因是"读索引与写索引的
   GHR 位窗不一致"（读侧 plane 来自重读选择阵列、offset 用实时 `vghr_q`；写侧用
   随包锁存值），结果类 3 读到的 21 个地址**整个仿真收到 0 次写**。这里 GHR 快照
   随指令走完全程（`chk` 字段），读写必然同址。

2. **GHR 快照必须是"块首 GHR"，三条 lane 相同。** 表按块索引，预测时用的是块首
   GHR；写入若改用"该分支自己之前"的 GHR，同一个 slot 的读写就落到不同的行 ——
   那正是上面那条病。块内第 2、3 条分支靠**不同的 slot 位**区分，不靠不同的 GHR。

### 面积-准确率（`branch_bench +BENCH` / CoreMark 同镜像）

面积 = 块 BTB 数据（行×4×**16**）+ 块 BTB 标签（行×(15-ROW_AW-4+2)）
     + gshare（行×8）+ RAS（8×32 + 8 + 4）+ GHR（12）

### Tier 1：位宽压缩（2026-09-25 已做，行为逐位不变）

删掉"恒为 0 的位"，不改任何索引或判断逻辑：

| 原来 | 位宽 | 现在 | 依据 |
|---|---:|---|---|
| `target[31:2]` | 30 → **14** | `target[15:2]` | 取指地址上界 64 KB（`ADDR_IN_MAP`）⇒ `target[31:16]` 恒 0 |
| 行标签 `pc[31:10]` | 22 → **6** | `pc[15:10]` | 同上 |
| `{cond, jal, jalr}` | 3 → **1** | `is_cond` | 消费侧只用 `slot_jmp = jal \| jalr`，两 bit 的区别**从没被用过** |

**14,552 → 8,920 bit（RTL 原样，−38.7%）；`BP_RAS=0` 综合剪掉 RAS 的 stk/evld 后
8,656 bit（−40.5%）。** 块 BTB 行宽 136 → 64 位，标签 23 → 7 位/行；gshare 不变。

验证（逐位对齐压缩前）：`branch_bench` 161,528 / 95.00% / 类3 87.15%；`addi` 308；
46 个非 coremark 用例全过；CoreMark `Total ticks` 11,387,824、`seedcrc 0xe9f5` /
`[0]crcfinal 0xf8b3`、score 2.634。

⚠️ **代价**：tag 只到 `pc[15]`，把 IFU 更紧地绑死在 64 KB 地址空间上。一旦 PC 超过
0xFFFF，被丢掉的高位会让**不同 PC 假命中同一行**（拿到别人的目标）——比取到垃圾更危险。
扩地址空间时 `TAG_HI` 必须跟着放宽。（ifu2 本来就没有 region 检查，这个假设已隐含存在，
但压缩把它从"取垃圾"变成了"假命中"。）

⚠️ **标签阵列必须计入**：`rv32ifu2_btb.v` 除了 136 位/行的数据行，还有一张
`tag_q`（`TAG_BITS+1` 位/行，含行 valid）。漏掉它会少算 1.5~3 Kbit ——
本文档早先的 13,056 就是这么来的，已更正。

| BTB 行 | BHT 行 | 面积 bit | branch_bench | 准确率 | CoreMark(ITER=2 周期) |
|---:|---:|---:|---:|---:|---:|
| 16 | 128 | 2,472 | 177,126 | 86.71% | 824,612 |
| 32 | 256 | 4,632 | 162,912 | 91.08% | 813,540 |
| **64** | **512** | **8,920** | **161,528** | **95.00%** | **792,369** |
| 128 | 1024 | 17,432 | 157,154 | 95.31% | 791,955 |

（上表面积是 **Tier 1 位宽压缩之后**的数；压缩前对应 3,880 / 7,448 / 14,552 / 28,696。
扫点是拿**旧位宽**跑的，但压缩逐位不改行为，所以周期数一列仍然成立。）

（表中 branch_bench 一列全部是 `BP_RAS=0` 即默认配置。早先这一列把基准行写成了
157,440 —— 那是 `BP_RAS=1` 的数，已更正为 161,528。）

（当前默认配置 = 第 3 行。`BP_RAS=0` 时 RAS 的 `stk`/`evld` 共 264 bit 无消费者，
综合可剪；`sp_q` 仍活着（它进 chk 快照），所以实际约 **14,288 bit**。）

* ⚠️ **两个基准的饱和点不一致，别只报一个**：CoreMark 上 64 行已饱和
  （14.55→28.7 Kbit 只快 0.05%）；但 branch_bench 上 128 行仍再快 2.7%
  （161,528 → 157,154）。定向基准的分支密度远高于真实负载，所以它更吃表容量。
  **以 CoreMark 为准 ⇒ 14.55 Kbit 是这个工作负载上的合理落点。**
* 砍到 7.5 Kbit 要付 +2.7%（CoreMark），砍到 3.9 Kbit 付 +4.1%。
* **对照有价值的旧点**：原设计 5,372 bit 的配置在 branch_bench 上是 179,761 拍；
  这里 **3,884 bit 就已经 177,126 拍** —— 面积更小、还更快。这就是"掺 PC"的价值。

### RAS：一个必须如实分开报的部件

| | RAS=0（默认） | RAS=1 |
|---|---:|---:|
| branch_bench 周期 | 161,528 | **157,440**（−2.5%） |
| jal/jalr 误预测 | 2,056 / 4,611 | **12 / 4,611** |
| 条件分支误预测 | 2,864 | 2,864（不受影响） |
| CoreMark 周期 | **792,369** | 794,371（**+0.25%**） |

jal/jalr 误预测被清掉 99.4%，但 CoreMark 反而略慢 —— 说明 **CoreMark 里 ret 的调用
深度基本稳定，BTB 本来就记得住**，RAS 的推测栈在这类代码上没有额外信息，只多了
"误预测后栈内容不可信"的干扰。所以默认关，需要 jalr 密集场景时 `BP_RAS=1` 打开。

（补记：只恢复栈指针不恢复内容时 CoreMark 是 +1.25%（802,266）；给每格加 valid 位、
恢复时把高于恢复点的格子作废之后降到 +0.25%。这一步是有效的，但仍不足以翻正。）

## 5. 踩过的坑（都在 RTL 注释里就地记了）

1. **`2'd4 - 0` 在 2 位里是 0**：`blk_left` 写成 2 位时"本块剩 4 条"溢出成 0，
   `want_push` 恒为 0，整个前端一条指令都发不出去。要用 3 位。
2. **`{a,b,c,d}` 是高位在前**：`bht_taken` 用 `{ctr[1],ctr[3],ctr[5],ctr[7]}` 拼，
   四个 slot 的方向整体倒过来（谁读谁的邻居）。症状是类 1 从 96% 掉到 4.5%，
   而表里看得见非零行 —— 极易误判成"写没落对地方"。
3. **BTB 里不能存 X 目标**：一条"从没跳过"的条件分支被分配时，若旧目标字段是 X
   （寄存器阵列上电为 X，初始化扫描只清 tag 的 valid 位），就会以 valid=1 + X 目标
   进表；之后 BHT 一旦把它预测成 taken，`next_pc` 变 X，整条前端崩掉。
   症状是 CoreMark 跑到 5 万多拍突然 PC 全 X，而所有短用例都测不出来。
   现在"旧字段不可信时一律填 0"。
4. **lane 的 PC 不能重复加块内偏移**：`q_pc` 本身就是"本拍第一条要交付的指令的
   PC"，偏移已经含在里面。数据用 `pc_ofs` 索引（对）、标签再加一次 `pc_ofs`（错），
   表现像"跳过若干条指令"。
5. **寄存器阵列必须扫描初始化**：`X & 0` 在 `if` 条件里是假，但 `X & 0` 在
   **赋值**里是 0 —— 而 `valid & (tag == …)` 在 valid 为 X 时结果是 **X 不是 0**，
   会一路传到 `next_pc`。所以别指望"valid 位自己会拦"。
6. **扫点前先确认配置真的落地**：`ICACHE_BYTES` 一类 define 若没接进 parameter，
   扫出来的"不同配置"其实是同一个配置（原树整张容量表就是这么废掉的）。
   现在 icache 会打印 `[IFU2-ICACHE] BYTES=… SETS=…`，扫点前先看这一行。
7. **`meminit.bin` 软链**：DUT 走编译期 `+define+PATH`，tb 参考模型按相对路径读
   `meminit.bin`，两者必须是同一个镜像。并行跑不同用例时忘了同步，症状是**第
   57 拍就 difftest 失配**，看起来像 RTL 坏了。本轮又踩了两次 —— 并行跑之前
   先把仓库根的 `meminit.bin` 也指到同一个镜像。

## 6. 已知边界

* **每块只预测一次控制转移。** 块内第二条条件分支若方向没预测对，走 EX 重定向兜底。
* **误预测恢复的 GHR 是近似的**：按"块首快照 + 本次真实方向"恢复，块内第 2/3 条
  分支时丢掉了同块更靠前那几条的结局。只影响预测质量，不影响正确性。
* **陷阱（RTU）时 GHR 直接清零**，不做精确恢复 —— 陷阱稀少，代价是其后一小段
  预测质量。
* **RAS 默认关**（见上表），它在本项目的两个基准上方向相反。
* **没有下一行预取**。原树 IPB 预取是"小容量缓存还能用"的关键；这里没做，
  1 KB→2 KB 只值 0.2% 说明当前工作集对容量不敏感，但没有验证过更大的工作集。
* **每块只预测一次控制转移**、**GHR 恢复是近似的**、**陷阱时 GHR 清零**：见上。
* 输入约定：`idu_accept_num` 不得超过当拍有效 lane 数（核心侧已保证）。
