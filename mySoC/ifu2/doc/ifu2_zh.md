# ifu2 — 自研 2 级 3 发射取指单元

2026-09-25。入口 `rtl/rv32ifu2_top.v`，6 个文件 **1,251 行**。
对照：`mySoC/ifu_rv32i`（C910 派生，3 级）41 文件 **14,967 行**；
`RISCV_CPU/cpu` 那个乱序核的整个前端 1,354 行。

`make run TEST=x IFU=2` 选用；`IFU=1` 仍是原树，`IFU=0` 是更早的 PC/NPC/IROM 通路。

## 1. 实测结果（同一二进制，逐拍 difftest 全过）

> ⚠️ **2026-09-29：本节所有 CoreMark 数字都是旧工具链（Xuantie GCC 10.4.0）跑的。**
> 现在构建系统已统一到 **GCC 14.2.0**，同一份源码同一个核 CoreMark 从
> **2.584 → 2.694（+4.25%）**，收益全在分支行为上（误预测 366,940 → 167,188，砍 54%；
> 控制转移少 8.1%；IPC 0.795 → 0.847）。**下面表里的绝对值要整体加约 4.25% 才是新基线。**
> 相对结论（IFU=2 比 IFU=1 快多少）不受影响 —— 换编译器只减误预测，不改前端形态。
> 详见 `coremark/README_COREMARK.md` 与 memory `gcc14-on-our-core`。

1. **IFU=1 在当前 Makefile 默认配置（1 KB + 5,372 bit 预测器）下比"完全没有 IFU"还慢 4.1%。**

## 2. 流水

```
F0  next_pc ─┬─→ i-cache 阵列寻址 (set = pc[8:4], 同步读, 真实 RAM)
             ├─→ 块 BTB (行 = 16 B 块 × 4 slot, 同步读)
             └─→ gshare 方向表 (同一块索引 ⊕ GHR, 同步读)
                    │
F1  q_pc/q_data ─→ tag 比较 → 对齐 ≤3 条 → 截断于第一个预测 taken → IBUF → IDU
     q_hit / slot_vld / slot_taken ─┘
```

**全设计只有一份 PC 寄存器**，在 `u_icache` 内部（`q_pc_q`）。顶层组合地算
"下一个取指地址"喂给阵列，下一拍它就是 `q_pc`。这不是省事，是**唯一不会重复取指
的写法**：若顶层另存一个 `pc_q` 再寄一份给 F1 用，一旦取指停顿，延迟的那份会把
同一个地址连看两拍，同一条指令被推进 IBUF 两次（difftest 报重复提交）。
把阵列地址定义成"下一个地址"、`q_pc` 定义成"它的寄存值"之后，数据与 PC 天然对齐，
停顿只是原地重看同一拍数据。

所有表都按**取指块**（16 B）索引，一次查表覆盖整块 4 个 slot —— 这是 2 级能成立的
前提：预测必须在指令译码**之前**就绪。

### i-cache 的阵列是真实 RAM（2026-09-26）

原来 tag/data 是裸 `reg` 阵列，上 FPGA 会烂成触发器。现在是 4 片 `rv32ifu2_spram`：

```
u_tag_way0 / u_tag_way1   32 × 23    ← 只有 tag，valid 不在这里
u_dat_way0 / u_dat_way1   32 × 128
```

三条设计决定，都是有原因的，改之前先读 `rtl/rv32ifu2_icache.v` 与
`rtl/rv32ifu2_spram.v` 的头注释：

1. **必须是 1R1W（简单双口），不能照抄 C910 的 1RW。** 查找读每拍都要发，而读地址
   （`next_pc[8:4]`，顶层组合算出来的）与写地址（`refill_pc[8:4]`）是**两个独立来源**
   —— redirect 与 `refill_en` 同拍时能落在毫无关系的 set 上。1RW 只能丢掉读，丢掉
   那拍 F1 就没数据了，正好是"重定向进 PC 零气泡"那条快路上的气泡。C910 敢用 1RW
   是因为它用 `trans_busy_q` 给**整个**回填事务插了气泡；ifu2 没有气泡可花。
2. **读口必须写穿透。** 回填那拍发的读很可能与写同址（PC 被冻在缺行上，块内偏移 0
   时前进量一定还在同一 16 B 行内 ⇒ 同一个 set）。没有写穿透，每次 miss 都要多花
   一拍并多发一次 BIU 事务。实测把写穿透去掉，`addi` 的 `BIU read txn` 从 45 涨到
   83（+84%）、拍数 308 → 362。
3. **valid 就放在 tag 行里**（行 = `{valid, tag}`，24 位，C910 结构），不另设
   valid 触发器。命中路径直接用阵列的寄存 Q，于是 valid 与 tag **不可能各说各话**
   —— 这一点有实测价值：把写穿透弄丢时，旧结构（valid 在触发器、tag 在阵列）会
   出现"valid=1 但 tag 是旧的"⇒ **假命中并交付 X**；现在两者一起从同一行读出来，
   陈旧读只能是 "valid=0" 的干净缺失，失效模式从"交付错指令"降级成"多几次回填"。
   牺牲路要的那两个 valid 位靠**捕获**（下一段），不靠第二个读口。

### 牺牲路那两个 valid 位是怎么来的（`valid_q` 捕获）

C910 能把 way 提前两级算好（`fifo → victim_q → trans_way_q`），靠的是它给整个回填
事务插了气泡。ifu2 没有气泡可花，牺牲路必须在 `refill_en` 那一拍就绪 —— 而**唯一的
读口那一拍正被查找读占用**。解法是**捕获**，靠一条构造性恒等：

```
q_set_q(k) = rd_set(k-1) = rd_addr(k-1)[8:4] = q_pc_q(k)[8:4]
refill_pc[8:4] = "事务开始时 q_pc 所在 set" = rf_set
```

于是**只要 `q_set_q == rf_set`，那一拍阵列 Q 里装的就是 `rf_set` 那一行**，抓进
`valid_q` 即可。捕获条件写成 `q_set_q == rf_set` 正是为了把这件事变成构造性事实，
与 BIU 快慢、与 redirect 都无关。

⚠️ 写成"miss 期间每拍都抓"是**错的**：一旦 BIU 变慢（`rv32ifu2_refill` 明确支持任意
延迟，FSM 会停在 `S_WAIT`）或期间来一次 `redirect`，`rd_set` 就变成别的行，抓到的是
别的 set 的 valid —— 不会交付错指令，但会按错的 valid 挑牺牲路，表现为罕见的周期
漂移，短用例抓不到。

⚠️ **`victim_way` 是 one-hot，不是编号**。回填后把 LRU 指向另一路时，对应的是
`victim_way[0]`（way0 是牺牲者 ⇒ 指向 way1 ⇒ lru 置 1），**不是** `~victim_way[0]`。
基线那句 `lru_q[rf_set] <= ~rf_way` 里的 `rf_way` 是**编号**，所以那边才取反 ——
照抄符号会得到正好相反的替换策略。实测：2 路里明明有一路无效却去挤有效那路，
CoreMark 上 `BIU read txn` 从 95,164 掉到 92,138、拍数反而 +194，而 difftest 与
三个 CRC 全过（**功能对、只有时序错**，是最难发现的那类）。

配套事实：**初始化扫描仍是 32 拍**（tag RAM 的写口被扫描借用，C910 式 sweep）。
它藏在 BTB 的 64 拍扫描下面，所以总拍数里看不见 —— 保持 32 是因为免费，不是因为
可观测。`btb`/`bht`/`ras`/`ibuf` 本次**不动**：它们的训练路径是组合读 + 同拍回写
同址，同步 RAM 做不了单拍 RMW；而"组合读 + 同步写"正好是 FPGA 分布式 RAM 的推断
模板，本来就落不成触发器。

改动验收（与换之前逐位一致）：`addi` 308；`branch_bench` 161,496 拍 + 五类准确率
全同；CoreMark `Total ticks 11,328,179` / `seedcrc 0xe9f5` / `crcfinal 0xf8b3` /
`retired inst 9,233,680` / `BIU read txn 95,164`；47 个用例 difftest 全过。

## 3. 相对 C910 版少掉的复杂度（不是少掉的功能）

| 删掉的东西 | 原行数 | 为什么能删 |
|---|---:|---|
| LBUF + entry | 1,757 | **在原顶层里本来就是死码**（`rv32_ifu_pipeline.v:239` 把 `cp0_ifu_lbuf_en` 接 1'b0，输出全悬空） |
| 间接 BTB + 阵列 | 661 | 实测 **0 %/Kbit**（256→4 行 ticks 逐位相同） |
| i-cache 独立封装 `icache_top` | 821 | 原顶层从不例化它 |
| SFP | 119 | SoC 里 `cp0_ifu_nsfe` 接 0 |
| PCFIFO credit/token、IP fragment、prefix 切分 | — | 见下 |
| way 预测状态、错 way 重发、首次受阻保存 | — | 两路并行读 + tag 比较后 mux |
| debug / vector / 多区域 / 断点 / precode 阵列 | — | 本 SoC 用不到 |

**"取指包"这个概念被取消了。** C910 要求凑出对齐的指令前缀，于是有 fragment /
prefix / PCFIFO 拆分一整套状态机。这里 F1 **逐 lane 交付 1~3 条**（每条独立 valid），
参差不齐由 IBUF 吸收，消费侧只看队列深度。于是那套机制整体消失。

**way 预测也没了。** 2 KB 的容量下多读一路数据，比维护"预测了哪一路 / 错了怎么重发 /
首次受阻怎么保存"那套状态机便宜得多。

## 4. 分支预测

* **块 BTB**（`rv32ifu2_btb.v`，64 行 × 4 slot：数据 8,704 + 标签 1,472 = 10,176 bit）：只管"有哪些控制转移、
  目标在哪、什么类型"。**不存方向**（方向本来就是 gshare 的活，两处各存一份必然后悔）。
* **gshare 方向表**（`rv32ifu2_bht.v`，512 行 × 4 slot × 2 bit = 4,096 bit）：`idx = pc[12:4] ^ fold(GHR)`。
  索引**只有一个公式，读和写都调它**。⚠️ `BP_PRED=0` 才走这条路；
  **2026-09-29 起重新是默认**（为 FPGA Fmax），见下一节末尾的"默认回切"说明。
* **RAS**（`rv32ifu2_ras.v`，8 项，`BP_RAS` 开关，**默认关**）：ret 的目标问栈顶，
  不问 BTB。实测见下表 —— 它对 jalr 密集的用例是大赢，对 CoreMark 是小亏。
* 训练回送走 `iu_btb_*`（条件分支 / JAL / JALR **全覆盖**）——原设计只回送条件分支，
  jalr 的目标学习完全缺失。

### 两条用血换来的规矩

1. **索引只能有一个公式。** 原设计类 3 卡在 50% 的最终病因是"读索引与写索引的
   GHR 位窗不一致"（读侧 plane 来自重读选择阵列、offset 用实时 `vghr_q`；写侧用
   随包锁存值），结果类 3 读到的 21 个地址**整个仿真收到 0 次写**。这里 GHR 快照
   随指令走完全程（`chk` 字段），读写必然同址。

2. **GHR 快照必须是"块首 GHR"，三条 lane 相同。** 表按块索引，预测时用的是块首
   GHR；写入若改用"该分支自己之前"的 GHR，同一个 slot 的读写就落到不同的行 ——
   那正是上面那条病。块内第 2、3 条分支靠**不同的 slot 位**区分，不靠不同的 GHR。

### 面积-准确率（`branch_bench +BENCH` / CoreMark 同镜像）

面积 = 块 BTB 数据（行×4×**16**）+ 块 BTB 标签（行×(15-ROW_AW-4+2)）
     + gshare（行×8）+ RAS（8×32 + 8 + 4）+ GHR（12）

### Tier 1：位宽压缩（2026-09-25 已做，行为逐位不变）

删掉"恒为 0 的位"，不改任何索引或判断逻辑：

| 原来 | 位宽 | 现在 | 依据 |
|---|---:|---|---|
| `target[31:2]` | 30 → **14** | `target[15:2]` | 取指地址上界 64 KB（`ADDR_IN_MAP`）⇒ `target[31:16]` 恒 0 |
| 行标签 `pc[31:10]` | 22 → **6** | `pc[15:10]` | 同上 |
| `{cond, jal, jalr}` | 3 → **1** | `is_cond` | 消费侧只用 `slot_jmp = jal \| jalr`，两 bit 的区别**从没被用过** |

**14,552 → 8,920 bit（RTL 原样，−38.7%）；`BP_RAS=0` 综合剪掉 RAS 的 stk/evld 后
8,656 bit（−40.5%）。** 块 BTB 行宽 136 → 64 位，标签 23 → 7 位/行；gshare 不变。

验证（逐位对齐压缩前）：`branch_bench` 161,528 / 95.00% / 类3 87.15%；`addi` 308；
46 个非 coremark 用例全过；CoreMark `Total ticks` 11,387,824、`seedcrc 0xe9f5` /
`[0]crcfinal 0xf8b3`、score 2.634。

⚠️ **代价**：tag 只到 `pc[15]`，把 IFU 更紧地绑死在 64 KB 地址空间上。一旦 PC 超过
0xFFFF，被丢掉的高位会让**不同 PC 假命中同一行**（拿到别人的目标）——比取到垃圾更危险。
扩地址空间时 `TAG_HI` 必须跟着放宽。（ifu2 本来就没有 region 检查，这个假设已隐含存在，
但压缩把它从"取垃圾"变成了"假命中"。）

⚠️ **标签阵列必须计入**：`rv32ifu2_btb.v` 除了 136 位/行的数据行，还有一张
`tag_q`（`TAG_BITS+1` 位/行，含行 valid）。漏掉它会少算 1.5~3 Kbit ——
本文档早先的 13,056 就是这么来的，已更正。

```
T0            块 PC 直接索引, 4 slot × 2 位饱和计数器, 必定命中
T1..TN        行 = {行有效, tag} + 4 × {slot有效, pred[2:0], u[1:0]}
```

slot 多数时候只用得上 1 个。

  而 RTL 的 **GHR_W 上限是 18**（25 位 chk 的预算）且 `TAG_W <= 12-ROW_AW`。

#### 动态 `USE_SEL`（2026-09-27）

规格 §fpred 生成策略的动态档，落在 `rtl/rv32ifu2_tage.v`。几何：**有符号 4 位饱和
计数器 × 64 项**，按 `pc[9:4]` 直接索引（不吃历史，与三张表同一个块粒度）。

⚠️ **别把 `USE_SEL` 和表项里的 `u` 搞混**（两者看过一眼就会混，规格的译文还是坏的）。
它们是规格里**两个独立编号的小节**，比较的对象都不一样：

| | `u`（规格 §useful 的更新） | `USE_SEL`（规格 §fpred 生成策略·动态） |
|---|---|---|
| 住在哪 | **表项里**（Ti 的第 3 个字段，`pv_q` 的 `SLOT_U`） | **表项外**（独立的 `use_sel_q[0:63]`） |
| 规格给它的定义 | 「这个 entry 是否值得长期占据 TAGE 表空间的**信誉度**」 | 「pcpn 信心不足时选 pcpn 还是 altpred」 |
| 更新时比谁 | **pcpn** 与结果是否相同 | **altpred** 与结果是否相同 |
| 谁读它 | 分配 / 老化逻辑 | fpred 选择器 |

两条更新规则都是"对了 +1"，但一个看 pcpn、一个看 altpred —— **用错会算反**。
规格数据流图里 USE_SEL 画在表的框外与 `T0 pred`/`confidence` 并排喂 fpred；
`u update` 则在 `branch outcome` 下面和 `pred update`/`allocation` 并列。

**选"或"不选"且"。** 规格那句规则（"不为弱**且** USE_SEL 为负时选 pcpn"）与它自己
的前文（"决定 pcpn **信心不足时**的选择方式"）互相打架，两种读法在**正好相反的两格**
上不同（弱&SEL<0、强&SEL≥0）。取"或"—— `fpred = (!weak || SEL<0) ? pcpn : altpred`，
理由：前文那句话只有"或"能兑现；规格自己链的 TAGE-SC-L 原文写的是
*"if (the confidence counter is not weak **or** USE ALT ON NA is negative)"*；
且"或"让强信心恒赢，是经典形式。

**门控是必须的，规格字面那条会掉分。** 实测（同镜像，47 用例 difftest 全过）：

| | 静态（`USEL_EN=0`） | 动态·无门控（规格字面） | **动态·门控（默认）** |
|---|---:|---:|---:|
| branch_bench 周期 | 159,722 | 160,458 | **159,720** |
| ├ 总方向准确率 | 96.57% | 95.92% | **96.57%** |
| ├ 类 3 | 93.38% | 87.20% | 93.38% |
| ├ 类 5 | 96.28% | 93.45% | **96.31%** |
| └ 条件分支误预测 | 1,965 | 2,334 | **1,964** |
| CoreMark 周期 | 11,285,969 | — | **11,281,012** |
| 方向表面积 bit | 8,464 | 8,720 | 8,720 |

无门控掉 0.65pp 的病因：**"只剩 T0 命中"（`ps==0`）那类分支也在训练 USE_SEL**，
而那时 altpred 与 pcpn **是同一个表项**，`altpred==taken` 量的根本不是"altpred 比
pcpn 好在哪"，而是"T0 准不准"。双模态的 T0 在类 3/类 5 上本来就弱，一路把计数器拽成
负 ⇒ 弱信心那档被翻成 pcpn，正好与静态相反。门控就是只保留"决定权真的交给了
USE_SEL"的那些样本：`is_weak(pcpn) && (altpred != pcpn)`。

⚠️ 门控里 `ps==0` 时 `is_weak(u_ppred)` 是**没意义**的（`u_t0_pred` 是 `{方向,2'b00}`
拼的 3 位口径，恒不落在弱区间）。不出错只因为同一拍 `altpred != pcpn` 必为假把它吃掉了
—— 这两个条件**不能拆开用**。RTL 里就地记了。

**上电等价性**：USE_SEL 清成 0 ⇒ `SEL<0` 为假 ⇒ 弱信心选 altpred ⇒ **复位后的行为与
静态策略逐位相同**，之后才按实测收敛。

**一条待办作废：不需要给 `chk` 加位。** 本文件头与 §4 早先都记着"上动态 USE_SEL 后
`upd_fpred == upd_taken` 不再等于'pcpn 猜没猜对'，必须把 `provider_pred` 带到 EX"。
那条**不成立**：fpred 按构造只可能是 pcpn 或 altpred 二者之一（`ps==0` 时两者都等于
`t0_pred`），于是 `altpred != fpred ⇒ fpred == pcpn` —— **u 更新的条件一成立，fpred
就已经是 pcpn 了**，与静态/动态无关。带过来的那一位同时充当条件与方向，`chk` 宽度没动。

`USEL_EN` / `USEL_GATE` 是 **RTL 参数**（不是 Makefile 开关），要 A/B 直接改
`rv32ifu2_tage.v` 的参数默认值重编。

**为什么收益这么小：归因结论（探针实测，量完已删）**

把动态规则能改的那块地量出来（`translate_off` 里的临时计数器，两个基准都跑过）：

```
                    branch_bench        CoreMark
条件分支训练事件        57,858           1,874,210
├ provider 弱信心        3,757 ( 6.5%)     372,943 (19.9%)  ← USE_SEL 有决定权的范围
│  └ 且 altpred≠pcpn      917 ( 1.6%)      85,900 ( 4.58%) ← 能训练/能分歧的范围
│     ├ altpred 猜对       899 (98.0%)      49,280 (57.4%)
│     └ pcpn    猜对        18 ( 2.0%)      36,620 (42.6%) ← 表面上的余量
└ 强信心               54,101             1,501,267
```

**两个基准的病因完全不同，必须分开说。**

**branch_bench：没有余量。** 弱信心且分歧时 altpred 有 **98%** 是对的 —— 静态规则
"弱信心 ⇒ altpred"的前提在这个定向基准上几乎完美成立（它的五类场景本来就是围着
"TAGE 该选谁"设计的干净模式）。天花板 = 18 条 / 57,858 = **0.031%**。而且计数器要
**先学到**才能起作用，连这 18 条也拿不全。旁证：终态 64 个计数器里 **44 个从没离开过
0**，15 负 5 正，且负的只到 −1/−2 而正的能到 +7 —— 正好对应"altpred 偶尔错、经常对"。

**CoreMark：有余量，但按 PC 分不开。** 弱信心占 19.9%，pcpn 对 42.6% —— 表面上有
36,620 条的余量。**但那是摊平的，不是聚集的**：按 64 个桶分开后，只有 **11 个桶**
以 pcpn 为多数，逐桶多数表决的天花板只有 **+2,814 条**（+3.28% of 85,900）。

**换索引**（探针里把 gate 事件按各种候选索引分桶，纯统计、不改预测器）。
分三批做的，每批一次 CoreMark：

*一批：加细 PC / 哈希（同一趟，64→256 项）*

| 索引 | 天花板 | 比静态多 |
|---|---:|---:|
| **`pc[9:4]`（现在的 64 项）** | 52,094 | **+2,814** |
| `pc[9:4]^pc[15:10]`（同尺寸，哈希） | 51,701 | +2,421 ← **更差** |
| `pc[11:4]`（**256 项，面积 ×4**） | 52,347 | +3,067 ← 只多 **+253** |

*二批：把"路径"折进索引（`USEL_IDX=1`，同尺寸 64 项，只换索引函数）*

| 索引 | 天花板 | 比静态多 | 实测 CoreMark |
|---|---:|---:|---:|
| `pc`（`USEL_IDX=0`） | 52,112 | **+2,489** | **11,281,012** |
| `pc ^ fold(ghr, 2)` | 51,589 | +1,966 | |
| `pc ^ fold(ghr, 5)` | 51,509 | +1,886 | |
| `pc ^ fold(ghr, 9)` | 50,417 | +794 | 11,285,707（**比 PC 差 4,695 拍**） |
| `pc ^ fold(ghr,14)` | 50,175 | +552 | |

**掺历史不是"加入信息"，是"把同一个分支的事件打散到多个桶"** —— 每个桶变成
不同分支的混合物，反而更不可分。**历史越长越差，单调。** 这与直觉相反，但数据很干净。

*三批：按表项身份索引（256 桶）*

| 索引 | 天花板 | 比静态多 |
|---|---:|---:|
| `{u_prov, tag}`（provider 的表项身份） | 54,064 | **+4,441（+78%）** |

⇒ **结论分两半：**

1. **"选 altpred 还是 pcpn"确实不取决于分支地址**（同一个 PC 不同次访问行为不同），
   但**也不能靠"把 GHR 折进索引"来补** —— 6 位折叠太粗，掺进去只是打散。
2. 真正有用的是**表项身份**（`{u_prov, tag}`）：天花板 +4,441，比 PC 的 +2,489 高 78%。
   注意这**不是**"把 USE_SEL 存进表项里"——表项在分配时被重置，存在里面就跟着清零；
   要的是**一张独立的、跨分配持久的阵列，按 provider 的表项身份索引**
   （`{u_prov, tag, slot}` 最多 1024 项 × 4 位 = 4,096 bit，与"存进表项"同面积）。
   ⚠️ 代价是结构性的：这个索引要等 provider 选出来才知道，所以在 F1 里**组合读**
   （不能像现在这样在 F0 算好地址）。

⚠️ 以上所有天花板都是"当前 gate 事件流"下的统计，且是**逐桶多数表决**的理想值，
实际拿到多少还要看计数器的学习速度（桶越多、每桶事件越少、学得越慢）。

⇒ 一句话：**这个机制能捞的余量 = |弱信心| × |其中 altpred 猜错| × |这部分能按 PC 分开|**，
CoreMark 上三个因子分别是 19.9% × 42.6% × ~7.7% ≈ **0.65% 的条件分支**；实测拿到
−4,957 拍（−0.044%），量级相符。branch_bench 上第二个因子塌成 2%，所以只剩 −2 拍。

⚠️ 顺带否掉了一个诱人的方向：**不能靠"加大 USE_SEL 表"换收益**（256 项只多 +253 条，
还要付 init 64→256 拍的代价），**也不能靠哈希**。要做大只能换机制（例如把 USE_SEL
索引到路径/GHR 而不是 PC），那已经不是规格里的那条了。

#### 与规格的偏离（RTL 里就地记了，这里是索引）

| 规格 | 本实现 | 为什么 |
|---|---|---|
| 每表独立 FH_IDX/FH_TAG 寄存器，增量更新 | **组合 fold** | GHR 只有 16~20 位，XOR 树更省；且增量方案在 `L` 不是 `W` 整数倍时还要额外 XOR 掉移出窗口的 `h[L-1]`，漏了就静默算错 |
| `i<k<M`, `M=表数目-1` | `i<k<=N`（**含最长表**） | 照原文最长表永远分配不到 ⇒ 一张死表 |
| 动态 `USE_SEL` 的训练**无门控**（规格字面） | **加了门控**：只在"弱信心且 altpred≠pcpn"时训练 | 无门控实测**差 0.65pp**，见下面 §动态 USE_SEL |
| `USE_SEL` 只按 pc 索引、无 tag | 同规格 | — |
| `pred` 初始化为结果 | 初始化为**弱**方向 | 强极值一进表就不可替换 |
| index/tag 用重叠的 PC 低位 | index 取 `pc[ROW_AW+3:4]`、tag 取高位 | 与 BTB 同行几何；两者仍单射，不产生假命中 |
| 每 256K 分支做 u 的 age 重置 | 未实现 | 实测中性，见上 |

#### 两条必须更正的既有说法

1. **`chk` 里的 GHR 快照不是"块首 GHR"。** `top.v` 的注释与本文档早先的规则 2
   都写着"必须是块首 GHR、三条 lane 相同"，而实际做到的是**每条 lane 推进时
   自己的 GHR**（读索引用 `ghr_after`，快照存的是下一拍的 `ghr_q`，两者恒等）。
   说"现在不坏"不够 —— 它在 SPEC 模型上**比块首 GHR 好 0.58pp**（5.43% vs 6.01%），
   所以谁去"修"它谁就是在制造回归。⚠️ 真正的陷阱是：**索引的 GHR 与这份快照是一对，
   要么一起改要么都别改** —— 只改一边就会重现 [[bp-class3-root-cause]] 那个
   "一整类分支收到 0 次写"的病。
2. **一行 4 个 slot 多数是闲置的**（核心每拍只吃一条 ⇒ 稳态每拍推一条 lane）。
   带标签表的**有效容量约等于 `2^ROW_AW` 而不是 4×`2^ROW_AW`**，而且同一条静态
   分支会因为 IBUF 占用情况不同落到不同的行。要根治得引入只在块边界推进的
   `ghr_blk` 并让 F0 索引与 chk 都用它 —— 那会同时改掉 gshare 的行为，
   必须作为独立 A/B，这一版没做。

## 5. 踩过的坑（都在 RTL 注释里就地记了）

1. **`2'd4 - 0` 在 2 位里是 0**：`blk_left` 写成 2 位时"本块剩 4 条"溢出成 0，
   `want_push` 恒为 0，整个前端一条指令都发不出去。要用 3 位。
2. **`{a,b,c,d}` 是高位在前**：`bht_taken` 用 `{ctr[1],ctr[3],ctr[5],ctr[7]}` 拼，
   四个 slot 的方向整体倒过来（谁读谁的邻居）。症状是类 1 从 96% 掉到 4.5%，
   而表里看得见非零行 —— 极易误判成"写没落对地方"。
3. **BTB 里不能存 X 目标**：一条"从没跳过"的条件分支被分配时，若旧目标字段是 X
   （寄存器阵列上电为 X，初始化扫描只清 tag 的 valid 位），就会以 valid=1 + X 目标
   进表；之后 BHT 一旦把它预测成 taken，`next_pc` 变 X，整条前端崩掉。
   症状是 CoreMark 跑到 5 万多拍突然 PC 全 X，而所有短用例都测不出来。
   现在"旧字段不可信时一律填 0"。
4. **lane 的 PC 不能重复加块内偏移**：`q_pc` 本身就是"本拍第一条要交付的指令的
   PC"，偏移已经含在里面。数据用 `pc_ofs` 索引（对）、标签再加一次 `pc_ofs`（错），
   表现像"跳过若干条指令"。
5. **寄存器阵列必须扫描初始化**：`X & 0` 在 `if` 条件里是假，但 `X & 0` 在
   **赋值**里是 0 —— 而 `valid & (tag == …)` 在 valid 为 X 时结果是 **X 不是 0**，
   会一路传到 `next_pc`。所以别指望"valid 位自己会拦"。
6. **扫点前先确认配置真的落地**：`ICACHE_BYTES` 一类 define 若没接进 parameter，
   扫出来的"不同配置"其实是同一个配置（原树整张容量表就是这么废掉的）。
   现在 icache 会打印 `[IFU2-ICACHE] BYTES=… SETS=…`，扫点前先看这一行。
7. **`meminit.bin` 软链**：DUT 走编译期 `+define+PATH`，tb 参考模型按相对路径读
   `meminit.bin`，两者必须是同一个镜像。并行跑不同用例时忘了同步，症状是**第
   57 拍就 difftest 失配**，看起来像 RTL 坏了。本轮又踩了两次 —— 并行跑之前
   先把仓库根的 `meminit.bin` 也指到同一个镜像。
8. **`X & X = X` —— AND 门控只在掩码是"已知 0"时才是干净的 0。**
   TAGE 的分配规则（规格 §6）要求读"比 provider 更长的表"的 u，而那时那些表项
   **没分配过**。第一版把门控写成 `slot_valid ? u : 2'b00`，是三元 → `X ? a : b`
   逐位合并 → 仍是 X；改成 `u & {2{slot_valid}}` 也还是 X，因为**从来没写过的
   项连 slot_valid 都是 X**。于是 `u_eff == 0` 的比较恒为假，**一行都分配不出去**，
   而其它所有数看起来都正常。
   症状三件套：`TAGE rows valid = 0 / 256`、**类 3 恰好回到 50.00%**、
   类 5 掉回 74.41%（= 只剩 T0 双模态在干活）。
   真正的修法是两条一起：① 初始化扫描**把 `pv_q` 也清掉**（不能只清 tag）；
   ② 门控信号取自被扫描清过的位（`row_valid`）。
   ⇒ 派生的规矩：**要 AND 门控，先确认掩码在"没写过"时是 0 而不是 X。**

9. **`chk` 位预算越界是静默的。** `25'd1 << 26` 在 25 位里就是 **0**，那一位永远
   置不上 —— `GHR_W=20` 时 `CHK_FPRED` 落在 bit 26，于是 TAGE 的 `upd_fpred`
   恒读到 0，分配逻辑整条失效。**症状和第 8 条一模一样**（类 3 恰好 50%），
   但病因完全不同。`GHR_W=24` 更狠：补零的复制次数变负数，直接 elaborate 失败。
   现在 `top.v` 有一个 `initial` 显式拦（`GHR_W <= 18`，RAS_AW=3 时），
   报的是一句人能看懂的话。

10. **改 define 名要两头一起改。** 新增 TAGE 开关时 Makefile 发的是
   `+define+BP_T0_HIST`，而 RTL 读的是 `` `ifdef BP_TAGE_T0H `` —— 编译**照样过**，
   只是那个开关永远取默认值。扫描表里"不同配置"其实是同一个配置，正是本节
   第 6 条那个坑的翻版。现在扫描脚本会把 `[IFU2-TAGE] ... AREA=` 那行打出来，
   配置没落地一眼就能看见。

## 6. 已知边界

* **每块只预测一次控制转移。** 块内第二条条件分支若方向没预测对，走 EX 重定向兜底。
* **误预测恢复的 GHR 是近似的**：按"块首快照 + 本次真实方向"恢复，块内第 2/3 条
  分支时丢掉了同块更靠前那几条的结局。只影响预测质量，不影响正确性。
* **陷阱（RTU）时 GHR 直接清零**，不做精确恢复 —— 陷阱稀少，代价是其后一小段
  预测质量。
* **RAS 默认关**（见上表），它在本项目的两个基准上方向相反。
* **没有下一行预取**。原树 IPB 预取是"小容量缓存还能用"的关键；这里没做，
  1 KB→2 KB 只值 0.2% 说明当前工作集对容量不敏感，但没有验证过更大的工作集。
* **每块只预测一次控制转移**、**GHR 恢复是近似的**、**陷阱时 GHR 清零**：见上。
* 输入约定：`idu_accept_num` 不得超过当拍有效 lane 数（核心侧已保证）。
