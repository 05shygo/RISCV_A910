## 2. 待查问题（按建议优先级）

### Q1 ⭐ 类 5 的 L1 大 BTB 命中率为什么只有 48.97%（C910 99.32%）？

**这是目前最大的单项差距，且完全没查过。**

- 现象：自研 11,385 次类-5 分支查询 L1 BTB，只命中 5,575。
- 类 5 是 **75% 偏 taken** 的分支（`x30++`、`x29 = x30 & 3`、`x29 != 3` 时前跳），
  4 条里 3 条要跳 —— 命中率不到一半意味着**超过一半的 taken 拿不到目标**。
- **未知**：是 8 条分支**全都**差，还是某几条差？是容量/thrash，还是训练时机/索引别名？

**怎么测**（仿照 class3 里做过的那次 per-branch 分桶）：
1. 把 L1 BTB 的查询/命中按类 5 的 8 条分支位置分桶（用 `btb_if_pc`），
   看是均匀差还是集中在几条。
2. 数 L1 BTB 的**训练上报**（`train_valid` / `train_pc`）有多少落在类 5 的 PC 上 ——
   若查询多、训练少，就是没填进去。
3. 对照类 4（93.77%）与类 3（77.17%），看是不是"分支密度"或"PC 间隔"相关。

**涉及**：自研 `rv32_ifu_btb.v`；TB 里已有探针 `bt_lookup_vld` / `bt_hit` /
`bt_if_vld` / `bt_if_hit` / `bt_if_pc`（见 §3.2）。

### Q3 类 3 的"索引在动但与结局不相关"—— 为什么？

这是类 3 唯一**没有解释**的观测。已实测：

- pre-array **行地址**（19 位历史）在类 3 上有 **6~9 个取值** → 深位历史是活的；
- **片内偏移** 1~3 个取值；
- 但被选中的 2 位计数器**只在 00↔01 之间**，`10`/`11` 在 4096 次里一次没出现。

**即：索引在变，但变的方式与相位不相关，于是每个计数器看到 50/50 混合。**
"为什么"完全没查。这是唯一还没被证伪的类-3 入手点。

**怎么测**：
1. 在预测时刻**同时**采 `(行地址, 片内偏移, 相位 v)` 三元组，看行地址与 v 的**相关性**
   （现在只有各自的取值集合，没有联合分布）。
2. 若相关 → 问题在计数器/训练；若**不相关** → 问题在那个 19 位历史的**构造**上
   （`{vghr_q[11:8], vghr_q[7:2] ^ vghr_q[19:14]}`），去查 GHR 的每一位在那一刻是
   真结局还是预测位。

## 4. 坑（都踩过，务必先读）

### 4.1 观测类

| 坑 | 说明 |
|---|---|
| **>>1 PC 约定** | C910 的 IF 侧 PC 总线是 `PC[39:1]`。`pcgen_l0_btb_if_pc` + `pcgen_l0_btb_chgflw_pc` 拼出来要 **`<<1`**；`ct_ifu_ipdp.btb_index_pc` 同样。**不换算会静默变成"PC 的一半"**，分桶全落类 0（实测范围 `0x058..0x4d0` 正好是真实区间的一半）|
| **C910 的 4 路 BTB 不自己比 tag** | `btb_ifdp_wayN_vld` 只是表项有效位（`ct_ifu_btb.v:595`）。真命中 = `ct_ifu_ipdp.v:5550` 的 `btb_branch_miss` 取反，且**必须门控"IP 级有分支"** |
| **C910 的 `ret` 不算 `jmp`** | `retire_inst0_jmp = normal_retire && ... && !rob_retire_inst0_pret`（`ct_rtu_retire.v:1486`）→ 要数 `rtu_ifu_retire0_preturn` |
| **方向预测错的分支一定在 retire slot0** | 预测错必冲刷，而 expt 表只有 inst0 一份 |
| **`rtu_hpcp_*` 那组不能用** | 要 CSR 编程才动；用组合逻辑的 `rob_retire_inst0_bht_mispred` |
| **类 1/类 2 的 L1 命中率不可比** | C910 分别走 LBUF / 不查不填（见 §1.3）|
| **per-class 探针要按类内位置分桶** | 直接对 8 条分支的某信号做按位或没有意义（PC 不同就会多值）；必须按位置分开 |

### 4.2 构建类

| 坑 | 说明 |
|---|---|
| `make run TEST=xxx` 会改 `meminit.bin` | 对称链接，跑完要手动换回 `bin/coremark.bin` |
| 自研改 `obj_nofsdb` 前要 `make asm` | 否则用的是旧的 `bin/*.bin` |
| C910 侧编译约 **25 s**、仿真约 **70 s** | 比预想快，可以放心迭代 |
| C910 的 `lbuf_pcgen_active` / `lbuf_ifctrl_active` / `lbuf_bht_*` / `pcgen_bht_chgflw*` 全是接死的 | 见 §1.4，别再试 |
| `LBUF_EN` 在 `mySoC/ifu_subsys.v:37` | 打开也没用（顶层常量接死）|

### 4.3 文档类

| 坑 | 说明 |
|---|---|
| **不要只看 L0 或 L1 的命中率当"准确率"** | 用户明确纠正过：准确率 = **最终预测 vs 实际跳转**（§1.2）；小部件命中率只是参照 |
| `entry_cnt` 的 popcount 不可当依据 | 删项时不清零（C910 同样写法，不是移植偏差）|
