# 专题：branch_bench 类 3（交替 T/N）为什么只有 50%

2026-09-24。本文把"类 3 = 50.00%"这一件事的**全部过程、实测数据、试过并否掉的修法、
排除的假设、以及最终判定**收敛到一处。相关但更宽的内容见
`bp_c910_vs_minirv_zh.md`（与 C910 的横向对比）与 `bp_change_log_zh.md`（P0 改动日志）。

> 📌 **类 3 之后要查什么（含未解释的观测）见 `bp_next_questions_zh.md`**。

---

## 0. 一句话结论

自研 IFU 在类 3 上 **50.00%（2048/4096），且 4096 次里一次 taken 都没预测出来**；
C910 是 86.72%。实测已定位到：**类 3 每条分支的历史索引都在变（pre-array 行地址 6~9 个取值、
片内偏移 1~3 个取值），但变的方式与结局不相关** —— 被选中的 2 位计数器看到的是
50/50 的混合，于是停在 00↔01、永不越过（`10`/`11` 在 4096 次里一次都没出现）。
净效果等于"每-PC 计数器"，在严格交替上只能 50%。

C910 范本里唯一对得上的机制（环路缓冲把记录的**真实结局**按取指节拍喂给 GHR）
**在自研侧无法靠接线或小改达成**：接口从来没设计过，且 LBUF 本体也不工作。
**判定为结构性课题。**

## 1. 现象

| | 自研 IFU（基线，P0 改动前）| C910 |
|---|---|---|
| 类 3 准确率 | **50.00%**（2048/4096）| **86.72%** |
| 类 3 预测 taken | **0 次** | 大量（6/8 条分支达 99.2~99.6%）|
| 类 1..5 总准确率 | 92.36% | 95.06% |

即：**两边总准确率差的 2.70pp 全部来自类 3**，其余四类基本持平
（类 1 95.79 vs 95.67、类 2 100.00 vs 99.95、类 4 都是 100%、类 5 89.33 vs 91.85）。

**50.00% 不是"随机"** —— 它恰好是 2 位饱和计数器在严格交替序列上从 00 出发的理论行为
（只在 00↔01 之间摆，`bit1` 恒 0 ⇒ 恒预测 not-taken ⇒ 命中一半）。实测的
`预测 taken = 0/4096` 与 `2048/4096` 与这个模型**一个不差**。

对比：若历史项真的随相位改变选表，两组计数器会分别饱和到 `11` 与 `00`
⇒ 会大量预测 taken 且准确率接近 100%。**所以实测数据本身就证明：类 3 的选表项
不随相位变。**

## 2. 类 3 在基准里是什么

`asm/branch_bench.S` 的 `[0x1c0, 0x250)`：

```asm
class3:
    xori x9, x9, 1          # 每轮外层循环翻转一次 (各条分支同相位)
    ...
    beq  x9, x0, c3a0       # 0x1d0
    beq  x9, x0, c3a1       # 0x1e0
    ...                     # 8 条, 16 字节间隔
    beq  x9, x0, c3a7       # 0x240
```

- 8 条静态分支，**16 字节间隔**（保证 BHT 的 `PC[13:4]` 与 `PC[9:3]` 都不同）。
- `x9` 每轮外层循环翻转一次 ⇒ 8 条分支**同相位**，每条自己的结局序列是严格 T,N,T,N。
- 外层 512 轮 ⇒ 每条分支 512 次。C910 侧实测 `45,056 / 4,096 / 4,096 / 4,096`
  与自研侧完全一致，两边的条件分支总数都是 57,858。

**注意**：这是一个"每-PC 计数器无能为力、但跨分支历史可以解"的构造 ——
8 条分支同相位，所以任意一条的历史都能预测其余各条。

## 3. BHT 的结构性退化点

自研 BHT 与 C910 **逐位相同**（读索引条件、更新表、写掩码表都对过），
所以下述行为不是移植引入的偏差：

```
行地址 (pre-array 读) = {vghr_q[11:8], vghr_q[7:2] ^ vghr_q[19:14]}   ← 完全由 GHR 决定, 无 PC 位
片内偏移 (32 选 2)     = PC[7:4] ^ GHR[3:0]                          ← PC 只以这 4 位进入
选表                   = sel[1] ? taken 平面 : ntake 平面            ← 平面由 PC 索引的选择阵列定
预测                   = 选中计数器的 MSB
```

**退化条件**：`GHR[3:0]` 一旦（在预测时刻）恒定，整个机器就变成
**每个 `PC[7:4]` 一个 2 位计数器**。在严格交替上那就是 50%。

C910 的同一段代码（`ct_ifu_bht.v:1415`）：

```verilog
//Predict Array offset = vghr[3:0] ^ pc[7:4]
assign pre_offset_if_0[3:0] = pcgen_bht_ifpc[6:3] ^ pre_vghr_offset_0[3:0];
//1430  pre_vghr_offset_0[3:0] = rtughr_reg[3:0];   // retire 校准过的 GHR
//1432  pre_vghr_offset_0[3:0] = bju_ghr[3:0];      // 推测 GHR
```

## 4. 定性过程（按时间顺序，每一步都有实测）

### 4.1 与 C910 逐条分支对比（C910 侧，TB per-branch-PC 计数）

| 位置 | pos1 | pos2~5 | pos6 | pos7 | pos8 |
|---|---|---|---|---|---|
| C910 准确率 | **50.00%** | 99.61% | **50.00%** | 99.61% | 99.22% |
| 类 5 对照 | **74.41%** | ~99% | — | **74.41%** | 99.02% |

`50.00%` 是每-PC 计数器在交替上的**能力上限**，`74.41%` 是 T,T,T,N 上"恒预测 taken"
的 75% 上限。**同一个类里 6/8 条能到 99.6%，超出每-PC 计数器的上限 ⇒ 只能来自历史。**

> 未解释：为什么恰好是 pos1/pos6（类 5 是 pos1/pos7）落在计数器行为上。
> pos1 能解释（它之前的 4 位历史全来自上一类，恒定）；pos6/pos7 解释不了。

### 4.2 GHR 喂料成分：两边差 9 倍（同探针实测）

| GHR 移位来源 | C910 | 自研 | 性质 |
|---|---|---|---|
| `ghr_updt_vld`（mispredict 注入真实结果）| 2,770 | 4,262 | 真值 |
| **`vghr_lbuf_updt_vld`（LBUF 复放的真实结局）** | **51,130** | **0** | **真值** |
| `vghr_ip_updt_vld`（IP 级条件分支的**预测位**）| 47,917 | 66,505 | 自指 |
| `lbuf_bht_active_state` 活跃拍数 | 52,660（46%）| 0 | — |
| **真实结果占比** | **约 53%** | **约 6%** | — |

C910 那条额外通路的来源（`ct_ifu_lbuf.v:6464`）：

```verilog
assign lbuf_bht_con_br_taken = lbuf_pop_con_br_taken;   // 环路缓冲复放时记录的【真实结局】
```

GHR 低 4 位的分布也印证了"喂的是什么"：

| `vghr_q[3:0]` | C910 | 自研 |
|---|---|---|
| `== 0` | 19,015 | 32,491 |
| `== 15` | 71,032 | 115,205 |
| 其它 | 24,866 | 31,870 |

两边都有 ~82% 的时间处于"全 0 或全 1"——这正是"被预测位喂饱"的指纹
（预测绝大多数是 taken，于是填满 1）。

### 4.3 决定性测量：预测时刻的四元组（自研侧）

在 **IP 级条件分支有效那一拍**采 `(ip_pc, pre_offset_onehot, sel_array_result, bht_counter)`，
按类内位置分桶：

| 位置 | **行地址取值集合**（按位或）| `oh` 取值数 | `sel[1]` | 计数器 00 / 01 / 10 / 11 |
|---|---|---|---|---|
| pos1 `0x1d0` | `3bf`（**9 位**）| **仅 1 个** | 0 | 257 / **255** / 0 / 0 |
| pos2 `0x1e0` | `33f`（8 位）| 2 | 0 | 768 / 0 / 0 / 0 |
| pos3 `0x1f0` | `23f`（7 位）| 3 | 0 | 769 / 255 / 0 / 0 |
| pos4 `0x200` | `03f`（6 位）| 3 | 0 | **1024 / 0 / 0 / 0** |
| pos5 `0x210` | `03f`（6 位）| 3 | 0 | **1024 / 0 / 0 / 0** |
| pos6 `0x220` | `03f`（6 位）| 3 | 0 | 769 / 255 / 0 / 0 |
| pos7 `0x230` | `03f`（6 位）| 3 | 0 | 769 / 255 / 0 / 0 |
| pos8 `0x240` | `03f`（6 位）| 3 | 0 | 768 / 256 / 0 / 0 |
| **类 5（对照，89.31%）** | `03f`~`3ff`（6~10 位）| 2~4 | **1** | **全是 11（饱和 taken）** |

> 行地址 = `{vghr_q[11:8], vghr_q[7:2] ^ vghr_q[19:14]}`，用到 **19 位历史**；
> 它是"深位历史有没有在动"的唯一观察窗。

**五条硬结论：**

1. **`10` 与 `11` 在类 3 全部 8 条分支上一次都没出现过。**
2. **历史索引是在动的，而且动得不小**：行地址 6~9 个取值、片内偏移 1~3 个取值。
   所以**不是"历史没到达"**（早先的写法有误，见 §4.3.1），而是——
3. **动的方式与结局不相关**：被选中的每个 2 位计数器看到的都是 50/50 的混合，
   于是停在 00↔01 永不越过。pos1 的 00↔01 分布**恰好 257/255**，正是这个的教科书形态。
   对照类 5（75% 偏 taken）的计数器饱和到 `11` —— 说明选择机制在那里**是有相关性的**。
4. **类 3 恒读 ntake 平面（`sel[1]=0`），类 5 恒读 taken 平面（`sel[1]=1`）。**
   而 pre-array 的初始化值是 **taken 平面 = `2'b11`、ntake 平面 = `2'b00`**
   ⇒ 两边报出来的都基本是**初始值**：类 5 报"恒 taken"（在它 75% 偏 taken 的底线上
   涨到 89.31%），类 3 报"恒 not-taken"（恰好 50.00%）。
5. **pos4/pos5 是 1024/1024 全 00** —— 从未被写过（00 收到 taken 更新应变成 01）。

#### 4.3.1 一处自我修正：pos1 不是"历史没到达"

早先（只有 `oh` 列时）的结论写的是"pos1 的片内偏移只有一个取值 ⇒ 历史项根本没到达它"。
补上**行地址**这一列后**这句被推翻**：pos1 的行地址有 **9 个取值**，
历史是到达了的（走行这一路）。片内偏移恒定只说明**偏移这一项**不动，不说明整体没历史。

正确的描述是结论 2/3：**索引在动，但与结局不相关。**

## 5. 试过并否掉的修法（全部有 A/B，全部已回退）

### 5.1 把 GHR 喂料从"预测位"换成"BJU 时刻的真实结局"（改 2 行）

```verilog
// 原: assign vghr_ip_updt_vld = cp0_ifu_bht_en && ipctrl_bht_con_br_vld;
//     vghr_q <= {vghr_q[20:0], ipctrl_bht_con_br_taken};      // 预测位
   assign vghr_ip_updt_vld = cp0_ifu_bht_en && iu_ifu_bht_check_vld;
   vghr_q <= {vghr_q[20:0], iu_ifu_bht_condbr_taken};          // 真实结局
```

| 指标 | 基线 | 改后 |
|---|---|---|
| 类 3 | 50.00% | **50.00%（没变）** |
| 类 1 | 96.07% | 94.95% |
| 类 5 | 89.31% | 83.25% |
| 类 3 预测 taken | 0 | 508 |
| 周期 | 179,585 | **185,099（+3.1%）** |

**否定。** 预测从"系统性错"变成"随机"，**信息量没有增加**。
失败原因：破坏了**读偏移与写偏移的对齐** —— 读用"移位后"的
`{vghr_q[2:0], ipctrl_bht_con_br_taken}`，写用随包带回的 `cur_ghr[3:0]`，
两者只因 `bht_ipdp_vghr_q` 在 `ifctrl_bht_pipedown` 上锁存才相等；
把更新点从 IP 挪到 EX 晚了 2 级，窗口整体错位。

> **教训**：任何改 GHR **追加时刻**的方案，先保证
> ① 读行公式与写行公式同形式；② 读偏移与写偏移同字段。

### 5.2 接通 `pcgen_bht_chgflw` / `_short`（C910 里是接通的）

`rv32_ifu_top.v:246-247` 早就声明了这两根线、`:821-822` 也被 `u_pcgen` 驱动，
只是 `:1364-1365` 没接到 bp_top（接了 `1'b0`）。**纯接线疏漏**，接上实测：

| | 基线 | 接通后 |
|---|---|---|
| 类 1 | 96.07% | 95.28% |
| 类 5 | 89.31% | **80.32%** |
| 类 3 | 50.00% | 50.00% |
| 周期 | 179,585 | **186,398（+3.8%）** |

**否定。** C910 的 `pcgen_bht_chgflw` 语义依赖 LBUF 驱动的取指模式，
单独接过来只会让选择阵列在错误的时机重读。

### 5.3 接通 LBUF 三根线 + `LBUF_EN=1`

把 `lbuf_bht_active_state` / `lbuf_ifctrl_active` / `lbuf_pcgen_active`
都接到 `lbuf_active`，并打开 `LBUF_EN`：

- `lbuf_bht_active_state` **998,457 拍常高**；
- 条件分支只执行了 **131 条**（正常 57,858）—— **前端被卡死**。

**灾难性否定。** 说明**自研侧的 LBUF 本体就不工作**（`active` 一旦进入就再也不撤），
不是"接上线就能用"。

## 6. 排除掉的假设（每条都实测过）

| 假设 | 结论 | 依据 |
|---|---|---|
| GHR 卡死在 0 | **否** | `vghr_q` 变化 47,806 次 |
| pre-array 没例化 / 被砍掉 | **否** | `rv32_ifu_bht_pre_array` 在，`pre_array_data_taken` 非零 178,512 拍 |
| 选择阵列失效 | **否** | `sel_array_result[1]=1` 出现 122,122 拍 |
| BHT 索引的 PC 位段对不上 C910 | **否** | miniRV `pc_bus` 是字节 PC 取 `[13:4]`；C910 `pc_bus` 是 >>1 PC 取 `[12:3]`；换算后都是 `PC[13:4]` |
| taken/ntake mux 接反 | **否** | 与 C910 逐字一致 |
| GHR 多移（同一分支移两次）| **否** | 上升沿 54,077 + mispredict 4,262 ≈ 57,858 根分支 |
| `bju_ghr` 两边语义不同 | **否** | 都是 `assign bju_ghr[21:0] = iu_ifu_chk_idx[21:0]`（预测时刻的 GHR 快照）|
| BHT 核心逻辑与 C910 有差异 | **否** | 读索引条件、更新表、写掩码表逐位相同 |

## 7. 结论与遗留

### 7.1 判定

**先回答一个被明确问到的问题：修好 LBUF + 补 1000+ 行 pop/retire 握手与逐条分支结局记录，
能不能搞定类 3？—— 实测判定：不能，别投。** 三条依据（前两条是 §4.3 的实测）：

1. **LBUF 只覆盖循环，类 3 不是循环。** 外层循环体（类1→类2→类3→类4→类5）约 140 条
   指令 / 560 字节，而 LBUF 容量是 16 项（C910 是 16 条，自研是 16×64bit）。
   类 3 的 8 条分支根本进不了 LBUF ⇒ 它的真实结局喂料**在类 3 的预测时刻不会触发**。
   反推 C910 那 51,130 次 LBUF 移位，几乎必然全部来自**类 1 的内层循环**
   （48/16/24 次退出的那种）—— 而类 1 两边本来就差不多。
2. **锁不在"深位历史没动"。** 实测行地址在类 3 上有 **6~9 个取值**，深位历史是活的。
   所以"喂真实结局让深位变真"这条通道**解不开这个锁**。
3. **更强的喂料实验已经做过且无效**：§5.1 给**每一条**条件分支都喂真实结局
   （真实结果占比 100%，远超 LBUF 的 ~53%），类 3 仍然恰好 50.00%。

C910 范本里与本问题对得上的机制，是**环路缓冲（LBUF）把记录的真实结局按取指节拍喂给
GHR**。它在自研侧**无法通过接线或小改达成**：

- 自研的 `rv32_ifu_lbuf.v` 只有 **149 行**（C910 是 6,954 行），是独立重写，
  **从来没有 BHT 接口**（端口表里没有 `lbuf_bht_con_br_vld`/`_taken`/`lbuf_bht_active_state`；
  文件里连一个 `lbuf` 之外的内部信号都没有）；
- 补齐需要：每条目的"是否条件分支"标记、来自 IB 级的 retire/pop 标识、
  BHT 侧预测捕获、以及 ~1000 行 C910 控制逻辑 + 一个 IB 级接口；
- 而且 **LBUF 本体也不工作**（见 5.3），所以要先修 LBUF 才能谈接口。

### 7.2 遗留（未验证的推断，如实记录）

- 为什么 C910 的类 3 恰好是 pos1/pos6 落在计数器行为上、其余 6 条到 99.6% ——
  pos1 能解释（历史恒定），pos6/pos7 解释不了，猜是 XOR 索引的别名冲突，**未验证**。
- "真实结果占比 53% vs 6% 是类 3 差异的原因"是**强证据 + 机制自洽**，
  但没有做成闭环实验（闭环需要真改 RTL，而两次尝试都被否）。

### 7.3 建议

**类 3 归为结构性课题，不再在本轮投入。** 转向
`bp_change_log_zh.md` §4.1 的 **L0 容量课题**（命中率 30.07% vs 目标 45%，
瓶颈已实测确认为 16 项表的**容量**，不是搅动）。
