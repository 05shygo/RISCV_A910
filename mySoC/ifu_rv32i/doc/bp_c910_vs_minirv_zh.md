# C910 与自研 IFU 的分支预测对比（同一份定向基准）

2026-09-23。用 §1 的 `asm/branch_bench.S` 原样移植到 C910 工程
（`/x2025/GPrj1/IC1/riscv/RISCV_CPU/open_riscv_2035`），在同一批场景上量 C910 的
分支预测质量，与自研 IFU 横向对比。

> 📌 **下一步要查的问题清单见 `bp_next_questions_zh.md`**（交接文档）。

**一句话结论**：总方向准确率 C910 **95.06%** vs 自研 IFU **92.36%**，差的 2.7pp
**全部来自"交替 T/N"一类**（86.72% vs 50.00%）——自研 IFU 在这类模式上一条 taken 都预测不出来；
其余三类两边基本持平。

---

## 1. 怎么保证两边可比

### 1.1 基准的移植（只改平台相关的三处）

`smart_run/tests/cases/branch_bench/branch_bench.s` 与 `asm/branch_bench.S`
**指令序列逐条一致**，只改了：

| # | 自研工程 (RV32) | C910 工程 (RV64) |
|---|---|---|
| 1 | `.section .text.init` | `.section .text.bench`（C910 的 `linker.lcf` 只收 `crt0.o(.text)` 与 `*(.text*)`）|
| 2 | 入口 `_start` | 入口 `main`（crt0 用 `jal main` 进入）|
| 3 | 退出 `a7=93; ecall` | `jal __exit` / `jal __fail`（crt0 的约定）|

**两头对上了**：两边测到的条件分支数完全一致 —— 类 1..5 各 57,344 条、
类 0（外层回边 + crt0）各 514 条，合计 **57,858 = 57,858**。两条独立编译链、
两套不同的 TB 口径得出同一个数，说明移植没有改变分支行为。

### 1.2 移植时踩到的坑：RVC 压缩指令（值得记）

C910 的 `-march=rv64imafdcxtheadc` **带 c 扩展**，`addi rd,rd,-1` / `nop` 会被压成
2 字节，`.org` 定死的 16 字节间隔全部失效 —— 实测分支间距变成 10/8 字节，
同一类里的多条静态分支会互相踩 BHT 表项。加 `.option norvc` 后
用 `objdump` 逐条核对，27 条条件分支精确落在 16 字节栅格上。

> 这类错误是**静默**的：仿真照样 PASS，只是测到的不是单条分支的历史。

### 1.3 PC 分桶不硬编码

C910 侧 TB 在 0 时刻读 `work/bench_meta.txt`（构建时由
`gen_bench_meta.sh` 从 ELF 用 `nm`+`objdump` 现场导出），拿到各类入口地址与
27 条条件分支的 PC 表。改 crt0 导致 `.text.bench` 基址漂移时不会静默错位
（实测基址 `0x66c`，类 1..5 = `0x76c/0x7ac/0x82c/0x8bc/0x8fc`）。

## 2. C910 侧的观测点（纯 TB 层次化引用，不改 RTL）

写在 `smart_run/logical/tb/tb.v` 的 `[IC1]` 段，`+BENCH` 才启用。

| 量 | 取自 |
|---|---|
| 分母：已提交条件分支 | `x_ct_core.rtu_ifu_retire0/1/2_condbr`（三槽求和）|
| 分子：方向预测错 | `x_ct_core.x_ct_rtu_top.rob_retire_inst0_bht_mispred` |
| 返回 | `x_ct_core.rtu_ifu_retire0_preturn` |
| L0 查询/命中 | `x_ct_ifu_top.x_ct_ifu_l0_btb.l0_btb_rd` / `l0_btb_ifdp_hit` / `l0_btb_ifctrl_chglfw_vld` |

三个必须知道的语义点（都从 RTL 读出来并实测验证过）：

1. **方向预测错的分支一定在 retire slot0**。预测错必然冲刷流水线，出错的分支就是
   最老的未提交指令；而 C910 的 expt 表只有 inst0 一份（`ct_rtu_rob_expt` 根本没有
   inst1/inst2 的 mispred 输出）。预测对的分支则可能落在 0/1/2 任意槽。
2. **返回不是 `jmp`**。`retire_inst0_jmp = normal_retire && rob_retire_inst0_jmp
   && !rob_retire_inst0_pret`（`ct_rtu_retire.v:1486`）—— `ret` 走 `preturn` 另一条线。
   照 `jmp` 数会得到 0。
3. **IF 侧的 PC 总线是 `PC[39:1]`**（retire 总线内部同样是 >>1，pad 才补回 `<<1`）。
   把 `pcgen_l0_btb_if_pc[38:15]` 与 `pcgen_l0_btb_chgflw_pc[14:0]` 直接拼起来得到的是
   PC 的一半 —— 实测拼出来是 `0x050..0x4d8`，正好是真实区间 `0x0a0..0x9b0` 的一半。

### 2.1 对账（可信度）

| 检查 | 结果 |
|---|---|
| 实测条件分支数 vs 解析期望 | 45,056 / 4,096 / 4,096 / 4,096 **四项全等** |
| 类 0 条件分支 | 514（外层回边 512 + crt0）——与自研侧一致 |
| 类 1..5 内 PC 不在分支表里的条件分支 | **0** |
| 分子三种口径 | A=2,831 / B=2,766 / C=2,766（差 65，见下）|
| 分母口径缺口（预测错但同拍 `condbr=0`）| 106 / 2,831，两口径准确率 95.06% vs 95.07% |

A 与 B 的 65 差、以及那 106 个"不同拍"的脉冲，量级只有 2~4%，且**换成补上缺口的口径
准确率只变 0.01pp**，不影响任何结论。已如实列出而不是取好看的那个。

## 3. 结果对比

### 3.1 方向预测准确率（每类的条件分支）

| 类 | 场景 | 自研 IFU（基线，改动前） | C910 | 差 |
|---|---|---|---|---|
| 1 | 稳定 taken 回边 | 95.79% | 95.67% | -0.12pp |
| 2 | 恒不跳前向分支 | 100.00% | 99.95% | -0.05pp |
| 3 | **交替 taken/not-taken** | **50.00%** | **86.72%** | **+36.72pp** |
| 4 | 调用/返回 | 100%（4,608 控制转移）| 100%（2,048 返回）| 持平 |
| 5 | 偏 taken T,T,T,N | 89.33% | 91.85% | +2.52pp |
| | **合计（类1..5，各 57,344 条）** | **92.36%** | **95.06%** | **+2.70pp** |

- 自研基线数字取自 `bp_change_log_zh.md` §1.3（各类误预测 1,896 / 0 / 2,048 / 437，
  合计 4,381 / 57,344 = 92.36%）。
- 类 4 两边都是 0 条条件分支，比的是"控制转移的目标对不对"：自研 4,608 条 jal/jalr
  全对；C910 2,048 条 `ret` 全对（RAS 目标零误预测）。

### 3.2 差在哪一类，为什么

**类 3 是唯一的实质差距，而且差得很难看：自研 IFU 是 50.00%，正好等于抛硬币。**

自研侧同一份报告的原始行：类 3 的 `预测 taken (BHT) = 0` —— 8 条分支、每轮翻转一次
`x9`、每条分支的结局序列是 T,N,T,N,…，而 BHT **一次 taken 都没预测出来**，
落进了"恒预测不跳"的双稳盆地。这类模式每-PC 的 2 位饱和计数器**恰好全错**。

C910 拿到 86.72%，是因为它的 BHT 用上了跨分支的历史。**§3.5 的定向实验已经把这条
从推断做成了实测**（并顺带推翻了我原先"自研侧没有历史机制"的说法 —— 那句话是错的）。

顺带一个反向的发现：**类 1（稳定 taken 回边）两边几乎一样**（95.79% vs 95.67%）。
所以自研 IFU 的 BHT 在"偏斜分支"上并不差，缺的是对相关性的利用。

### 3.3 周期数（**不是**预测质量指标）

| | 自研 IFU | C910 |
|---|---|---|
| 总周期 | 179,748 | **114,903** |
| 冷启动/引导占比 | 0.57%（IFU init 1,027）| 3.51%（首次进基准 retire 在 4,038 拍）|
| retire 指令数 | — | 133,300 |

C910 快 **1.56×**。但这个数字**不能归给分支预测**：C910 是乱序三发射，自研核是
5 级顺序单发射，两者结构差着量级。列在这里只是为了说明基准在 C910 上跑得动、
长度够（要求 ≥5 万拍）。

C910 的冷启动占比 3.51% 高于本次基准设计时定的 2% 目标 —— 原因是 C910 的 crt0
要做 PMP/MMU/各级 cache 与预测器的失效与使能，引导段比自研工程长得多；外层轮数
**刻意保持 512 轮不变**（与自研侧同构），没有为了压这个比例去改轮数。

### 3.4 L0 BTB：**这一项两边不可直接比**

C910 的 L0 BTB 与自研核的 16 项 L0 BTB 是**同一个结构**（自研的就是从
`ct_ifu_l0_btb.v` 适配来的），但两边的**用法不同**：

- 自研核：L0 BTB 也**只是快滤** —— 它后面同样有大 BTB（`rv32_ifu_btb.v`，
  360 行，例化于 `rv32_ifu_bp_top.v:408`）。

  > ⚠️ **更正（2026-09-24）**：本节早先写的是"自研核的 16 项 L0 BTB 是**唯一的 BTB**"，
  > **这句是错的** —— 当时只看 L0 的计数就下了结论，没有去查有没有 L1。
  > 实测自研核的 L1 BTB **在工作且是主力**：查询 96,184 拍、命中 **83,712 拍（87.03%）**；
  > 分类命中率 类1 94.14% / 类2 99.68% / 类3 77.17% / 类4 93.77% / 类5 **48.97%**。
  > 相对照，L0 只有 7,077 次命中。**两边 L0 承担的角色其实是相同的**（都是快滤），
  > 早先那句"两边 L0 承担的角色根本不同"也随之作废（见下）。
- C910：L0 BTB 只是**大 BTB 前面的快滤**，每个取指周期都被读
  （实测 `l0_btb_rd` 高达 104,936 拍，占总周期 91%），条件分支的目标大多由更大的
  BTB 提供。

所以"命中率"这个比值在两边不是同一个量，**本文不算这个比值**，只列实测原始计数：

| C910 实测 | 次数 |
|---|---|
| L0 读选通周期 | 104,936 |
| 变更流重定向（`pcgen_l0_btb_chgflw_vld`）| 46,504 |
| L0 原始命中周期（`l0_btb_ifdp_hit`）| 7,083 |
| L0 可用命中（`cnt==1`，真能改流向）| 4,301 |
| └ 其中类 4（返回）| **4,129（96.0%）** |
| └ 类 3 / 类 5 | 10 / 156 |
| └ 类 1 / 类 2 | **0 / 0** |

最后两行是这次测出来最有意思的一条：**这份负载里 C910 的可用 L0 BTB 命中几乎全是
返回地址**（4,129/4,301），条件分支的一个都没命中 —— 条件分支的目标由更大的 BTB 承担。
**更正后**：自研核的 L0 命中（类 1 46,761 / 类 4 5,372）与 C910 的
（类 1 0** / 类 4 4,129）**量级相当**，两边 L0 承担的角色是一样的 ——
**都是大 BTB 前面的快滤**，条件分支目标主要由大 BTB 提供。
（** C910 类 1 的 L0 可用命中为 0，与自研侧的 46,761 差异较大，这点尚未解释。）

> 早先本文用这一节去支撑"命中率低是容量问题、只能加表项"，**该推论已作废**：
> 既然 L0 是快滤，它的命中率低本来就是设计使然，不是要提的指标。
> 真正该看的是大 BTB 的命中率 —— 实测 **87.03%**（分类见上）。

### 3.4b 小部件逐类对比（2026-09-24 补）

前面 §3.1 比的是**最终方向预测 vs 实际跳转**（这才是"分支预测准确率"）；
本节把两个核的**小部件**也逐类比一遍，作为参照。

**两边口径说明（重要）**

| 部件 | 自研侧取法 | C910 侧取法 |
|---|---|---|
| 最终方向 | `ex_bht_pred` vs `ex_alu_f`（按 `pc_EX`）| `rob_retire_inst0_bht_mispred` vs `rtu_ifu_retire0_condbr_taken` |
| L0 BTB | `lookup_en` / `hit`（IF 级）| `l0_btb_rd` / `l0_btb_ifdp_hit` |
| **L1 大 BTB** | `btb_if_vld` / `\|btb_if_hit`（IF 级 BTB 结果）| `ct_ifu_ipdp.btb_branch_miss` 取反，门控在"IP 级有分支" |
| RAS | 类 4 jal/jalr 误预测 | 类 4 `ret` 目标误预测 |

> **C910 的 L1 命中信号要小心**：4 路 BTB（`ct_ifu_btb`）**自己不比对 tag** ——
> `btb_ifdp_wayN_vld` 只是该表项的有效位（`ct_ifu_btb.v:595`）。
> 真正的 tag 比对在 `ct_ifu_ipdp.v:5550`：
> ```verilog
> assign btb_branch_miss = !btb_branch_way_vld ||
>                          (btb_branch_tag[9:0] != {btb_index_pc[19:13], btb_index_pc[2:0]}) ||
>                          !cp0_ifu_btb_en;
> ```
> **命中 = `!btb_branch_miss`**，且只在"IP 级有分支"时有效。
> 另：`btb_index_pc` 是 **>>1 约定**（直接拼出来是 `0x058..0x4d0`，正好是真实 `0x0a0..0x9b0` 的一半）。

**逐类结果**

| 类 | 场景 | 最终方向（自研 / C910）| L0 BTB 可用命中 | **L1 大 BTB 命中率（自研 / C910）** |
|---|---|---|---|---|
| 1 | 稳定 taken 回边 | 95.79% / 95.67% | 46,761 / 0 | 94.14% / **0.00%** ⚠️ |
| 2 | 恒不跳前向 | 100.00% / 99.95% | 0 / 0 | 99.68% / 3.33% ⚠️ |
| 3 | **交替 T/N** | **50.00% / 86.72%** | 0 / 0 | **77.17% / 99.67%** |
| 4 | 调用/返回 | 100% / 100% | 5,372 / 4,129 | 93.77% / **99.63%** |
| 5 | **偏 taken T,T,T,N** | **89.33% / 91.85%** | 782 / 156 | **48.97% / 99.32%** |

**⚠️ 类 1 与类 2 的 L1 一列不可比，别当差距读：**

- **类 1 的 0.00% 不是缺陷**：C910 的内层循环跑在**环路缓冲（LBUF）**里、由复放供指，
  根本不查 BTB（所以它的 L0 可用命中也是 0）。自研核没有可用的 LBUF（见 §3.5），
  同类 1 只能靠 L1 BTB 覆盖 → 94.14%。**两边用的是两套机制。**
- **类 2 样本只有 30**：C910 对"恒不跳"的分支不查/不填 BTB（不需要目标）。

**类 3/4/5 完全可比，是硬结果。**

**这张表最重要的发现：类 5 的目标预测差 50.35pp，是全表最大。**

先前只看方向时，类 5 是"只差 2.52pp"的小项；补上目标预测后它变成了最大的单项差距
（自研 48.97% vs C910 99.32%）。类 5 是 **75% 偏 taken** 的分支 —— 4 条里 3 条要跳，
命中率不到一半意味着**一半以上的 taken 拿不到目标**，这是要花钱的（每次都要等）。

类 3 的目标预测也差 22.50pp，但它的方向问题（36.72pp）更大、且已判定为结构性。

**结论（修正后的优先级）**：目标预测这条线上，**类 5 > 类 3 >> 类 4**。

### 3.5 定向实验：C910 到底靠什么拿到 86.72%

原结论里"因为 C910 用了 GHR"只是推断。补做了三件事，前两件把它坐实，第三件推翻了我
对自研侧的判断。

#### (1) RTL：历史直接参与选表（结构性事实，不是推断）

`ct_ifu_bht.v`：

```verilog
//1411  //Predict Array offset = vghr[3:0] ^ pc[7:4]
//1415  assign pre_offset_if_0[3:0] = pcgen_bht_ifpc[6:3] ^ pre_vghr_offset_0[3:0];
//1430    pre_vghr_offset_0[3:0] = rtughr_reg[3:0];   // retire 校准过的 GHR
//1432    pre_vghr_offset_0[3:0] = bju_ghr[3:0];      // 推测 GHR
// 391  bht_pred_array_rd_index = {vghr[12:9], {vghr[8:3]^vghr[20:15]}};  // 读地址也是 GHR 造的
```

预测表项的索引 = **`PC[6:3] ^ GHR[3:0]`**，读地址也由 GHR 拼出。**历史在预测路径上，
这是读 RTL 读出来的，不需要行为实验去推。**

#### (2) 行为：类 3 内部逐条分支（新增 per-branch-PC 计数）

按 gshare 机制可以给出**可证伪的定量预测**：branch1（`0x83c`）之前的 4 位历史全来自
类 2（恒不跳、恒定），索引不随相位变 ⇒ 只能 50%；branch2 起历史里含同轮的 T ⇒ 应接近 100%。

实测 C910 侧：

| 类 | pos1 | pos2 | pos3 | pos4 | pos5 | pos6 | pos7 | pos8 |
|---|---|---|---|---|---|---|---|---|
| 3 交替 | **50.00%** | 99.61% | 99.61% | 99.61% | 99.61% | **50.00%** | 99.61% | 99.22% |
| 5 T,T,T,N | **74.41%** | 99.02% | 99.02% | 98.83% | 98.83% | 99.02% | **74.41%** | 99.02% |

**50.00% 是任何"每-PC 计数器"在严格交替序列上的理论上限**（实测 256/512，一个不差）；
74.41% 对应 T,T,T,N 上"恒预测 taken"的 75% 上限。同一个类、同样 16 字节间隔、逐条
分支的结局序列完全相同，却出现**两种截然不同的行为** —— 好的那些（6/8 条到 99.6%）
**超出了每-PC 计数器的能力上限**，只能来自历史。结论成立。

> **没解释清楚的部分（如实记录）**：为什么恰好是 pos1/pos6（类 5 是 pos1/pos7）落在
> 计数器行为上。pos1 能解释 —— 它之前的 4 位历史全来自上一类（类 3 前面是类 2 的恒不跳、
> 类 5 前面是类 4 的恒定控制转移），索引恒定、只有一个计数器。**pos6/pos7 的历史是变化的，
> 解释不了**，猜测是 XOR 索引的别名冲突，**未验证**。

#### (3) 推翻：自研侧的 BHT 是**同一个结构**，GHR 也是活的

我原先的说法（"自研侧没有把这层相关性用起来"）暗示两边机制不同。**这是错的。**

- `rv32_ifu_bht.v:374-394` 与 `ct_ifu_bht.v` **逐字同源**：同样的注释、同样的
  `pc[6:3] ^ vghr[3:0]` 索引公式、同样的 `{vghr[12:9], ...}` 读地址。
- `pre_vghr_offset_0` 在自研侧有完整驱动（`rv32_ifu_bht.v:1200-1212`），pre-array
  （`rv32_ifu_bht_pre_array`）也真的例化了。
- **实测 GHR 是活的**（在 TB 里挂探针，branch_bench 下）：

  | 探针 | 实测 |
  |---|---|
  | `vghr_q` 非零拍数 | 177,084 |
  | `vghr_q` 发生变化的拍数 | **47,806** |
  | `pre_vghr_offset_0` 非零拍数 | 146,935 |

**所以真正的差异被收窄成一条具体现象**：类 3 的 8 条分支在自研侧 **4096 次里一次
taken 都没预测出来**（`预测 taken (BHT) = 0`），准确率 50%。而这不是"2 位计数器在
50/50 输入下的正常表现" —— 正常的饱和计数器在交替输入上会在 01/10 之间摆动，
**至少有一半的拍会预测 taken**，准确率也还是 50%。**一个 taken 都预测不出来，
说明这个计数器是被"摁"在 not-taken 上的，不是正常工作。**

已排除的嫌疑：

| 嫌疑 | 结论 |
|---|---|
| GHR 卡死在 0 | **否**，47,806 次变化 |
| pre-array 没例化 / 被砍掉 | **否**，`rv32_ifu_bht_pre_array` 在 |
| BHT 索引的 PC 位段对不上 | **否**，两边换算后都是 `PC[13:4]`（miniRV `pc_bus` 是字节 PC 取 `[13:4]`；C910 `pc_bus` 是 >>1 PC 取 `[12:3]`）|

#### (4) 根因：GHR 被"预测"喂，在 50/50 上自锁

接着往下查，机制拼出来了。**先说清楚哪些是实测、哪一步是推理。**

**推理的起点**：一个 2 位饱和计数器在 T,N,T,N 上从 00 出发只在 00↔01 之间摆，
`bit1` 恒为 0 ⇒ **恰好 0 次预测 taken**，准确率恰好 50%。这正是实测到的
（0/4096，50.00%，一个不差）。反过来，若历史项真的随相位改变选表，两组计数器会
分别饱和到 11 和 00 ⇒ 会大量预测 taken 且准确率接近 100%。**所以实测数据本身就
证明了一件事：类 3 这些 PC 的计数器选择不随相位变。**

**链子**（每一环都有实测）：

| 环 | 实测 |
|---|---|
| GHR 最新一位来自**预测**而非结果 | `rv32_ifu_ipctrl.v:123` `bht_taken = last_packet[122]`（packet 带下来的 IF 级预测位）；对照 C910 `ct_ifu_ipctrl.v:1960` `ipctrl_bht_con_br_taken = bht_result` |
| GHR 确实被"预测"填满 | `vghr_q[3:0]` 分布：**== 15 占 115,205 拍（64%）**，== 0 占 32,491 拍（18%），其它 31,870 拍 —— 82% 的时间整段全 0 或全 1，这正是"喂预测"的指纹（预测绝大多数是 taken） |
| 类 3 执行期间 GHR 最新位被摁在 0 | `vghr_q[3:0]` 出现过 8 个值 {0,2,4,6,8,12,14,15}，**8 个里 7 个最低位是 0** |
| 于是 `pre_offset = PC[7:4] ^ GHR[3:0]` 退化成常数 | `vghr_q[3:0]=0` ⇒ 索引 = `PC[7:4]`，每根分支一个固定计数器 |

**自锁闭环**：预测恒 not-taken → GHR 低位填 0 → 选表项不变 → 单计数器在 00↔01 摆
→ 预测恒 not-taken → 回到起点。**50/50 恰好是唯一没有恢复力的点**：只要有偏置，
计数器就会饱和到一端、预测变对、GHR 被填成另一端、索引重新分开，自己就解开了。

这与**全部**实测吻合，包括为什么只有类 3 坏：

| 类 | 锁到 | 结果 |
|---|---|---|
| 1 回边（偏 taken 98%）| taken，GHR 填 1，计数器饱和 11 | 99.5% 预测 taken，准确率高 ✓ |
| 2 恒不跳 | not-taken | 100% ✓ |
| 5 T,T,T,N（偏 taken 75%）| 偏 taken，GHR 大多是 1、偶尔 0 | 索引会变 ⇒ 部分解锁，89.31% |
| **3 交替（50/50）** | **not-taken** | **无恢复力 ⇒ 死锁，50.00%** |

**定量根因：GHR 有 94% 是"预测的历史"，不是"结果的历史"。**

继续测"解锁通路"（mispredict 时用 `{bju_ghr[20:0], iu_ifu_bht_condbr_taken}`
注入**真实结果**）—— **它是活的**：`ghr_updt_vld && check_vld` 共 4,262 拍，
其中注入 1 有 2,328 次、注入 0 有 1,934 次。所以不是"通路死了"，是**频率**：

| GHR 移位来源 | 次数 | 占比 |
|---|---|---|
| IP 级条件分支（**预测位** `last_packet[122]`）| 66,505 − 4,262 = **62,243** | **94%** |
| mispredict 重定向（**真实结果**）| **4,262** | 6% |

真值注入平均每 ~2 根分支才来一次，而预测移位频繁得多 —— **注入的那一位很快就被
挤出低 4 位窗口**，所以预测时刻看到的 `vghr_q[3:0]` 几乎全是预测值。对类 3，
预测锁在 not-taken ⇒ 那 4 位是 `0000` ⇒ 选表项恒定。

**这一条把五个类全解释通了**（这也是它可信的原因 —— 不是只解释类 3）：

| 类 | GHR 低 4 位 | 选表项 | 单计数器行为 | 实测 |
|---|---|---|---|---|
| 1 回边（偏 taken 98%）| 恒 `1111` | 恒定 | 饱和到 11，恒预测 taken | 99.5% 预测 taken ✓ 准确率高 |
| 2 恒不跳 | 恒 `0000` | 恒定 | 停在 00/01，恒预测 not-taken | 100% ✓（恰好对）|
| 5 T,T,T,N（偏 taken 75%）| 大多 1、偶尔 0 | **会变** | 部分跟踪 | 89.31%（部分解开了）|
| **3 交替（50/50）** | **恒 `0000`** | **恒定** | 00↔01 摆，恒预测 not-taken | **50.00%** |
| 0 其余 | — | — | — | — |

**共同点**：这个预测器退化成了"每-PC 计数器 + 恒定选表"。**偏斜分支上它够用**
（类 1/2 照样高分），**只有 50/50 才暴露**。C910 的类 3 能到 86.72%，正是因为
它的选表项真的随相位在变。

顺带排除"GHR 多移"：`bht_event` 独立事件 54,077 次 + mispredict 重定向 4,262 次
≈ 57,858 根分支，对得上。

#### (5) 收口：差异在 GHR 的「喂料」，不在 BHT 代码

上一节留下的疑问是"C910 结构看起来逐行相同却没退化"。**在 C910 上做同一套测量后，答案清楚了。**

同一份探针挂在两边的 BHT 上（C910: `x_ct_ifu_bht`，miniRV: `u_bht`）：

| GHR 移位来源 | C910 | miniRV | 性质 |
|---|---|---|---|
| `ghr_updt_vld`（mispredict 注入真实结果）| 2,770 | 4,262 | 真值 |
| **`vghr_lbuf_updt_vld`（LBUF 复放的真实结局）** | **51,130** | **0** | **真值** |
| `vghr_ip_updt_vld`（IP 级条件分支的**预测位**）| 47,917 | 66,505 | 自指 |
| LBUF 活跃拍数 | 52,660（46%）| 0 | — |
| **真实结果占比** | **约 53%** | **约 6%** | — |

C910 的第三条通路喂的是 `ct_ifu_lbuf.v:6464 lbuf_bht_con_br_taken = lbuf_pop_con_br_taken`
—— **环路缓冲复放时记录的该条件分支的真实结局**，不是预测。

**miniRV 这条通路被硬接死了。** `rv32_ifu_top.v:1360-1362`：

```verilog
    .lbuf_bht_active_state             (1'b0),
    .lbuf_bht_con_br_taken             (1'b0),
    .lbuf_bht_con_br_vld               (1'b0),
```

**定向验证（否定结果，但正是否定才定位准）**：把 `mySoC/ifu_subsys.v:37` 的
`LBUF_EN` 从 0 改成 1 重跑 —— `lbuf_bht_active_state` **仍是 0**、
`vghr_lbuf_updt_vld` **仍是 0**、类 3 **仍是 50.00%**。
说明这不是开关问题，是**顶层常量接死**。实验做完已还原（`git diff` 为空）。

另外核对过：mispredict 恢复用的 `bju_ghr` 两边也**逐字相同**
（`assign bju_ghr[21:0] = iu_ifu_chk_idx[21:0]`，即预测时刻的 GHR 快照），
所以差异确实只剩 LBUF 这一处。

**结论链**：miniRV 的 GHR 有 94% 由**预测位**喂 ⇒ 预测锁死时 GHR 也锁死
⇒ `pre_offset` 恒定 ⇒ 每根分支只有一个 2 位计数器 ⇒ 50/50 上恒预测 not-taken。
C910 有一多半的移位来自真实结局 ⇒ GHR 锚在现实中 ⇒ 锁不住。

#### (6) 闭环实验：按 (5) 的建议改了一遍 —— **假设被推翻，已回退**

(5) 给出的修法是"把每条条件分支在 BJU 校验出真实结局时也更新 GHR"，代价估计"几十行、
预期 +2~3pp"。**照做并实测，结果是否定的。**

改法（`rv32_ifu_bht.v`，2 行）：把 GHR 那条通路的选通与载荷从预测位换成真实结局 ——

```verilog
// 原: assign vghr_ip_updt_vld = cp0_ifu_bht_en && ipctrl_bht_con_br_vld;
//     vghr_q <= {vghr_q[20:0], ipctrl_bht_con_br_taken};      // 预测位
   assign vghr_ip_updt_vld = cp0_ifu_bht_en && iu_ifu_bht_check_vld;
   vghr_q <= {vghr_q[20:0], iu_ifu_bht_condbr_taken};          // 真实结局
```

用 `check_vld` 替换 `ipctrl_bht_con_br_vld` 当选通（实测 57,858 次 = 条件分支总数，
比原来的 66,505 更接近真实分支数），**不新增通路**，避免同一根分支被移两次。

**A/B（branch_bench，`+BENCH`）**

| 指标 | 基线 | 改后 | |
|---|---|---|---|
| 类 3 准确率 | 50.00% | **50.00%** | **没变** |
| 类 1 准确率 | 96.07% | 94.95% | **-1.12pp** |
| 类 5 准确率 | 89.31% | 83.25% | **-6.06pp** |
| 类 3 预测 taken | 0 | 508 | 预测**变了** |
| 周期数 | 179,585 | **185,099** | **+3.1%** |
| difftest | Pass | Pass | 功能仍正确 |

**判定：假设推翻，改动已回退**（`git diff` 为空，基线逐位复现 179,585 / 96.07 / 50.00 / 89.31）。

**这个否定结果本身很有信息量：**

1. **类 3 从"系统性预测 not-taken"变成了"预测有变化但无信息"** —— 预测 taken 的次数从 0
   变成 508，准确率却仍然恰好 2048/4096。说明喂真实结局**没有给这个场景增加任何信息量**，
   只是把"恒错"换成了"随机"。
2. **类 1/类 5 反而退化 + 周期 +3.1%**，最可能的原因是**流水线偏斜**：GHR 必须在
   **IF 级预测时刻**是正确的；把更新点从 IP 挪到 EX（BJU 校验）晚了 2 级，GHR 的最新的
   4 位变成"往前错 2 根分支"，窗口错位。
3. **C910 的 LBUF 之所以管用，正是因为它绕开了这个偏斜** —— 环路缓冲在 **IF 级复放**，
   记录的真实结局在**正好需要的那个流水点**上可用。BJU(EX) 时刻的真值再准也来晚了。

**修正 (5) 里的建议**：我先前说这是"几十行局部改动、预期 +2~3pp"，**这个估计是错的**。
要真正修好类 3，需要的是：

- (a) **让 LBUF 工作**（IF 级复放 + 记录结局），或
- (b) **换一种不依赖"GHR 在预测时刻准确"的机制**（比如每条分支带自己的局部历史、
  或把选表项从 GHR 改成"分支自己的历史"）。

两者都不是小改动。**所以 P1 的优先级应当回到 §4.1 那条（L0 容量），类 3 归为结构性课题**，
不要再当成"顺手就能拿的 +3pp"。

**仍未做的验证**：以上是"机制一致 + 差异巨大且方向正确"的强证据，但**没有做
"注入真值后类 3 立刻变好"的闭环实验**（那需要改 RTL 而不是挂探针）。建议作为 P1 的第一步。

**下一步（按优先级）**：
1. 验自研侧 mispredict 解锁通路：在 `ghr_updt_vld && iu_ifu_bht_check_vld` 那一路挂计数，
   看类 3 期间有没有真的注入过 `iu_ifu_bht_condbr_taken`。
2. 在 `rv32_ifu_bht.v:1227/1234`（`pre_vghr_offset_1` / `pre_offset_onehot_ip`）挂探针，
   直接验证"类 3 相位翻转时选中的计数器不变"。
3. 若确认是自锁：**最小修法是把 GHR 改为由解析出的真实结果驱动**（或在 mispredict 时
   强制注入真值），而不是由预测位驱动。

### 3.6 定向实验（续）：预测时刻四元组，以及两次被实测否掉的修法

§3.5 的最后一步是"在预测时刻直接量 (行地址, 片内偏移, 平面选择, 计数器值)"。
做完了，结论很干净；据此试的两个修法**都被实测否掉**。

#### (1) 测量：类 3 与类 5 的对照

在 IP 级条件分支有效那一拍采四元组，按类内位置分桶（TB 探针，`+BENCH` 门控）：

| 类 3（50.00%，坏）| `oh` 取值数 | `sel[1]` | 计数器 00 / 01 / 10 / 11 |
|---|---|---|---|
| pos1 `0x1d0` | **仅 1 个** | 0 | 257 / **255** / 0 / 0 |
| pos2 `0x1e0` | 2 | 0 | 768 / 0 / 0 / 0 |
| pos3 `0x1f0` | 3 | 0 | 769 / 255 / 0 / 0 |
| pos4 `0x200` | 3 | 0 | **1024 / 0 / 0 / 0** |
| pos5 `0x210` | 3 | 0 | **1024 / 0 / 0 / 0** |
| pos6/7/8 | 3 | 0 | 769 / 255 / 0 / 0 |
| **类 5（89.31%，好）** | 2~4 | **1** | **全是 11（饱和 taken）** |

**`10` 与 `11` 在类 3 全部 8 条分支上一次都没出现过。**

三条硬结论：

1. **pos1 的偏移只有一个取值** ⇒ 历史项根本没到达这条分支，退化成纯每-PC 计数器。
   实测 257/255 的 00↔01 对半分布，正是 2 位计数器在严格交替上的教科书行为
   —— 一个不差的 50%。
2. **类 3 恒读 ntake 平面（`sel[1]=0`），类 5 恒读 taken 平面（`sel[1]=1`）。**
   而 pre-array 的初始化值是 **taken 平面 = `2'b11`、ntake 平面 = `2'b00``。
   两边报出来的都基本是**初始值**：类 5 报"恒 taken"（在它 75% 偏 taken 的底线上再涨到
   89.31%），类 3 报"恒 not-taken"（恰好 50.00%）。
3. **pos4/pos5 是 1024/1024 全 00** —— 从未被写过（00 收到 taken 更新应变成 01）。

#### (2) 据此试的修法 A：接通 `pcgen_bht_chgflw` —— **否定，已回退**

`rv32_ifu_top.v:246-247` 早就声明了 `pcgen_bht_chgflw` / `_short`，`:821-822` 也被
`u_pcgen` 驱动，只是 `:1364-1365` 没接到 bp_top（接了 `1'b0`）。C910 里是接通的。
**这是纯接线疏漏，接上即可** —— 于是接上实测：

| | 基线 | 接通后 |
|---|---|---|
| 类 1 | 96.07% | 95.28% |
| 类 5 | 89.31% | **80.32%** |
| 类 3 | 50.00% | 50.00% |
| 周期 | 179,585 | **186,398 (+3.8%)** |

**退化，已回退。** 说明 C910 的 `pcgen_bht_chgflw` 语义依赖 LBUF 驱动的取指模式，
单独接过来只会让选择阵列在错误的时机重读。

#### (3) 据此试的修法 B：接通 LBUF 三根线 + `LBUF_EN=1` —— **灾难性否定，已回退**

把 `lbuf_bht_active_state` / `lbuf_ifctrl_active` / `lbuf_pcgen_active` 都接到
`lbuf_active`，并打开 `LBUF_EN`：

- `lbuf_bht_active_state` **998,457 拍常高**；
- 条件分支只执行了 **131 条**（正常 57,858）—— **前端被卡死**。

**结论：自研侧的 LBUF 本身就不工作**（`active` 一旦进入就再也不撤），
不是"接上线就能用"。这与 §3.5(5) 的静态结论一致（那 149 行是独立重写、没有 BHT 接口）。

#### (4) 这一步的最终判定

C910 范本里唯一在实测上与本问题对得上的机制（LBUF 把记录的**真实结局**按 IF 节拍
喂给 GHR）**在自研侧无法通过接线或小改达成**：接口从来没设计过，而且 LBUF 本体也不工作。
要落地等于先修好 LBUF、再补 1000+ 行的 pop/retire 握手与逐条分支结局记录。

**因此类 3 归为结构性课题，不在本轮投入**；建议转向 §4.1 的 L0 容量课题。

## 4. 对自研 IFU 的含义

1. **类 3 的 50% 是真实且低成本的改进点**，而且 §3.5 把它定位得很窄了：
   **不是"没有历史机制"（机制在、GHR 也活），而是这个场景下选中的计数器被摁在
   not-taken 上（4096 次里 0 次预测 taken）。** 这比 §6.4 里"准确率 ≥88.5%"那个
   目标具体得多：**先查清类 3 的计数器为什么一次 taken 都不出**。
2. **类 1/2/4 已经没有改进空间**（95.7~100%），P1 的收益不应寄希望于它们。
3. **不要把 C910 的 L0 命中率当成对标目标**。C910 的 L0 命中里 96% 是返回地址，
   它的条件分支目标是另一级 BTB 给的；自研核只有这一张 16 项表，
   想提命中率只能**加表项**（与 `bp_change_log_zh.md` §4.1 的结论一致）。
