## 1. 一切的前提：取指必须“赌”，不能“等”

超标量前端每个周期要吃进一个 16 B 块（4 条 RV32I 指令），而分支的真实方向要到执行级才知道。如果前端选择“等到结果再取”，那么每遇到一条分支就损失数十个周期的取指带宽；实测程序平均每 5～7 条指令一条分支，这等于让前端大部分时间在等。

于是整个设计只剩一个选择：**在取指时就猜，并且保证猜错能被精确撤销**。这一句话派生出全部结构：

```text
猜得越早 → 错误路径上白取的指令越少，但可用信息越少（信息少 → 表要小、要快、要简单）
猜得越晚 → 信息多（已译码、已知是哪种控制流），但只对“后面还没取的部分”有用
⇒ 不能只在一个阶段猜，于是形成 IF → IP → IB → 后端校验的多级阶梯
```

**判据**：任何一级预测器只要“比不猜好”就值得存在，不需要它自己解决所有分支。这是理解下面所有“为什么”的总纲——本设计里的每个结构都在回答“我在哪一级、用我手上那点信息，能多正确一点吗”。

## 2. RV32I 控制流与前端相关指令详解

本节是 ISA 速查 + 前端视角。预测器只关心五类东西：六种条件分支、JAL、JALR、AUIPC，以及“哪些 rd/rs1 是链接寄存器”；其余指令对前端来说都是“顺序走”。

### 2.1 前端看得见哪些字段

RV32I 所有指令都是 32 位定长。字段位置与格式有关：

| 格式 | 用途 | bit31 | 30..25 | 24..20 | 19..15 | 14..12 | 11..7 | 6..0 |
|---|---|---|---|---|---|---|---|---|
| R | 寄存器-寄存器运算 | funct7 | — | rs2 | rs1 | funct3 | rd | opcode |
| I | 立即数运算、load、JALR | imm[11:0] | — | — | rs1 | funct3 | rd | opcode |
| S | store | imm[11:5] | — | rs2 | rs1 | funct3 | imm[4:0] | opcode |
| B | 条件分支 | imm[12] | imm[10:5] | rs2 | rs1 | funct3 | imm[4:1]（bit11..8）、imm[11]（bit7） | opcode |
| U | LUI、AUIPC | imm[31:12]（跨越 bit31..12 全部五列） | ↑ | ↑ | ↑ | ↑ | rd | opcode |
| J | JAL | imm[20] | imm[10:1]（bit30..21） | imm[11]（bit20） | imm[19:12]（bit19..12） | ↑（bit14..12 同属 imm[19:12]） | rd | opcode |

**预测器实际用到的只有**：`opcode[6:0]`、`funct3[14:12]`（仅条件分支和 JALR 有）、`rd[11:7]`、`rs1[19:15]`（仅 JAL/JALR 用于 call/return 提示）、以及立即数位。

**完全不需要**：`rs2[24:20]`、`funct7[31:25]`、以及任何操作数内容。也就是说，“这条分支是 BEQ 还是 BGEU”“这条 ALU 指令是 ADD 还是 SUB”对预测器毫无影响——它只判断“跳/不跳”，不判断“为什么跳”。注意 JAL 与 AUIPC **没有 funct3 字段**：那些位属于立即数（JAL 的 bit14:12 是 imm[14:12]，AUIPC 的 bit14:12 是 imm[14:12]），所以“funct3 任意”这种说法并不准确。

### 2.2 六种条件分支

| 助记符 | funct3[14:12] | 条件（rs1 与 rs2 比较） | 有无符号 |
|---|---|---|---|
| BEQ | `000` | rs1 == rs2 | — |
| BNE | `001` | rs1 != rs2 | — |
| BLT | `100` | rs1 < rs2 | 有符号 |
| BGE | `101` | rs1 >= rs2 | 有符号 |
| BLTU | `110` | rs1 < rs2 | 无符号 |
| BGEU | `111` | rs1 >= rs2 | 无符号 |

- `funct3 = 010` / `011` 是**保留编码**（早期草案曾用作 BLTZ/BGEZ，现行规范不再定义），配 opcode `1100011` 时不是控制流，必须作为非法指令流向 IDU。
- RTL 里的判据就是这一条的位级写法：`inst[6:0]==7'h63 && (inst[14:12]==3'b000 || inst[14:12]==3'b001 || inst[14])`。最后那个 `inst[14]` 一位就覆盖了 `100`/`101`/`110`/`111` 四种（它们的高位都是 1），加上 `000`/`001` 正好是六种合法分支——这种写法在 C910 里很常见，读 RTL 时要能一眼还原。
- **六种分支对预测器是同一类**：方向预测只看“跳/不跳”，目标只由立即数决定。有符号/无符号的差别只影响执行级（BJU）的条件计算。

**汇编器伪指令**：你在反汇编里看到的 `beqz/bnez/...` 都会展开成上面六条真指令，很多还带操作数交换：

| 伪指令 | 展开为 | 备注 |
|---|---|---|
| `beqz rs, L` | `beq rs, x0, L` | 与零比较 |
| `bnez rs, L` | `bne rs, x0, L` | |
| `bltz rs, L` | `blt rs, x0, L` | |
| `bgez rs, L` | `bge rs, x0, L` | |
| `blez rs, L` | `bge x0, rs, L` | **操作数交换** |
| `bgtz rs, L` | `blt x0, rs, L` | **操作数交换** |
| `bgt rs, rt, L` | `blt rt, rs, L` | **操作数交换** |
| `ble rs, rt, L` | `bge rt, rs, L` | **操作数交换** |
| `bgtu rs, rt, L` | `bltu rt, rs, L` | **操作数交换** |
| `bleu rs, rt, L` | `bgeu rt, rs, L` | **操作数交换** |

交换操作数意味着“汇编里第一个出现的寄存器”未必是 `rs1`。这对方向/目标预测没有影响，但如果将来要基于操作数做别的提示（例如与零比较的偏置统计），必须按**真实字段**判断，而不是按源文本顺序。

### 2.3 立即数拼装：B 型与 J 型（逐位）

RISC-V 故意把 B/J 型的立即数位**打散**，理由有两个：让 `inst[31]` 在所有含立即数的格式（I/S/B/U/J）里都是符号位，符号扩展只需看一位；并让各格式的立即数位尽量落在相同位置，减少译码硬件。代价是拼装看起来“乱”。

```text
B 型（条件分支，目标范围 ±4 KiB，立即数 bit0 恒为 0 不编码）
 bit  31      30..25    24..20 19..15 14..12  11..8    7       6..0
      imm[12] imm[10:5]  rs2    rs1   funct3  imm[4:1] imm[11]  opcode
        ↑符号位                 ↑六种    ↑位1..位4  ↑位11
目标 = PC + sext13({imm[12], imm[11], imm[10:5], imm[4:1], 1'b0})

J 型（JAL，目标范围 ±1 MiB，立即数 bit0 恒为 0 不编码）
 bit  31      30..21      20      19..12       11..7  6..0
      imm[20] imm[10:1]  imm[11] imm[19:12]    rd     opcode
        ↑符号位  ↑位1..位10  ↑位11   ↑位12..位19
目标 = PC + sext21({imm[20], imm[11], imm[10:1], imm[19:12], 1'b0})
```

**算例**（把字段和拼装对着看一遍就记住了）：`bne x5, x0, -8`，位于 PC = `0x8000_1000`。

```text
offset = -8 → 13 位补码 = 1_1111_1111_1000
  imm[12]=1  imm[11]=1  imm[10:5]=111111  imm[4:1]=1100  imm[0]=0
字段落位：
  inst[31]=1  inst[30:25]=111111  inst[24:20]=00000(x0)  inst[19:15]=00101(x5)
  inst[14:12]=001(BNE)  inst[11:8]=1100  inst[7]=1  inst[6:0]=1100011
RTL 的拼装（bp_decode）：
  {inst[31], inst[7], inst[30:25], inst[11:8], 1'b0} = 1_1_111111_1100_0
  = 13'b1_1111_1111_1000 = 0x1FF8 = -8 ✓
目标 = 0x8000_1000 + (-8) = 0x8000_0FF8
```

| 类型 | 立即数位宽 | 目标 | 范围 | 前端能否直接算 |
|---|---|---|---|---|
| B（六种条件分支） | 13 位有符号（bit0 隐含 0） | `PC + imm` | ±4 KiB | **能** |
| J（JAL） | 21 位有符号（bit0 隐含 0） | `PC + imm` | ±1 MiB | **能** |
| I（JALR） | 12 位有符号 | `(rs1 + imm) & ~1` | ±2 KiB + 寄存器值 | **不能**（缺 rs1） |
| U（AUIPC） | 20 位（占 bit31:12，低 12 位为 0） | `PC + sext20(imm) << 12` | ±2 GiB（4 KiB 粒度） | **能** |

**为什么条件分支必须预测**：目标是算术（前端有立即数即可算），但方向取决于两个操作数的比较结果，前端拿不到操作数。所以前端能算出“如果 taken 会跳到哪里”，却完全不能判断“到底跳不跳”——这正是 BHT 存在的唯一理由。范围只有 ±4 KiB 也意味着一次 `bne` 只能跳到附近，远距离跳转必须由两条指令（`auipc` + `jalr`，见 §2.6）或跳转表完成。

**为什么 JAL 也仍然需要表**：JAL 的目标确实是纯算术，但它恒定 taken；前端在**译码前**并不知道某个位置是不是一条 JAL，所以仍然需要一个“这里有一条控制流、目标是 X”的表（BTB）来在取指当拍改向。译码之后（IP 级）当然可以直接算，但那时已经晚了一拍。

**为什么 JALR 的表是另一张**：它的目标依赖寄存器值，前端**永远算不出来**，只能记忆“上次从这里跳到了哪”。

**为什么 AUIPC 特殊**：它不改变取指流，所以不进 L0、不产生方向预测、不追加历史；但它的结果依赖自身 PC，所以后端需要它的 PC 才能校验/修正——这就是它被归入 `pc_oper`（PC 相关操作）的原因。把“PC 相关”和“改控制流”当成同一件事，是这类设计里最常见的概念混淆。

### 2.4 JAL / JALR / AUIPC 的用法与变体

**JAL**：`jal rd, offset`

| 写法 | 含义 |
|---|---|
| `jal x1, func` | 直接调用：跳到 func，返回地址 PC+4 写入 x1 |
| `jal offset`（省略 rd） | 等价 `jal x1, offset`，汇编器默认 rd = x1 |
| `j offset` | 等价 `jal x0, offset`：**不写返回地址**的纯跳转（rd=x0 时不写回） |

**JALR**：`jalr rd, rs1, imm` 或 `jalr rd, imm(rs1)`

| 写法 | 含义 |
|---|---|
| `ret` | `jalr x0, 0(x1)`：标准返回，不写回 |
| `jr rs1` | `jalr x0, 0(rs1)`：间接跳转（跳转表、函数指针尾调用） |
| `jalr rs1` | `jalr x1, 0(rs1)`：通过寄存器调用，写返回地址到 x1 |
| `jalr x5, 0(x5)` | 用第二链接寄存器的间接调用（协程风格） |
| `jalr x1, 0(x1)` | 合法但少见：以“当前 x1 的值”为目标再写回 x1；本版按 §2.5 表格最后一行的保守规则处理 |

**AUIPC**：`auipc rd, imm20`，`rd = PC + sext20(imm20) << 12`

| 典型组合 | 用途 |
|---|---|
| `auipc rd, %pcrel_hi(sym)` + `addi rd, rd, %pcrel_lo(label)` | 取符号的 PC 相对地址（位置无关代码） |
| `auipc rd, ...` + `jalr x1, ...(rd)` | **远距离调用**（超出 `jal` 的 ±1 MiB 时） |
| `auipc rd, ...` + `jalr x0, ...(rd)` | **远距离尾调用**（`tail`），不返回 |
| `auipc rd, ...` + `lw/sw` | 访问全局变量（`medany` 代码模型） |

### 2.5 链接寄存器与 call/return 约定

RV32I **没有专门的 call/return 指令**：它们只是 `jal`/`jalr` 恰好把返回地址写进了链接寄存器。

- `x1`（ABI 名 `ra`）是标准链接寄存器；`x5`（ABI 名 `t0`）可作**第二链接寄存器**（协程、部分编译器/运行库会用）。
- 判定规则：`rd ∈ {x1,x5}` → 这是一次“调用”；`rs1 ∈ {x1,x5}` → 这是一次“返回”。**只有 JAL/JALR 参与这个判定**；条件分支的 rs1/rs2 与提示无关。

| rd（写回寄存器） | rs1（基址寄存器） | 提示分类 | 能否直接用 RAS 旧栈顶当目标 |
|---|---|---|---|
| 非 x1/x5 | 非 x1/x5 | 都不是 | — |
| x1/x5 | 非 x1/x5 | 调用（push） | — |
| 非 x1/x5 | x1/x5 | 返回（pop） | 仅当 `imm == 0` 时可用 |
| x1/x5，且 rd ≠ rs1 | x1/x5 | 调用 + 返回（push 覆盖被弹出的项，深度不变） | 仅当 `imm == 0` 时可用 |
| x1/x5，且 rd == rs1 | x1/x5 | 本版只按“调用”处理 | **不可用**（保守：不声称旧栈顶有效，落到 IND BTB） |

“提示分类”与“能否直接用旧栈顶当目标”是**两个不同的决定**：即使确认这是一次返回，如果 `imm ≠ 0`（例如 `jalr x0, 8(x1)`），真实目标并不等于栈顶，所以只能把提示交给 IND BTB 去学。最后一行是本版实现相对 v3.1 规格表的保守处理，原因是 rd 与 rs1 是同一个链接寄存器时，无法在不引入额外状态的前提下证明栈顶与返回目标一致。

### 2.6 你在真实代码里会看到的四种序列

**① 直接调用与返回**（最常见，RAS 的主要受益者）

```asm
    jal   x1, func            ; 调用：提示 push，返回地址 = PC+4
    ...
func:
    ...
    jalr  x0, 0(x1)           ; ret：提示 pop，目标来自 RAS 栈顶（imm==0）
```

**② 远距离调用 / 函数指针调用**（间接预测的受益者）

```asm
    auipc x1, %pcrel_hi(func) ; 目标地址的高 20 位
    jalr  x1, %pcrel_lo(lbl)(x1)  ; 目标 = x1 + 低位立即数
```
这里 `jalr` 的 rd = rs1 = x1，属于 §2.5 表格最后一行：本版按“调用”处理、不直接使用 RAS 栈顶，目标由 IND BTB 学习。**注意：即使这是一次“调用”，前端也不知道目标**——它依赖前面那条 `auipc` 的执行结果（其实前端可以顺着算出来，但那需要把两条指令关联起来，本版不做这件事）。

**③ 循环**（BHT 的受益者）

```asm
loop:
    addi  x5, x5, -1
    bne   x5, x0, loop        ; 前 N-1 次 taken、最后一次 not taken
```
这类分支的方向由“当下处于第几次迭代”决定；用 1 条只表达偏置的计数器预测，最坏情况是每次退出都错一次。历史能记住最近几次的方向序列，从而把循环退出预测得比较准——这就是 BHT 需要 22 bit 历史的实际理由之一。

**④ 跳转表 / switch**（IND BTB 的主要受益者）

```asm
    slli  x6, x7, 2           ; 索引 ×4
    auipc x5, %pcrel_hi(jt)
    addi  x5, x5, %pcrel_lo(jt)
    add   x5, x5, x6
    lw    x5, 0(x5)
    jr    x5                  ; jalr x0, 0(x5)：多态间接跳转
```
同一条 `jr` 指令会跳到表里任意一项，**目标随索引变化**。纯用 PC 索引的预测器在这里没有信息可用；用“最近的间接控制流路径 + 历史”做索引才能区分不同 case 的去向（§8）。

### 2.7 对齐与非法编码

- 本版 IALIGN = 32（不实现 C 扩展），所有指令地址必须是 4 字节对齐，即 `PC[1:0] == 0`。
- `jal`/条件分支的编码里 bit0 隐含为 0，但 **bit1 是编码里真实存在的位**：如果目标算出来 `bit1 == 1`，这是一次非对齐跳转，异常（instruction-address-misaligned）**归因于源分支指令本身**，而不是“取指失败”。所以前端绝不允许“把 bit1 清零、凑一个对齐目标”来蒙混过去——那会改变程序语义、并把异常归到错误的 PC。
- `jalr` 先把结果 bit0 清 0（这是指令定义的一部分），然后再检查 bit1。
- 非法编码必须原样流向 IDU 并最终报非法指令，**不能让前端的预译码把它们吞掉或误判成控制流**。与本层相关的非法情况至少包括：

| 非法编码 | 原因 |
|---|---|
| opcode `1100011` 且 funct3 = `010`/`011` | 保留编码，不是分支 |
| opcode `1100111` 且 funct3 ≠ `000` | JALR 只定义 funct3=000 |
| opcode `1101111` 之外的“看起来像 JAL”的组合 | J 型只有这一个 opcode |

### 2.8 一句话总结

**前端能确定“跳到哪里”（除了 JALR），不能确定“是否跳”和“JALR 跳到哪里”**。三种不确定性对应三张表（BTB / BHT / IND BTB），而“返回”这一类有精确语义的控制流用栈（RAS）而不是表。

## 3. 与 TLB / Cache 结构的类比

你熟悉 TLB 与 Cache 层次，那么最快理解分支预测的办法是**先看清哪些部分真的同构、哪些部分只是看起来像**。

### 3.1 一个更根本的划分：地址类 vs 判定类

| | TLB / Cache 里的对应物 | 有没有 tag | 有没有 hit/miss |
|---|---|---|---|
| **地址类**：L0 BTB、主 BTB、IND BTB、RAS | L1 TLB / L1 Cache / L2 TLB | 有（源 PC 就是 tag） | **有**，命中判定 + 未命中兜底 |
| **判定类**：BHT 方向表 + 选择表 | 无 tag 的查值表（更像 scratchpad 或直接索引的映射表） | **没有** | **没有**：任何索引都返回一个计数器 |

**这一条决定了很多直觉能不能平移**：你在 TLB/Cache 里养成的“tag 比较 → 命中判定 → miss 处理”三段式，只适用于地址类的三张表加 RAS；把它套到 BHT 上就会凭空写出一个不存在的 miss 路径（数据流文档里特意写明“BHT 没有 hit/miss”，原因就在这里）。BHT 的正确性是**统计量**（准确率），不是结构事实（命中率）。

TLB 与 Cache 并行查询这一习惯也同样成立：TLB 给“地址在哪”，Cache 给“数据是什么”；这里 BTB/IND/RAS 给“下一条取哪里”，BHT 给“这条分支往哪走”，两组查询天然并行、互不阻塞。

### 3.2 逐个结构的类比表

| 分支预测机制 | 你熟悉的对应物 | 真正相同的地方 | 关键差异 |
|---|---|---|---|
| L0 BTB（16 项 CAM，组合比较） | **µTLB / 全相联 TLB** | 小、全相联、同拍出结果；未命中只是“慢一点”，由下一级兜底 | TLB miss 要走页表；L0 未命中什么都不发生，顺序取指即可 |
| 主 BTB（512 行 × 4 槽，tag + 同步读） | **L1 Cache**（索引 + tag + way） | 用 PC 索引、tag 比较、多路选择；way hint ≈ Cache 的路预测 | 存的不是数据而是“控制流事实”；标签相符**不代表内容仍正确**（代码改写会让项过时）→ 所以需要定向失效 |
| BTB 读出锁存、结果保持到下一次结果 | Cache 的 tag/data 流水访问 | 同步 SRAM 宏、一拍读回、结果寄存器 | Cache 的结果被消费一次即可；BTB 结果没有 ready/valid 握手，必须由 IF/IP 保证能捕获 |
| BTB 更新缓冲 + 读出旁路 | **Store Buffer + store-to-load forwarding** | 端口忙时先缓冲、读完再写；读命中同一地址时旁路最新值 | Store 不能丢（体系结构状态）；BTB 更新可以丢（只是提示） |
| BHT 方向表 | 无 tag 的查值表（直接索引） | 索引 → 取值，无比较、无替换 | 没有命中/未命中；冲突表现为**准确率下降**而不是一次 miss 事件 |
| BHT 选择表（Bi-Mode） | **两路组相联 + 路预测** | 用一个便宜的预测器决定“用哪一路”，省掉另一路的访问 | 路预测猜错有 tag 可以立刻发现；模式选择在取出时**无法验证**，只能靠后续误预测反推 |
| BHT 4 项训练缓冲 | Store Buffer（但可丢） | 吸收突发写、读路径旁路、按序写出 | 缓冲条目必须携带历史快照，否则会旁路到无关分支（见 §11） |
| IND BTB（256 项，两拍读） | **L2 TLB 的角色** | 比第一级更大更慢；第一级给不出答案时启用 | 索引不是 PC 而是“路径 + 历史”，用来区分多态间接跳转；它与主 BTB 是**并联备选**，不是严格的层间包含 |
| RAS 12 项推测 + 6 项提交 | **推测状态 vs 体系结构状态**（重命名表 vs 提交表 / checkpoint） | 一份跟着推测走、一份只在提交点更新；恢复时从提交的那份重建 | 提交份只有 6 项（不是完整影子），所以恢复范围小于推测范围——这是明确的性能折中，不是实现缺陷 |
| VGHR（推测历史） / RTUGHR（提交历史） | 推测状态 / 体系结构状态 | 一个随预测推进、一个随退休推进 | 历史**无法“重放”得到**：不能靠重新执行算出来，只能显式修复（`local_recover` / flush） |
| L0 定向失效 | 单条目失效（`invlpg` / 按 VA+ASID 匹配） | 只清一项，不整表清，代价小 | 触发者是硬件的目标校验（ADDRGEN），不是软件指令 |
| 维护 mask（5 位选择 L0/BTB/BHT/IND/RAS） | 分级维护（Cache / TLB / 预测器分别失效） | 用掩码选择范围，完成后给 done | done 的含义是“旧内容不再复活”，不是“表已清空可任意使用” |
| flush / cancel 域（前端取消、在途读作废） | 流水线 flush 与在途事务排空 | 分类处理：有的继续收尾、有的直接作废 | 预测器没有总线事务要收尾，但**历史必须修复**，不能只清 valid |
| BTB 假命中（目标错） | 路预测错 ≠ Cache miss | 可恢复、不产生重填、不改状态机 | 代价是撤销整条取指路径，远大于一次数据重发；因此允许假命中，但绝不允许伪造语义（§10） |

### 3.3 类比会在哪里误导你

1. **代价模型不同**。Cache miss 的代价是固定的内存延迟；预测失误的代价与“错得多远、流水线多深、错误路径上取了多少指令”有关，是变化的，而且**准确率是统计量**——没有“一次预测 miss”这种可计数的离散事件，只有“准确率下降”。
2. **命中 ≠ 正确**。Cache 用 tag 证明“这份数据属于这个地址”；预测表的 tag 只能证明“这条源 PC 上次指向这里”，不能证明“这次仍然如此”（代码可能被改写、上下文可能变了）。所以预测器需要**定向失效**和**恢复协议**，而 Cache 不需要。
3. **可丢弃性相反**。Cache 内容丢了下一次再取就有；预测表内容丢了要重新学习，且学习过程本身会误预测。因此失效/维护的频率对预测器是性能敏感参数。
4. **没有“容量”概念的另一面**：你无法像统计 Cache miss rate 那样统计 BHT 的冲突率，只能端到端统计准确率；所以 BHT 的设计改动（例如把 22 bit 历史改成 16 bit）**只能靠整机准确率来评估**，不能靠某个局部指标。

## 4. 为什么是五种结构，而不是一个更强的预测器

关键在于：**四类控制流的“可预测性来源”根本不同**，用一种结构同时表达四种，必然在某一种上付出很大代价。

| 控制流 | 目标从哪里来 | 方向从哪里来 | 合适的结构 |
|---|---|---|---|
| 条件分支 | 算术：PC + 立即数（前端可算） | 相关性/偏置，历史里 | 2 bit 计数器表（方向预测器） |
| JAL | 算术：PC + 立即数 | 恒 taken | 直接目标表（BTB）即可 |
| JALR（间接） | 寄存器值，**前端拿不到** | 恒 taken | 只能“学”出来的表（IND BTB） |
| 返回（`jalr x1,0(x1)`） | 与调用点一一对应 | 恒 taken | 栈：语义精确，不需要学 |

- **JAL / 条件分支的目标是纯算术**，前端有立即数就能算，所以不需要“存储”；需要存储的只是“这里到底有没有一条跳转、跳到哪里”，这正是 BTB 的作用（它存的是“控制流知识”，不是“控制流计算”）。
- **JALR 的目标是不可计算的**（依赖寄存器），这决定了它必须有一张独立的表去记忆“上次从这里跳到了哪”。把 JALR 也塞进主 BTB 是不行的：同一个 JALR 会跳到多个目标，单一目标项轮流被覆盖，命中率接近随机。
- **返回的目标有精确语义**（等于匹配 call 的下一条指令），栈天然表达这件事，而表只能“学”，且同一 PC 在多调用点下会互相污染。所以 RAS 的存在不是“多一层缓存”，而是“换一种信息表达方式”。
- **条件分支的方向是可学习的统计量**，需要历史；因此 BHT 是唯一需要“历史 + 计数器”的结构，也是唯一需要长历史寄存器的结构。

**推论**：结构数量多不是复杂度失控，而是因为每类控制流的最优表达方式不同。反过来说，如果只实现 RV32I 就想砍掉 IND BTB 或 RAS，等于宣布“返回和间接跳转不做预测”，那是性能决策，不是 ISA 裁剪决策。

## 5. 为什么分四级改向：早 vs 准的阶梯

| 级 | 手上有什么信息 | 能做什么预测 | 为什么放这一级 |
|---|---|---|---|
| IF（L0 BTB） | 只有 PC | 块内最早 taken 目标 + 类型 + Way 提示 | 与阵列访问同拍给出，**同拍改向**，代价最小 |
| IP（BHT 方向 + BTB + IND） | 已译码，已知块内有哪些分支 | 每条条件分支的方向、直接目标、间接目标 | 信息够了，但结果晚 1～2 拍 |
| IB（RAS 目标、路径推进） | 已知这是 call/return，且前缀已被接纳 | 返回目标、下一步间接索引 | 依赖“已接纳”事件，不能更早 |
| 后端（校验 + 恢复） | 真实寄存器值、真实方向 | 训练与精确恢复 | 唯一的真值来源 |

**L0 为什么可以只有 16 项？** 因为它买的是**延迟**，不是覆盖率。16 项 ≈ 16 个 16 B 块 = 256 B 代码足迹，刚好覆盖最内层循环体——而最内层循环承担了程序里绝大多数的动态分支。它覆盖率低没关系：主 BTB（512 行 × 4 槽 = 2048 目标槽，直接覆盖 8 KiB 代码）在 1～2 拍后给出更准的答案，L0 猜错由 IP/IB 校正。这就是“分级”的意义：**用小而快的结构吃掉最热的预测，用大而慢的结构兜底**。这也正是 µTLB 与 L2 TLB 的分工，只不过这里的“miss penalty”表现为“晚一拍改向”。

**为什么 IF 级还能有一个全相联的小结构？** 因为 16 项寄存器 CAM 可以做**组合比较**，而 512 行 SRAM 必须同步读。这不是容量取舍，而是电路层面的取舍：想要“同拍”，就只能承受“小”。

**L0 为什么只存 taken 项？** 条目存在的唯一目的是改向；不 taken 的分支不改变取指路径，存下来只会白白占掉 16 个位置。

**L0 为什么要求 `src[3:2] >= lookup[3:2]`？** 因为一次取指可能从块中间进入（前面几条已经取过），入口之前的控制流对这次取指不可达。

**L0 的返回项为什么不存目标、只存标志？** 因为返回目标随调用深度变化，同一个 `ret` 在不同深度返回不同地址；所以 L0 存“这里有一个返回”并用当前的 RAS 栈顶作为目标——即“存储事实”而不是“存储结果”。

**L0 为什么只允许被校验过的事件写入，而不能把早期猜测写回？** 因为一个只有 16 项的结构经不起自我确认：错误的猜测写回去，下次还会命中它，形成无法自纠的错误锁定。所以更新只来自 IP/IB/ADDRGEN 已证明的事件，并且 ADDRGEN 还有一条**定向失效**通路专门删除被证明错误的那一项。

## 6. 方向预测：为什么需要历史，为什么是 Bi-Mode

### 6.1 为什么要历史

2 bit 计数器只能表达“这条分支偏 taken 还是偏 not-taken”。但大量分支的方向取决于**前面发生过什么**（例如 `if (a && b)` 展开后的两条分支、循环退出判定、以及互斥分支对）。这类相关性只有一个地方存得下：最近若干条条件分支的真实/预测方向序列。历史长度决定能否分辨这些模式，所以 C910 用 22 bit，本版保留。

### 6.2 为什么需要“两套方向表 + 一个选择表”，而不是一张更大的表

一张表同时服务“几乎恒定的分支”和“强相关的分支”时会出现**破坏性干扰**：如果两条分支（或同一条分支的两种上下文）映射到同一个计数器，且行为相反，那么每次训练都会把对方冲掉，最终预测准确率趋近 50%——比“只按偏置猜”还差。这正是 Cache 里**冲突缺失（conflict miss）**的同构问题，只不过这里没有 tag，所以“冲突”不会被发现，只会表现为准确率下降（§3.3 第 4 条）。

Bi-Mode 的思路是**按分支的行为把它分派到两套表之一**，让每一套表只服务于“会用它”的那类分支；再用一个选择计数器（selection）学习“这条分支属于哪一类”。这就是阵列的组织方式：

```text
方向表每一行 = 16 个 taken 模式计数器 + 16 个 not-taken 模式计数器（同一行、同一位偏移）
选择表每一行 = 8 个 2 bit 选择计数器，按 PC 索引
预测 = 选择计数器挑一套表 → 该行中偏移选中的那个计数器给出方向
```

**为什么选择表按 PC 索引，而方向表按历史索引？** 因为“这条分支属于哪一类”是**分支自己的属性**（相对稳定，PC 决定），而“这次的方向”依赖**到达这里的上下文**（历史决定）。两类信息分别索引两种表，正好对应它们各自的稳定性。

### 6.3 为什么训练准入这么“绕”

方向表在饱和时停止更新（避免抖动），选择表在饱和时也停止更新，并且还有一组“模式一致/不一致”抑制条件。这些条件看起来繁琐，但它们就是 Bi-Mode 的**防污染机制**：训练一条分支时不能顺手把“另一套表”也改掉，否则两套表会退化成同一套，Bi-Mode 的意义就消失了。

本版的处理方式是**逐条保留 C910 的有效逻辑**（饱和表达式、模式抑制、写旁路优先级），而不是替换成教科书式的 bimodal 或 gshare。理由很实际：原逻辑的偶发行为（例如“方向表更新仍可使整笔训练入队”这类细节）是 3000 周期差分测试的对象；把它“顺手改对”会让所有已完成的等价性验证失效，而且那属于**算法变更**，应该作为独立课题重新评估，不能混在 RV32 地址裁剪里。

## 7. 历史怎么用：为什么“行 = 历史、列 = PC”

方向表的索引被刻意拆成两半：

```text
行     = 历史的函数（不含 PC 项）
行内位置 = PC 的函数（与低位历史异或）
```

这样做买到三件事：

1. **一次阵列读服务整块**。一个 16 B 块里可能有 1～4 条条件分支，如果按“每条分支一次读”来做，就需要多次阵列访问；把 PC 放进行内偏移后，块级一次读回一整行 32 个计数器，块内每条分支只是“换一个 one-hot”而已。这是**吞吐**上的取舍。
2. **读的发起可以早于“知道块内有哪条分支”**。行只依赖历史，因此只要历史确定，行就是确定的；IP 级可以先把行读回来，再等到知道“这条分支在第几个槽”时用偏移取值。这是**时序解耦**：阵列访问的调度不依赖译码结果。
3. **低位历史仍然参与**（异或进行内偏移），所以 22 bit 历史没有被浪费——高位决定行（贵、慢、容量大），低位决定行内位置（便宜、就地），是一种把“历史位按重要性和代价分层”的工程折中。

**为什么同块内第二条分支的偏移要追加“本分支的预测方向”？** 因为方向表的快照是“到达这个块之前的历史”，而块内第 2 条分支实际看到的历史里应该包含第 1 条分支的方向；快照加上该次预测方向才是它真正的上下文。这就是 spec 里强调“每条分支的历史只追加一次”的原因——追加错一次，后面所有分支的上下文都会错位。

## 8. 间接跳转：为什么单独一张表、为什么用路径、为什么退休才训练

- **单独一张表**：见 §4，JALR 的目标不可计算，只能记忆。
- **为什么用“路径 + GHR”而不是纯 PC**：同一个 JALR（典型例子是函数里的返回或函数指针调用）在不同调用点会跳到不同目标，这种“多态”取决于**调用路径**。用最近四次间接控制流的源地址（各取 8 bit）拼成一个路径寄存器，再与 GHR 低 8 位异或，索引就会随调用路径改变——这是一个便宜且有效的“上下文指纹”。纯 PC 索引对多态间接跳转几乎无效。
  类比：这相当于给 TLB 加 ASID/VMID——同一个 VA 在不同上下文下映射到不同 PA，必须把上下文并进索引或标签，否则会互相覆盖。这里的“上下文”就是调用路径。
- **为什么训练只来自 retire0 的误预测**：前端没有寄存器值，唯一知道真实目标的是执行级；但**执行级可能存在错误路径上的指令**（它自己的预测也可能是错的，或者它更老的分支尚未解析）。退休点是“架构状态已确定”的唯一点，所以在那里写入最安全。代价是训练时机晚、且必须走 retire0 特殊口——这正是 spec 里要求后端“把需要该口的误预测事件安排到 retire0”的原因。
- **为什么读要两拍**：物理 SRAM 是同步的，读地址 → 数据需要一个边沿，再加一个输出保持寄存器（避免写操作污染输出）。**这两拍不能靠“猜”绕过**，只能让 IB 容忍等待，并把“等待中”和“未命中”区分开：`fifo_stall` 期间根本不发起读，而 `ind_result_vld` 明确表示“这一笔读回来了”。把这两者混同，就会出现“把还没读到的结果当成 miss”这类错误。

## 9. 返回预测：为什么是栈，为什么是 12+6

- **栈而非表**：返回目标与调用点一一对应，栈可以在零训练、零冲突的情况下精确复现；表则要学习，且同一返回 PC 在多调用点下会互相覆盖。
- **为什么必须支持 x1 和 x5**：见 §2.3。只支持 x1 会漏掉协程与部分编译器输出。同理，`ras_pop` 的判定要处理 `rd == rs1`（同一寄存器既读又写）的组合——这正是 §2.3 表格里“提示分类”与“目标是否可用”必须分开定义的原因。
- **为什么 12 个推测项 + 6 个提交项，而不是 18 个**：推测栈在误预测后**内容已不可信**——错误路径上的 push 已经把栈压歪了。这时候有两种做法：(a) 给推测栈做检查点，能整栈回滚；(b) 只保留“提交侧能证明的”那一小段。本版选 (b)：提交侧的 6 项是唯一有据可查的后缀，恢复时**只重新发布这 6 项**，别的一律作废。代价是恢复后深层返回可能预测不到（回落到 IND/BTB/后端校验），收益是不需要任何内容检查点就能保证“恢复后不会发布错误地址”。
  类比：这就是“推测映射表 + 提交映射表”的关系，只不过提交侧只保留了一小段窗口，而不是完整影子。
- **为什么 RAS 恢复要等退休**：提交侧备份只在指令真正退休时更新；IU 在执行级发现误预测时，提交侧还是旧的。于是协议只能是：IU 先重定向并置起恢复等待（`mispred_stall`），前端在等待期间不做任何依赖 RAS/IND 的推测；等误预测源退休（或更老的全 flush 取代它）时，用提交侧状态恢复并解除等待。**这不是保守到可以省的步骤**：跳过它就意味着用陈旧栈顶去预测返回。

## 10. 目标与 Way：BTB 为什么这样组织

- **为什么“行 = 16 B 块、槽 = 4 条指令”**：RV32I 定长 4 B，一个取指块恰好 4 条指令，所以“块内第几条”天然就是 2 bit 槽号。BTB 存的是**块内位置 + 目标**，一次读回四槽，块内所有分支的目标一次拿全。RV64/RVC 下这件事被半字边界和变长指令搅乱（16 B 里可能有 8 条指令），本版正因为定长才能把映射做得这么干净。
- **为什么只允许 `slot >= 入口槽` 命中**：与 L0 同理——入口之前的槽这次取指根本到不了。
- **为什么要存 Way 提示**：取指要先读 I-Cache 的 Tag 才知道命中哪一路，而 Data 阵列若两路都读，功耗与访问时间都要翻倍。提示让 Data 读只使能一路，是纯粹的**功耗/时序优化**。关键点：提示猜错**不是 Cache miss**——不发总线、不装行、不更新任何替换状态，只是把数据重发一次。把它当 miss 处理会污染 Cache 状态并引入无谓的延迟。
- **为什么允许 BTB“假命中”**：BTB 命中产生的只是一条**可撤销的推测路径**。它猜错时，后端按真实指令语义执行并恢复。但有一条底线：推测**永远不能改变程序语义**——所以当预测给出的目标不可能（例如低两位非 0）时，前端不产生改向，只把“这个目标不可用”作为信息交给后端，由源指令去报地址不对齐异常（§2.4）。这解释了 `bad_target` / `target_unknown` 这对信号存在的意义：它们不是错误，而是“拒绝猜测”的合法结论。
- **为什么主 BTB 更新要经过一级缓冲并做旁路**：阵列是单端口的，而校验结果（BJU）是突发到来的。如果每笔更新都独占端口，取指会被拖住；如果只排队不旁路，紧跟着的取指读到的是旧目标。所以：更新入缓冲 → 端口空闲时写出 → 读出时若命中同一 (源块, 槽) 就用缓冲值覆盖 SRAM 旧值。**旁路必须在读出路径做，而不是改写到 SRAM 里**，否则会和正在进行的读出冲突。这与 store buffer 的 store-to-load forwarding 完全同构。
- **为什么允许连续更新阻塞读、不承诺无损满速**：为一个“可等待重试”的查询加队列，收益只有极端更新突发下的少量周期，代价是一整套流控与死锁分析。本版选择把仲裁责任留给完整 ADDRGEN 控制，并把这个限制写进文档。

## 11. 数据一致性：为什么有 4 项训练缓冲，为什么可以丢

BHT 的更新来自 BJU 校验，读来自取指。二者共用阵列端口，且都不是可以无限等待的对象。

- **缓冲存在的理由**：让校验结果“不丢”，同时不阻塞取指读。
- **缓冲深度为 4 的理由**：校验返回是逐条的（每周期最多一条），而写出只需在端口空闲时进行；4 项足以吸收一次短突发。
- **为什么命中缓冲要比较 (索引, 历史快照) 而不是只比索引**：因为同一个索引在不同历史下对应不同计数器。只比索引就会把无关分支的更新旁路给当前预测，产生难以复现的偶发误预测。所以缓冲条目里必须存**当时的历史**，这是一条数据正确性要求，不是优化。
- **为什么满了就丢**：训练是“给未来的提示”，不是体系结构状态。为它引入反向背压，等于把执行流水线耦合到一张表上，还要在恢复/flush 期间证明不会形成等待环。所以本版沿用“丢弃 + 计数”的有损策略，并用专门的计数器（`bht_train_drop_count`）把损失变成**可观测、可验收**的量，而不是静默发生。丢训练只影响下次预测准确率，**不得影响恢复、提交历史与路径推进**——这条不变量正是把“性能路径”与“正确性路径”分开的体现。
  类比：**store buffer 里的 store 绝不能丢**（那是体系结构状态），而**预取请求可以丢**（丢了下次再发）。训练缓冲属于后者：它只影响“未来猜得准不准”。

## 12. 为什么需要 `local_recover`（局部修复）这个新端口

前端做的是**投机**：它边预测边推进历史。当后面某一级发现“刚才那条预测是错的”时，有两种可能：

- 错误影响的是**已经过去的一大段**（例如执行级发现误预测）→ 用全局恢复：清掉年轻流水、回到提交边界。代价大，但边界清晰。
- 错误只影响**一小段**（例如 L0 假命中、BTB 目标错、块内某分支被截断）→ 只需要把历史回退到“保留下来的那个前缀”，然后继续正常取指。这时如果拉全局 flush，会把仍然有效的较老工作（IBUF 里已经正确的指令）一起丢掉，纯属浪费。

问题在于：**前端自己算不出“保留下来的前缀的历史应该是多少”**——那需要保存历史检查点。所以本版的做法是：由发现错误的那一级把**精确的历史快照**交给预测器（这就是 `local_recover_vld/ghr`），预测器只负责用这个值修复自己（VGHR、hash、偏移、后继恢复标记）。这条设计把“谁负责判断范围”和“谁负责修复状态”分开了，也解释了为什么 `frontend_cancel` 单独存在却不够用：它只能阻止**本拍**产生新事件，不能撤销**已经追加**的历史。

类比：这相当于“按条目失效”与“整表 flush”的区别（§3.2）——但这里失效的对象是**历史状态**而不是表项，所以必须附带一个精确的修复值。

## 13. 裁剪边界：哪些简化来自 ISA，哪些与 ISA 无关

| 变化 | 对预测的影响 | 性质 |
|---|---|---|
| 定长 4 B 指令 | 块/槽映射精确，“块内第几条”= 2 bit 槽号；块内多分支可以按槽序静态枚举 | 真简化 |
| IALIGN=32 | 目标低两位非 0 是**源指令的异常**；前端绝不允许“把 bit1 清零凑一个对齐目标” | 语义收紧（§2.4） |
| 只有 x1/x5 两种链接寄存器 | RAS 提示逻辑简单，但仍要处理 rd/rs1 同寄存器等组合 | 基本不变（§2.3） |
| AUIPC 存在 | 它是 pc_oper（后端需要它的 PC 做校验），但不改向、不进 L0、不追加历史 | 需要显式区分 |
| 无 MMU，PC = PA | 索引与比较的对象是物理地址，预测路径上没有翻译延迟；也不存在虚拟别名造成的索引抖动 | 真简化 |
| 保留特权标签 | IND BTB 项与 RAS 项仍带 priv，比较两次（项内 + 本次读）；跨特权切换不会误用旧目标 | **不能删**（与 MMU 无关） |
| 删除 RVC 相关逻辑 | 去掉半字边界、H0 拼接、bry_missigned 重定位 | 真简化，但“块内多分支分段”仍然存在 |

**要点**：删除 MMU 不意味着删除“上下文”。特权级标签、上下文比较、flush 语义都是预测正确性的一部分；被删掉的只有翻译这一层。

## 14. 取舍总表：每个机制买到什么、付出什么

| 机制 | 买到 | 付出 |
|---|---|---|
| L0 BTB（16 项，组合） | 同拍改向（省下最贵的等待） | 覆盖率极低；需要 IP/IB/ADDRGEN 的校正与定向失效配套 |
| 主 BTB（512×4，双 bank 同步读） | 常规代码的目标覆盖 + Way 提示 | 2 拍延迟；单端口与更新缓冲的仲裁复杂度 |
| Bi-Mode BHT（1024×64 + 128×16） | 抑制别名干扰，长历史相关性可用 | 训练准入逻辑复杂；两套表的写掩码与旁路要成对维护 |
| 22 bit 双历史 | 长相关预测 + 精确恢复 | 两套历史各自维护、各自恢复，恢复优先级必须分明 |
| 4 项训练缓冲 + 旁路 | 校验不阻塞取指、读不读到旧值 | 缓冲条目必须携带历史快照；满时损失训练 |
| IND BTB（256×35，两拍） | 间接跳转目标预测 | IB 必须容忍两拍等待；训练被限制在 retire0 |
| RAS（12+6） | 返回预测近乎精确 | 恢复只能发布 6 项；深层返回在恢复后可能预测不到 |
| 分级改向（IF/IP/IB/后端） | 早猜 + 准猜兼得 | 每一级都要定义“谁能改向、撤销多远、历史怎么回滚” |
| 局部修复端口 | 局部错误不牵连较老工作 | 需要发现错误的那一级提供精确历史快照 |
| 训练可丢（有损） | 不与后端形成背压/等待环 | 准确率有不可控损失，需计数器观测 |

## 15. 迁移这份设计时要记住的原则

1. **按“可预测性来源”划分结构**，不要按“功能名字”划分；JALR 和 return 看起来都是跳转，但一个要学、一个是栈语义。
2. **级数 = 信息量 × 延迟的折中**，不是结构越多越好；每一级都必须能独立地回答“我比不猜好在哪”。
3. **推测可以错，但绝不能改变语义**：不可用的目标要变成标志位，而不是伪造目标。
4. **读路径与训练路径必须成对修改**：索引、历史形式、掩码三者任一改动都要同时改两侧，否则误预测会以“偶发、难复现”的形式出现。
5. **性能路径与正确性路径必须分开**：训练可以丢、可以污染，历史/路径/栈的恢复不可以；把两者混在一根 valid 或一个队列里，就会在恢复期间产生无法证明的行为。
6. **恢复范围要按“可证明”来定**，不是按“我们有几项存储”来定；没有内容证明时只恢复指针 = 允许发布错误地址。
