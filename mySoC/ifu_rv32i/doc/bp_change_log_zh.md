# 分支预测 / L0 BTB 改动日志（P0 期）

本文是 `bp_issues_and_plan_zh.md` §3 "P0 一致性修复"四条改动的逐条 A/B 实测记录。
每条改动都给出：**改了什么 → A/B 两组数字 → 是否达到 §6.4 目标 → 未达标的归因**。

**基线**：`IFU=1`、`ICACHE_EN=1`、`LBUF_EN=0`、`BHT_TRAIN_EN=1`，CoreMark `ITERATIONS=25`。
所有数字都是本机同一套 TB（`tb/tb_miniRV_dpi.sv`，含 `+BENCH` 分场景计数器）实测。

## 0. 摘要（先说结论）

整场 CoreMark `ITERATIONS=25`（10.14M 拍，约 21 分钟）实测，基线是本次重跑的同一套 TB：

| 结论 | 说明 |
|---|---|
| ✅ **硬门槛全过** | `make run-all` **46 项全过（Failed Tests: none）**；CoreMark 三个 CRC（`0xe714`/`0x1fd7`/`0x8e3a`）全对、无 `Diffrence`、`Test Point Pass!`、周期数 **+0.067%**（软门槛 ±1%）|
| ✅ **白取大幅下降** | `invalidate` 196,593 → **150,720（-23.3%）**；其中"方向错"（taken 位粘滞）154,954 → **104,289（-32.7%）** |
| ✅ **降级通路接上了** | kill 从全场 **135 次** → **155,313 次**；废项分配 438,191 次 → **0** |
| ❌ **§6.4 五项指标只达标两项** | 达标：周期数、废项占比。未达：条件分支准确率（86.84% vs 目标 88.5%）、L0 命中率（30.07% vs 目标 45%）、invalidate/accept（14.16% vs 目标 8%）|
| ⚠️ P0-1 的**字面写法是错的**，直接照抄会打穿调用/返回 | `chk_idx[24]` 是 BHT 计数器低位，对 `jal/jalr` 没有意义 → L0 命中 5,372 → 0。详见 §2.1 |

| ⚠️ **审计文档的因果链有一条被实测推翻** | P-1 把"命中率只有 33%"归因于"废项挤掉有用项"；实测把废项降到 0 之后命中率**没有上升**。所以**不是搅动**。（本节原写"真正原因是 16 项表的容量"，**该结论已于 2026-09-24 作废**：自研核同样有大 BTB 且命中率 87.03%，L0 只是快滤，命中率低本来就是设计使然。详见 §4.1 的更正框）|
| ⚠️ **ITER=1 快速代理在这个指标上方向是反的** | invalidate/accept：代理说变差（9.88→10.34%），整场说变好（15.87→14.16%）。详见 §3.3 |

**一句话**：P0 把审计文档点名的三条行为错都修对了，代价是 0.067% 的周期，
换来白取 -23%、方向冲突 -33%、废项归零 —— 但**没有**换来准确率与命中率的提升。

> ⚠️ **2026-09-24 补**：本文原先把"L0 命中率没提升"归因于"16 项表容量不够、
> 只能加表项"。**该归因已作废** —— 自研核同样有 L1 大 BTB（`rv32_ifu_btb.v`）且实测
> 命中率 **87.03%**，L0 只是它前面的快滤，命中率低是设计使然。§6.4 里"L0 命中率 >45%"
> 这个目标本身需要重新讨论。

## 1. 新增定向基准 `asm/branch_bench.S`（P0 的验证前提）

### 1.1 为什么必须新建

既有小用例不可用：`beq` 全程只有 1,509 拍，其中 1,027 拍是 IFU 初始化，统计量被淹没。
CoreMark 只能看总量，**分不出是哪一类分支在变好/变差** —— 而 P0 的三条改动恰好各自
只对某一类分支生效（not-taken 的分支 / 弱 taken 的分支 / 调用返回）。所以先建基准。

### 1.2 设计

五个互不重叠的 PC 区间，TB 按 `pc_EX` 分桶统计（`+BENCH` 才启用，CoreMark 不受影响）：

| 类 | PC 区间 | 场景 | 条数/间隔 | 用途 |
|---|---|---|---|---|
| 1 | `[0x100,0x140)` | 稳定 taken 的循环回边 | 3 条 / 16B | 回边 48/16/24 次才退出，BHT 饱和到强 taken |
| 2 | `[0x140,0x1c0)` | 几乎不跳的前向分支 | 8 条 / 16B | 条件恒假（`x6=x8=1` 的各种反向比较），**恒不跳** |
| 3 | `[0x1c0,0x250)` | 交替 taken/not-taken | 8 条 / 16B | `x9` 每轮翻转，8 条同相位交替 |
| 4 | `[0x250,0x290)` | 函数调用/返回 | 4 调用点 + 2 被调函数 | 同一函数被 4 个不同调用点调用 ⇒ 4 个不同返回地址，只有 RAS 对才活得下来 |
| 5 | `[0x290,0x320)` | 偏 taken 的 T,T,T,N 节奏 | 8 条 / 16B | **专门造"弱 taken 预测"**（见 1.4） |
| 0 | 其余 | 外层循环 / 初始化 / 退出 | — | 只作对账 |

- **运行长度**：外层 512 轮，实测 **179,748 拍**（要求 ≥ 5 万拍），IFU 初始化 1,027 拍占
  **0.57%**（要求 < 2%）。`make run TEST=branch_bench` 通过，difftest 干净。
- **为什么 16 字节间隔**：BHT 的选择阵列索引取 `PC[9:3]`
  （`rv32_ifu_bht.v:456 bht_sel_array_index = pcgen_bht_pcindex[9:3]`，而
  `pcgen_bht_pcindex = pc_bus[13:4]`）。16 字节间隔让每条静态分支的 `PC[13:4]` 与
  `PC[9:3]` 都不同，避免"类内 8 条分支共用 1 个 2 位计数器"把场景测歪。
- **布局约束**：`.org` 定死地址，TB 的 `bench_class()` 与 `.S` 头部注释是同一个契约，
  两边必须一起改。已用 `objdump` 逐条核对分支落点。
- **行尾对账**：报告最后打印"各桶条件分支合计 = 全局 `n_cond`"，实测精确相等
  （57,858 = 57,858），保证没有分支掉进桶外。

### 1.3 基线实测（改动前）

| 类 | 条件分支数 | 准确率 | 误预测 | 弱 taken | L0 命中 | 分配 | 其中废项 |
|---|---|---|---|---|---|---|---|
| 1 回边 | 45,056 | 95.79% | 1,896 | 2,038 | 46,761 | 1,908 | 261 |
| 2 不跳 | 4,096 | 100.0% | 0 | 0 | **0** | 4,096 | **4,096** |
| 3 交替 | 4,096 | 50.00% | 2,048 | 0 | **0** | 4,096 | **4,096** |
| 4 调用 | 0 (jal/jalr 4,608) | jal/jalr 100% | 0 | 0 | 5,372 | 4,095 | 0 |
| 5 T,T,T,N | 4,096 | 89.33% | 437 | **512** | 782 | 4,473 | 667 |

类 2/3 的 **8,192 次分配一个都命中不了**（0 命中）—— 这就是 P-1 说的废项，而且它直接
体现在类 4 上：调用/返回那一类的 L0 判错是 **511 次 = 每轮外层循环 1 次**，因为表被
类 2/3 的废项冲掉，类 4 的条目每轮都要重新分配，中间有个窗口用的是旧 target。

### 1.4 类 5 是补出来的，原因值得记一笔

最初按 §6.4 只做了四类，其中类 3 用纯交替。实测发现**类 3 的 BHT 落进了"恒预测不跳"
那个双稳盆地**（`预测 taken = 0`），于是整类一条弱 taken 都产不出来 ——
P0-1/P0-2 唯一会改行为的那个事件类（`bht_pred=1 && chk_idx[24]=0`）**完全没有被覆盖**。

所以补了类 5：`x30` 每轮 +1、`x29 = x30 & 3`、`x29 != 3` 时前向跳。稳态结局序列是
T,T,T,N —— 2 位饱和计数器停在 `11`，每次 N把它压到 `10`，下一个 T 就是"用弱计数器预测
taken"。实测该类产出 **512 次弱 taken**（占 4,096 次的 12.5%），靶子成立。

> 类 3 保留纯交替不动（那是 §6.4 明确要求的场景），类 5 是补充覆盖，不是替代。

## 2. P0-1..P0-4 逐条记录

改动都落在 `rv32_ifu_l0_btb.v`，配套把 `train_packet[184]`（= `chk_idx[24]` = 预测当时
BHT 计数器低位）从 ibctrl 经 `rv32_ifu_pipeline` / `rv32_ifu_top` / `rv32_ifu_bp_top`
接到 L0 的新端口 `update_cnt_lo`（4 个文件的端口表各加一根线）。

### 2.1 P0-1 武装条件改为强 taken

**改法（最终）**

```verilog
// rv32_ifu_l0_btb.v
assign update_cnt_bit = update_taken && ((update_type != 3'd1) || update_cnt_lo);
```

**为什么不是文档里的字面写法** —— 文档 §3 写的是 `update_cnt_bit = train_taken & train_packet[184]`。
照字面做完，`branch_bench` 类 4（调用/返回）的 **L0 命中从 5,372 掉到 0**，判错从 511 变 0：

| 指标（branch_bench） | 基线 | 字面 P0-1 | 带 `con_br` 限定 |
|---|---|---|---|
| 类 4 L0 命中 | 5,372 | **0** | 5,372 |
| 类 4 L0 判错 | 511 | 0 | 511 |
| 类 1 判错 | 370 | 131 | 131 |
| 全局 invalidate | 1,258 | 506 | 1,017 |
| 命中率 | 50.75% | 44.42% | 49.25% |

原因：`chk_idx[24]` 是 **BHT 计数器**的低位。条件分支的 `update_taken` 就是 BHT 方向预测位，
所以"taken 且低位=1"确实等价于 `counter==2'b11`（强 taken）；但 `jal/jalr` 的
`update_taken` 来自 `prediction_taken = ... || jal || (jalr && btb_hit)`，**跟 BHT 计数器
没有关系**，那个低位对该 PC 就是一个无关的计数器残余值。拿它去决定 jal/jalr 要不要武装，
等于用噪声门控，实测那些 PC 的残值多数是 0，于是调用/返回的 L0 项全部不再武装。

查 C910 源码证实这就是它带 `con_br` 限定的原因（`ct_ifu_ipdp.v:5856-5862`）：

```verilog
assign l0_btb_counter_zero = ifdp_ipdp_l0_btb_hit && !ifdp_ipdp_l0_btb_counter
                          && ... && ipctrl_ipdp_con_br          // <-- 只对条件分支
                          && (bht_pre_result[1:0] == 2'b11);
```

无条件转移在 C910 里走的是另一条依据（分配时 `ct_ifu_ibdp.v:2287
l0_btb_update_cnt_bit = |ibdp_hn_jal[7:0]`，即"块里有 jal 就武装"）。所以这里按
`update_type` 分开：**条件分支看强 taken，jal/jalr 维持原语义**（`update_taken` 本身）。

**A/B（branch_bench，累计）**

|---|---|---|---|
| 周期数 | 179,748 | 179,599 | **-149 (-0.08%)** |

| 类 1 L0 判错 | 370 | 131 | **-239 (-65%)** |

**判定**：**未达 §6.4 目标**。定向基准上是小赢（判错 -65%），CoreMark 上是小输
（周期 +0.31%、准确率 -0.30pp、invalidate/accept 反而变差）。

**归因**：C910 的"只有强 taken 才武装"是**保守**规则。CoreMark 里有大量"弱 taken 且倾向
taken"的分支，旧行为在第一次弱 taken 就武装并开始提前改向，其中**大部分改向是对的**
（ITER=1：`accept` 掉 8,353，条件分支误预测只多 205；整场：`accept` 掉 260,559，
误预测多 5,098 ⇒ 两边都是 **约 98% 的丢失改向本来是对的**）。少掉的改向要等
IP 级再改，多花的是取指气泡，所以周期涨、准确率跌。

周期退化 **+0.31%（ITER=1）/ +0.56%（整场，见 §3.2）< 1%**，按 A2 软门槛不回退；
语义对齐（A3/C1）优先。但 §3.2 的整场逐条归因说明：**只上 P0-1 是净亏**，
必须和 P0-2/P0-3 一起上才有正效果。

### 2.2 P0-2 撤销条件改为弱 taken

**改法**

```verilog
// 旧: update_kill = update_en && update_match && !update_taken && update_cnt_armed;
// 新:
assign update_kill = update_en && update_match && update_taken && !update_cnt_lo &&
  (update_type == 3'd1);
assign update_hold = update_en && update_match && !update_taken;
```

对齐 C910 `l0_btb_not_saturate`（`ct_ifu_ipdp.v:5850-5855`，触发条件是
`bht_pre_result[1:0] == 2'b10`，即弱 taken）+ `l0_btb_wen[3] = ... && (not_saturate || mistaken)`。
按 A3 去掉 `update_cnt_armed` 门控；同 P0-1 的理由保留 `con_br`（`update_type == 3'd1`）限定。
`update_cnt_armed` 变成死信号，已删除（A4）。

"删掉"vs"留着不武装"的固有代价：C910 用 `wen[3]` 删项、用独立的 IP 级分配通路补回，
本版两者挤在同一条 ibctrl 通路上，删一次就得在下一次 miss 时重新填。定向基准上净效果
几乎为零（-15 拍），说明这个代价被"少一次错误改向"抵消了，但没有正收益。

### 2.3 P0-3 分配加资格

**改法（两处，必须一起改）**

```verilog
assign alloc_vld = update_en && !update_match && update_taken;

// 关键: update_fire 也要跟着改
assign update_fire = update_en && ((update_match && !update_hold) || alloc_vld);
```

> **坑（必须记）**：文档只写了改 `alloc_vld` 一行。但 `ibdp_update_entry[entry] =
> update_match ? update_select : entry_fifo_q[entry]` —— **未命中时写入的目标是 FIFO 头项**，
> 而 FIFO 只在 `alloc_vld` 时推进。只改 `alloc_vld`、不改 `update_fire`，就会出现
> "写头项但不转格"，反复覆写同一个槽 ⇒ 表里出现同 PC 重复项 ⇒ 正好是 P-4 那颗地雷的
> 触发器。TB 的"同 PC 重复项导致多路匹配"计数器实测 **0 拍**，确认两处一起改之后没有踩到。

**A/B（branch_bench，相对 P0-1+2）**

| 指标 | P0-1+2 | P0-1..3 | 变化 |
|---|---|---|---|
| 周期数 | 179,584 | 179,585 | +1 |
| **废项分配（类 2/3/5）** | 9,004 | **0** | **全清** |
| 类 2 分配 | 4,096 | 0 | -4,096 |
| 类 3 分配 | 4,096 | 0 | -4,096 |
| **类 4 L0 命中** | 5,372 | **7,564** | **+2,192 (+41%)** |
| 类 4 L0 判错 | 511 | 1,033 | +522 |
| 全局 accept | 48,704 | 49,746 | +1,042 |
| 全局 invalidate | 1,014 | 1,538 | +524 |
| 全局命中率 | 49.27% | 51.38% | +2.11pp |
| 总分配 | 15,166 | 11,299 | -3,867 |
| 同 PC 重复项 | 0 | **0** | 自检通过 |

类 4 的 +41% 命中就是"不再被废项冲掉"的直接证据 —— 这**证实**了废项确实在伤害别的类。

### 2.4 P0-4 选择优先级与查找一致

**改法**

```verilog
// 旧: update_select[entry] = update_match_vec[entry] && !(|(update_match_vec & HIGHER_ENTRIES));
// 新:
assign update_select[entry] = update_match_vec[entry] && !(|(update_match_vec & LOWER_ENTRIES));
```

顺带删掉变成死代码的 `HIGHER_ENTRIES`（A4）。

**A/B**：branch_bench 周期数 179,585 → **179,585**；CoreMark ITER=1 **435,248 → 435,248**，
把两次运行除 VCS 抬头以外的输出做了 `diff`，**逐行完全相同**。

**判定**：**当前负载下是纯 no-op**，与文档 §2 P-4 的预判一致（`alloc_vld = update_en &&
!update_match` 保证一个 PC 在表里最多一条有效项，`同 PC 重复项 = 0`）。
保留的理由不是性能，是**拆雷**：P1 一旦把分配改成"IP 级报 miss 才分配"，分配与命中就不
再来自同一个独占判定，重复项立刻会出现，届时"更新打最高编号、查找打最低编号"会变成
"查找可见的那条永远陈旧"的正反馈。这是为 P1 铺路，收益要在 P1 才体现。

## 4. 对审计文档的三处修正（实测得出，供 P1 参考）

### 4.1 P-1 的因果链是错的：命中率低是**容量**问题，不是搅动问题

> ⚠️ **本节结论已作废（2026-09-24 更正）**。本节的推理建立在一个**没验证的前提**上：
> "自研核的 16 项 L0 BTB 是唯一的 BTB"。**这个前提是错的** —— 自研核同样有 L1 大 BTB
> （`rv32_ifu_btb.v`，例化于 `rv32_ifu_bp_top.v:408`），实测查询 96,184 拍、
> **命中 83,712 拍（87.03%）**，是目标预测的主力；L0 只是它前面的快滤。
> 因此"L0 命中率低 ⇒ 容量不够 ⇒ 要加表项"**推不出来**：L0 命中率低本来就是快滤的
> 正常表现。下面"把 PC 在不在表里与在表里但没武装分开量"那个实验建议仍然有效
> （它能说明 L0 的**训练质量**），但**不要再以"L0 命中率 >45%"为目标**。
> 分类的 L1 命中率实测：类1 94.14% / 类2 99.68% / 类3 77.17% / 类4 93.77% / 类5 48.97%。

文档 §2 P-1 的推理是：废项进表 → 16 项 FIFO 每分配一次转一格 → 条目存活 ≈ 200 拍 →
命中率只有 33%。

**实测反例**：P0-3 把废项从 16,434 次降到 **0**、总分配砍掉 **52%**，命中率却**没有上升**
（34.83% → 33.37%，反而略降）。如果 33% 是搅动造成的，分配减半应该让命中率明显上升。

**真实原因**：16 项表的容量远小于 CoreMark 的控制转移工作集。废项清干净之后，
有效条目均值反而从 10.40 **降到** 7.24（表里东西更少了，但都是有用的），
命中率却没有上升 —— 说明**大部分查询的 PC 根本不在表里**。

> **⚠️ 不要用 TB 的"表内平均武装条目"当证据**：那一栏读的是 `entry_cnt` 的 popcount，
> 而 `entry_cnt` 在删项时**不会被清**（`rv32_ifu_l0_btb_entry.v` 只在 `entry_wen[2]` 时
> 写 cnt，删项是 `wen[3]`）—— 核实过 C910 的 `ct_ifu_l0_btb_entry.v` 也是同样写法，
> 所以这不是本版的偏差，但它的后果是：被 kill 掉的条目 `vld=0, cnt=1`，
> 于是这一栏会数出一堆"已删除但仍计为武装"的条目，出现 **武装(13.44) > 有效(7.24)**
> 这种不可能的组合。功能上无害（命中由 `entry_vld` 把关），但**这一栏不能作为
> "表里有多少可命中条目"的依据**。要拆分"PC 不在表里"与"在表里但没武装"，
> 应该直接对 `entry_rd_hit`（vld 门控）与 `eligible` 分别计数 —— 见 §5.3 第 1 条。

**对 P1 的含义**：P1 若只做"更新源回归 IP 级 + 命中 one-hot 随包"，**不会**把命中率推到
45%。要提升命中率只有两条路：**(a) 把 L0 项数做大**（16 项是 RV32 适配时定的，C910 是
多少需要重新核对）；**(b) 提高该进表的 PC 的进表率/存活率**。
建议 P1 立项前先量清楚 `entry_rd_hit` 与 `eligible` 两条计数（上面那条），
用数据决定是扩表还是改分配策略。

### 4.2 invalidate/accept 的分母在 P0 之后变了，看这条比值要小心

`accept` 在 P0 之后掉了 ~15%（54,980 → 46,984）又回到 52,488，invalidate 几乎没动
（5,431 → 5,426）。所以 invalidate/accept 从 9.88% 变成 10.34% **主要是分母变小**，
不是白取变多。§6.4 用这条比值当验收指标时，必须同时看两个绝对值（审计文档 §4 已经写了
这一条，实测再次验证）。

### 4.3 调用/返回那一类的 L0 target 会系统性地错

branch_bench 类 4（4 个调用点调用同一函数）在 P0-3 之后 L0 命中涨到 7,564，
判错也涨到 1,033（**≈ 每轮外层循环 2 次**，正对应 2 个 `ret` 站点）。
原因是 L0 里每个 PC 存的是一个**静态** target，而 `ret` 的正确目标依赖 RAS。
P0 期间废项把条目冲掉所以看不出来；表不再搅动之后它就暴露了。
这正是 P1 要解决的（命中 one-hot + IP 级 `mispred_pc` 身份判定），
**建议 P1 把"ret 站点"单独拎出来量一次**。

## 5. 结论与遗留

### 5.1 P0 达到了什么

1. **三条行为错都修对了**（整场 ITER=25 实测证据）：
   - 武装只看强 taken（条件分支）—— 弱 taken 事件在 branch_bench 类 5 上被单独计到 512 次；
   - 降级删项真正生效 —— kill 从全场 **135 次**变成 **155,313 次**；
   - 分配加资格 —— 废项从 **438,191 次**变成 **0 次**。
2. **白取下降 23.3%**，其中方向冲突下降 32.7%。这是审计文档点名的核心症状。
3. **拆掉了 P1 的前置地雷**：`update_fire`/`alloc_vld` 一致性、`update_select` 与
   `hit_select` 同向。
4. **新增了可复用的定向基准** `asm/branch_bench.S`（179,748 拍，五类场景，PC 分桶，
   `make run TEST=branch_bench` 通过）。

### 5.2 P0 没有达到什么（必须如实记录）

- §6.4 五项指标**只达标两项**（周期数 +0.067%、废项占比 0%）；
  条件分支准确率、L0 命中率、invalidate/accept 三项未达。
- **L0 查询命中率反而降了 3.02pp**（33.09% → 30.07%），而 accept 少了 14%。
  这是"少而准"的交换：白取降得比 accept 更多，所以 inv/accept 比值改善、
  周期几乎不动。但**命中率这一项就是退化了**，不能粉饰。
- **P0 没有带来准确率收益**（86.87% → 86.84%，基本持平）。这是设计使然：
  "P0 阶段不动结构，只改 L0 更新语义那四处"（C1），而这四条都是**收紧**规则
  （少分配、少武装、多删项）；准确率的提升要靠 P1 拿到 `l0_btb_hit` / `mistaken` /
  `bht_pre_result` / `con_br` 这些 IP 级资格信息、以及 C910 的 `mispred_pc` 身份判定
  之后才有可能。

### 5.3 下一步（建议调整 P1 的优先级）

1. **先量容量，再动结构**（§4.1）：加两个 TB 计数 —— 对 `entry_rd_hit`（PC 在表里，
   vld 门控）与 `eligible`（在表里**且**可命中）分别数 popcount，就能把
   "PC 不在表里" 与 "在表里但没武装" 分开。这一步很便宜，但决定了 P1 是先扩表
   还是先改分配策略。**不要**再用 `entry_cnt` 的 popcount 当依据（理由见 §4.1）。
2. **P1 按原计划做**：更新源回归 IP 级 + 命中 one-hot 随包带，删掉 ibctrl 的自创 `train_*`。
   P0-4 已把选择优先级对齐，P1 换 one-hot 时不会再踩重复项的坑。
3. **`ret` 站点单独量**（§4.3）：P0 之后目标存错**涨了 13%**（32,226 → 36,422），
   主要来自"表不再搅动之后，`ret` 站点的静态 target 系统性地错"。这正是 P1 的
   命中 one-hot + `mispred_pc` 身份判定要解决的，建议 P1 接收前先量一次基线。
4. **per-change 整场归因**：本次只跑了"P0-1 only"与"P0-1..4"两个整场（见 §2 的
   逐条 ITER=1 + 整场）——因为 ITER=1 代理在比值类指标上方向不可靠（§3.3），
   逐条整场才是可信的归因手段。后续 P1 的每条改动建议直接上整场。
5. 回归门槛维持不变：`make run-all` 46 项全过（已实测通过）+ CoreMark 三 CRC +
   无 `Diffrence`。

6. **下一步要查的问题清单见 `bp_next_questions_zh.md`** —— 按优先级排好了，
   每条附已有数据、可验证假设、具体测法。**开新会话调查时从那里开始。**

1. **2.70pp 的差距全部来自类 3，而且已经定位到一条很窄的现象**：类 3 的 8 条分支在
   自研侧 **4096 次里一次 taken 都没预测出来**（`预测 taken (BHT) = 0`），准确率 50%。
   **这不是"2 位计数器在 50/50 输入下的正常表现"** —— 正常的饱和计数器在交替输入上
   会在 01/10 之间摆动，至少一半的拍会预测 taken（准确率同样是 50%）。一次都不出，
   说明计数器被摁在 not-taken 上。

   ⚠️ **并更正对比文档里的一处说法**：原先写"C910 用了历史、自研侧没用"是**错的**。
   `rv32_ifu_bht.v:374-394` 与 `ct_ifu_bht.v` 逐字同源（同一个 `pc[6:3] ^ vghr[3:0]`
   索引公式），`pre_vghr_offset_0` 驱动完整，pre-array 也真的例化了；TB 挂探针实测
   **GHR 是活的**（branch_bench 下 `vghr_q` 变化 47,806 次）。机制在，是**这个场景下
   没起作用**。详见 `bp_c910_vs_minirv_zh.md` §3.5。

   注意类 1 两边几乎一样（95.79% vs 95.67%），所以问题不在"偏斜分支"。
2. **C910 的可用 L0 命中里 4,129/4,301 = 96% 是返回地址**（类 1/2 是 0）。
   它的 L0 BTB 只是大 BTB 前的快滤，条件分支目标由更大的 BTB 给。
   ⚠️（2026-09-24 更正：本节原写"印证 §4.1…想提命中率只能加表项"，但 §4.1 的前提
   ——"L0 是唯一的 BTB"——已被实测推翻：自研核的大 BTB 在工作且命中率 87.03%。
   下面这句只保留"L0 命中几乎全是返回地址"这个观察本身。）
   不要拿 C910 的 L0 命中率当对标目标。
3. **类 1/2/4 已经没有改进空间**（95.7~100%），P1 的收益不应寄希望于它们。

完整文档另见 `bp_c910_vs_minirv_zh.md`（含 C910 侧观测点的语义坑：误差分支一定在
retire slot0、`ret` 不算 `jmp`、IF 侧 PC 总线是 `PC[39:1]`）。

三条修法（换 GHR 喂料 / 接通 `pcgen_bht_chgflw` / 接通 LBUF），
